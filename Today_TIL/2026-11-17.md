## 2. 학습 데이터 생성

### 규정 그룹과 사례 만들기

먼저 12개의 규정 그룹을 생성하고, 각 그룹에서 6가지 사례를 만들어 총 72개의 데이터를 구성했다.

```python
groups = [
    {
        "group_id": f"policy{i:02d}",
        "team": team,
        "limit": limit,
        "updated_limit": limit + 10000,
    }
    for i, (team, limit) in enumerate(
        zip(teams, limits), start=1
    )
]

case_specs = []

for group in groups:
    old_document = make_document(group)
    new_document = make_document(group, updated=True)

    # [일부 생략] 그룹별 6가지 사례 생성 및 저장
```

`zip()`으로 팀과 규정 한도를 묶고, `enumerate()`로 그룹 번호를 부여한다.

`make_document()`는 기존 규정과 개정 규정을 문서 형태로 만드는 함수다. 이후 각 그룹마다 6가지 상황을 구성해 `case_specs`에 저장한다.

여기서 `groups`와 `case_specs`의 차이를 구분하는 게 중요했다.

- `groups`: 규정 자체에 대한 정보
    
- `case_specs`: 규정을 이용해 만든 질문과 조건 정보
    

결과적으로 규정 그룹 12개에서 사례 72개가 만들어진다.

### 모범답안 생성

생성한 사례의 정답은 `reference_answer()`에서 만든다.

```python
def reference_answer(spec):

    if spec["case_type"] in {"missing", "irrelevant"}:
        return {
            "status": "abstained",
            "answer": "...",  # [생략] 보류 안내 문구
            "citations": [],
        }

    amount, limit = spec["amount"], spec["limit"]

    if amount > limit:
        answer = ...  # [생략] 승인 필요 안내
    else:
        relation = (
            "한도와 같으므로"
            if amount == limit
            else "한도 이하이므로"
        )
        answer = ...  # [생략] 승인 불필요 안내

    return {
        "status": "answered",
        "answer": answer,
        "citations": [spec["documents"][0]["id"]],
    }
```

처음에는 LLM이 모범답안을 생성하는 줄 알았는데, 이번 실습에서는 Python 함수가 정해진 규칙에 따라 답변을 만든다.

먼저 `case_type`을 확인해서 근거가 부족한 상황이면 `abstained`를 반환한다. 그렇지 않으면 질문 금액과 규정 한도를 비교해 답변을 생성한다.

반환값은 `status`, `answer`, `citations` 세 가지다.

여기서 `abstained`는 근거가 부족해서 답변을 보류했다는 의미이고, `citations`는 답변에 사용한 문서 ID를 뜻한다.

이 방식으로 답변 가능한 데이터 48개와 답변을 보류하는 데이터 24개가 생성된다.

**정리하면, 모델이 학습할 정답을 먼저 일정한 규칙으로 만들어 두는 과정이다.**

## 3. 학습 대화 형식 구성

### case_specs를 messages로 변환

앞에서 만든 `case_specs`는 아직 모델이 학습할 대화 형식이 아니다.

이를 `system`, `user`, `assistant`로 구성된 `messages` 형태로 변환한다.

```python
rows = []

for spec in case_specs:
    model_input = {
        "question": spec["question"],
        "documents": spec["documents"],
    }

    rows.append({
        "id": spec["id"],
        "group_id": spec["group_id"],
        "case_type": spec["case_type"],
        "messages": [
            {"role": "system", "content": SYSTEM_PROMPT},
            {
                "role": "user",
                "content": json.dumps(
                    model_input, ensure_ascii=False
                ),
            },
            {
                "role": "assistant",
                "content": json.dumps(
                    reference_answer(spec),
                    ensure_ascii=False
                ),
            },
        ],
    })
```

각 메시지의 역할은 다음과 같다.

|구분|역할|
|---|---|
|system|모델이 따라야 할 답변 규칙|
|user|질문과 근거 문서|
|assistant|모델이 학습할 모범답안|

코드를 보면 `group_id`, `case_type`은 레코드에 저장하지만 `user` 메시지에는 넣지 않는다.

이유는 두 값이 실제 질문을 해결하는 데 필요한 정보가 아니라 데이터 관리용 메타데이터이기 때문이다.

특히 `case_type`을 입력에 포함하면 모델이 근거를 확인하기 전에 어떤 답변을 해야 하는지 힌트를 얻을 수 있다. 이런 경우 모델이 규정을 판단하는 대신 메타데이터에 의존할 위험이 있다.

이 부분을 공부하면서 **데이터를 관리하기 위해 필요한 정보와 실제 모델에 입력해야 하는 정보는 다르다**는 점을 알게 됐다.

최종적으로 `case_specs` 72개가 학습 대화 레코드인 `rows` 72개로 구성된다.

## 4. 토큰화와 정답 경계 확인

### 입력과 정답을 따로 토큰화하는 이유

토큰화는 텍스트를 모델이 처리할 수 있는 토큰 ID로 변환하는 과정이다.

이번에는 `apply_chat_template()`을 사용해 입력 부분과 정답을 포함한 전체 대화를 각각 토큰화했다.

```python
prompt_ids = tokenizer.apply_chat_template(
    sample["messages"][:2],
    tokenize=True,
    return_dict=False,
    add_generation_prompt=True,
)

full_ids = tokenizer.apply_chat_template(
    sample["messages"],
    tokenize=True,
    return_dict=False,
    add_generation_prompt=False,
)

assert full_ids[:len(prompt_ids)] == prompt_ids

answer_ids = full_ids[len(prompt_ids):]
```

여기서 두 변수의 차이가 중요하다.

- `prompt_ids`: system과 user를 토큰화한 결과
    
- `full_ids`: system, user, assistant 전체를 토큰화한 결과
    

`add_generation_prompt=True`는 모델이 assistant 답변을 생성할 수 있도록 응답 시작 부분을 추가하는 설정이다.

두 번 토큰화한 뒤에는 `assert`로 `full_ids`의 앞부분이 `prompt_ids`와 정확하게 일치하는지 확인한다.

이 검사가 통과하면 `len(prompt_ids)`를 기준으로 정답이 시작되는 위치를 구할 수 있다.

### 확인한 결과

```
prompt_ids = 299
full_ids   = 376
answer_ids = 77
```

전체 376개 토큰 중 입력에 해당하는 부분이 299개이고, 이후 77개가 정답 영역이다. 여기에는 답변 종료 토큰과 마지막 줄바꿈도 포함된다.

처음에는 굳이 두 번 토큰화할 필요가 있는지 궁금했는데, 이후 SFT에서 입력 부분과 정답 부분의 손실 계산을 구분하기 위해 필요한 과정이었다.

실제 입력 영역을 `labels=-100`으로 마스킹하는 작업은 3장에서 진행한다.

### 최대 토큰 길이 확인

전체 72개 데이터의 토큰 길이는 257~380개였고, 설정한 `MAX_LENGTH=512`를 초과한 데이터는 없었다.

토큰 길이를 확인하는 이유는 입력을 잘못 자르면 근거 문서나 정답의 종료 토큰이 사라질 수 있기 때문이다.

단순히 최대 길이로 잘라서 사용하는 것보다 실제 데이터의 길이를 먼저 확인하는 게 중요하다는 것을 배웠다.

## 5. 데이터 품질 검증

### validate_record()로 데이터 확인

학습 데이터를 생성했다고 바로 학습에 사용하는 것이 아니라, 데이터가 정해진 구조와 규칙을 지키는지 검사한다.

```python
def validate_record(row):
    spec = specs_by_id[row["id"]]

    messages = row["messages"]
    check_message_fields(messages)

    user = json.loads(messages[1]["content"])

    # [일부 생략] 원본 사례와 user 내용 비교

    response = json.loads(messages[2]["content"])
    check_response_fields(response)

    # [일부 생략] 인용 문서 ID 및 중복 검사

    check_reference_rule(
        spec, response, response["citations"]
    )
```

검증 함수는 크게 다음 항목을 확인한다.

|함수 및 검사|확인하는 내용|
|---|---|
|식별 정보 검사|ID 및 메타데이터|
|`check_message_fields()`|메시지 구조와 역할|
|`check_response_fields()`|응답 JSON 형식|
|인용 검사|실제 제공된 문서 ID인지 확인|
|`check_reference_rule()`|답변이 정해진 조건과 일치하는지 확인|

정상 데이터 72개는 모두 검사를 통과했다.

### 잘못된 데이터도 검사하기

이번에 중요하게 본 부분은 정상 데이터만 확인하지 않았다는 점이다.

`copy.deepcopy()`로 원본 데이터를 복사한 뒤 일부러 잘못된 값을 넣고, `validate_record()`가 오류를 탐지하는지 확인했다.

```python
bad_citation = copy.deepcopy(sample)

response = json.loads(
    bad_citation["messages"][2]["content"]
)

response["citations"] = ["없는-문서"]

bad_citation["messages"][2]["content"] = (
    json.dumps(response, ensure_ascii=False)
)

# [일부 생략] validate_record()로 오류 탐지
```

`copy.deepcopy()`는 원본과 독립적인 복사본을 만드는 함수다. 따라서 복사본을 수정해도 원본 데이터에는 영향을 주지 않는다.

검증 결과 정상 데이터는 72/72개 통과했고, 의도적으로 만든 오류도 2/2개 탐지했다.

**검증 함수는 정상 데이터를 통과시키는 것뿐 아니라 잘못된 데이터를 제대로 거절하는지도 확인해야 한다는 점을 배웠다.**

## 6. group_id 기준 데이터 분할

### 행 단위로 나누지 않는 이유

학습 데이터를 train, dev, test로 나눌 때는 같은 규정에서 만들어진 사례가 서로 다른 데이터셋에 포함되지 않도록 해야 한다.

이런 관련 정보가 학습과 평가에 동시에 들어가면 모델이 이미 본 정보를 활용해 평가 문제를 맞힐 수 있다.

이를 **데이터 누수(Data Leakage)** 라고 한다.

이번 실습에서는 이를 줄이기 위해 `group_id`를 기준으로 데이터를 분할했다.

```python
group_ids = sorted({
    row["group_id"] for row in rows
})

random.Random(SEED).shuffle(group_ids)

split_groups = {
    "train": set(group_ids[:8]),
    "dev": set(group_ids[8:10]),
    "test": set(group_ids[10:]),
}

splits = {
    name: [
        row for row in rows
        if row["group_id"] in selected_groups
    ]
    for name, selected_groups
    in split_groups.items()
}

check_split_overlap(split_groups, splits, groups)
```

처리 순서는 다음과 같다.

1. `group_id`를 중복 없이 추출한다.
    
2. `sorted()`로 순서를 고정한다.
    
3. `SEED=42`를 사용해 그룹 순서를 섞는다.
    
4. `split_groups`에서 각 데이터셋의 그룹을 정한다.
    
5. `splits`에서 해당 그룹에 속한 실제 데이터를 가져온다.
    
6. `check_split_overlap()`으로 중복 여부를 검사한다.
    

여기서 헷갈렸던 부분은 `split_groups`와 `splits`의 차이였다.

- `split_groups`: 각 데이터셋에 포함할 그룹 ID
    
- `splits`: 해당 그룹에 속한 실제 데이터 레코드
    

### 분할 결과

|구분|그룹 수|데이터 수|역할|
|---|---|---|---|
|train|8|48|모델 학습|
|dev|2|12|모델 점검 및 비교|
|test|2|12|최종 평가|

그룹 단위 분할 결과, train/dev/test 사이에 겹치는 그룹은 0개였다.

이번 내용을 통해 데이터를 단순히 무작위로 나누는 것과 관련성을 고려해서 나누는 것은 차이가 크다는 것을 알게 됐다.

특히 평가 데이터를 어떻게 구성하는지에 따라 모델 성능을 신뢰할 수 있는지가 달라진다는 점이 중요했다.

## 7. 데이터 저장과 재현성

마지막으로 분할한 데이터를 JSONL 파일로 저장하고, SHA-256 해시를 생성해 파일 무결성을 확인한다.

```python
for name, part in splits.items():
    path = output_dir / f"{name}.jsonl"

    payload = "".join(
        json.dumps(row, ensure_ascii=False) + "\n"
        for row in part
    )

    path.write_text(payload, encoding="utf-8")

    file_hashes[path.name] = hashlib.sha256(
        path.read_bytes()
    ).hexdigest()

# [일부 생략] 데이터 카드 생성, ZIP 압축 및 검증
```

JSONL은 한 줄에 JSON 레코드 하나씩 저장하는 형식이다.

SHA-256은 파일 내용을 기준으로 해시값을 계산하는 알고리즘으로, 이후 파일 내용이 변경되었는지 확인할 때 사용할 수 있다.

최종 결과물은 다음과 같다.

```
training_data.zip
 ├── train.jsonl       (48개)
 ├── dev.jsonl         (12개)
 ├── test.jsonl        (12개)
 └── dataset_info.json
```

`dataset_info.json`에는 데이터 구성 정보, 모델 정보, 분할 시드, 토큰 길이, 파일 해시 등이 저장된다.

파일을 저장한 뒤에는 ZIP을 다시 읽어 원본 데이터와 일치하는지도 확인한다.

이번 과정을 통해 학습 데이터도 코드처럼 버전과 실험 조건을 관리해야 한다는 점을 배웠다.

## 8. 공부하면서 정리한 용어

|용어|이해한 내용|
|---|---|
|Fine-tuning|사전학습된 모델을 특정 목적에 맞게 추가 학습시키는 과정|
|SFT|정답 데이터로 모델을 지도 학습하는 방식|
|LoRA|모델 전체 대신 작은 추가 파라미터를 학습하는 방식|
|QLoRA|양자화된 모델에 LoRA를 적용해 메모리 사용량을 줄이는 방식|
|DPO|선호하는 답변과 그렇지 않은 답변을 비교해 학습하는 방식|
|Token|모델이 텍스트를 처리하는 단위|
|Tokenizer|텍스트를 토큰 ID로 변환하는 도구|
|Chat Template|모델에 맞게 대화 역할과 구분 토큰을 적용하는 형식|
|Label|학습에서 모델이 예측해야 하는 정답|
|Masking|특정 토큰을 손실 계산에서 제외하는 처리|
|Loss|모델 예측과 정답의 차이를 나타내는 값|
|Metadata|데이터 관리와 분석에 필요한 부가 정보|
|Abstain|근거가 부족해 답변을 보류하는 것|
|Data Leakage|평가에 사용할 정보가 학습에 노출되는 문제|

|JSONL|JSON 레코드를 한 줄씩 저장하는 파일 형식|
|SHA-256|파일 무결성 확인에 사용하는 해시 알고리즘|

## 10. 오늘의 회고

오늘 공부하면서 가장 크게 이해한 부분은 학습 데이터를 만드는 과정과 실제 모델에 제공하는 데이터를 구분해야 한다는 점이었다.

`case_specs`에서 질문과 조건을 만들고, 이를 `rows`의 `messages` 형식으로 변환하는 과정이 처음에는 비슷해 보였는데, 코드를 따라가면서 각각의 역할이 다르다는 것을 알게 됐다.

토큰화 부분도 기억에 남는다. 단순히 문장을 토큰으로 변환하는 것뿐 아니라 입력과 정답의 경계를 정확히 찾는 과정이 필요했고, 이 부분이 다음 장의 `labels=-100` 마스킹으로 이어진다는 점을 이해했다.

그리고 `group_id`를 기준으로 데이터를 나누는 이유도 정리할 수 있었다. 이전에는 데이터를 무작위로 나누면 된다고 생각했지만, 관련된 사례가 학습과 평가에 동시에 포함되면 성능 평가가 왜곡될 수 있다는 것을 알게 됐다.

아직 실제 모델을 학습시킨 것은 아니기 때문에 이번 데이터가 성능에 어떤 영향을 줄지는 확인하지 못했다. 다음 장에서는 준비한 데이터를 이용해 SFT를 진행하면서 토큰 마스킹과 손실 계산이 실제 학습에 어떻게 연결되는지 확인해 보고 싶다.

### 오늘의 한 줄 정리

# 2026-11-14(KANT Project 3 마무리: Retriever 검색 방식 비교와 회고)

## 1. 오늘 공부한 것

PDF 기반 RAG Q&A(해운 PDF 50개, 3,750페이지)에서 **Retriever**를 맡았다. 질문과 관련된 PDF 근거 청크를 찾는 부분이다. Naive, Hybrid, Hybrid + Rerank 세 방식을 같은 조건에서 비교했다. 오늘은 그 결과와 시행착오, 협업 과정을 정리했다.

## 2. 핵심 개념 정리

| 방식 | 동작 | 장점 | 한계 |
| --- | --- | --- | --- |
| Naive (Dense) | E5 임베딩 + Qdrant 코사인 유사도 | 표현이 달라도 의미가 비슷하면 찾음 | 문서 번호·약어 같은 키워드에 약함 |
| Hybrid | Dense + BM25를 RRF로 결합 | 의미와 키워드를 함께 봄 | 정확한 페이지 선정은 약함 |
| Hybrid + Rerank | 후보 50개를 CrossEncoder가 재채점 | 최종 순서가 좋아짐 | 후보에 없는 근거는 못 살림, 느림 |

- **RRF**: 점수가 아니라 **순위**를 합친다. `1/(60 + Dense 순위) + 1/(60 + BM25 순위)`
- **Hit@k / Recall@k**: Hit은 근거를 하나라도 찾았는지, Recall은 필요한 근거 그룹을 얼마나 찾았는지 본다.

## 3. 결과 (page 기준, 56문항)

- Hybrid + Rerank가 가장 좋았다. k=5 Recall 0.676, k=10 Recall 0.765, k=20 Recall 0.808.
- k=10 기준 Recall은 Naive 0.689, Hybrid 0.700, Hybrid + Rerank 0.765였다.
- k=20의 Recall이 가장 높았지만 LLM에 넘기는 토큰과 비용을 고려해 **k=10**을 골랐다. 다만 k=10과 k=20의 답변 품질·비용은 직접 비교하지 못했다.
- 리랭킹은 GPU에서 질문당 약 1.28초가 걸렸다. 후보가 50개로 고정이라 k를 줄여도 시간은 거의 그대로였다.

## 4. 헷갈렸던 부분과 깨달은 점

- **page Recall이 document Recall보다 9~12% 낮았다.** 맞는 문서는 찾았는데 페이지를 틀리는 경우가 많았다. 병목은 문서를 찾는 단계보다 페이지를 고르는 단계였다.
- **BM25 한국어 토큰화(josa·Kiwi)는 채택하지 않았다.** BM25 단독 순위는 좋아졌지만, k=10 Hybrid + Rerank Recall은 regex 0.765, josa 0.768, Kiwi 0.764로 차이가 없었다.
- **RRF 상수 60은 이 데이터에서 검증하지 못했다.** 원논문 기준의 안정적인 기본값이라는 것만 확인했다.
- **리랭커는 새 청크를 찾지 못한다.** 후보 50개 안에 근거가 없으면 해결할 수 없다.

## 5. 팀워크·협업에서 배운 점

- **프로젝트 리더가 시작 전에 제약사항과 인터페이스를 정해 준 것이 큰 도움이 됐다.** 무엇을 만들고 어디까지 건드리는지 처음부터 분명해서 편하게 진행할 수 있었다.
- **코드를 모듈화하고 목업을 기준으로 미리 개발했다.** 다른 팀원의 모듈이 끝나기를 기다리지 않고 내 Retriever를 먼저 작성할 수 있어서 대기 시간이 많이 줄었다.
- **월권이 될 수 있는 부분을 구조로 막았다.** 각자 맡은 모듈의 경계가 분명해서 팀원 간 충돌이 생기지 않았다.
- 개발 전에 경계와 인터페이스를 먼저 설계하는 것이 협업의 속도와 안정성을 좌우한다는 것을 배웠다.

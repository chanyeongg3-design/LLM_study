# 1. 오늘은 무엇을 공부했을까?

오늘은 LLMOps 2장 강의를 통해 **LLM의 답변을 평가하고, 프롬프트를 수정했을 때 실제로 성능이 개선되었는지 확인하는 방법**을 공부했다.

이전에는 프롬프트를 수정한 뒤 AI가 더 좋은 답변을 생성하면 개선되었다고 생각했다.

하지만 오늘 강의를 공부하면서 단순히 답변이 좋아 보이는 것만으로는 성능이 개선이 되었다고 판단하기 어렵다는 것을 알게 되었다.

중요한 것은 **동일한 질문과 평가 기준을 사용해 변경 전후의 결과를 비교하는 것**이었다.

오늘 학습한 전체 과정은 다음과 같다. 
```mermaid
 A[📂 Golden Dataset 준비] --> B[🏷️ 프롬프트 버전 관리]
    B --> C[🤖 LLM 답변 생성]
    C --> D[🧪 Evaluator 자동 평가]
    D --> E[⚖️ Baseline vs Candidate 비교]
    E --> F[🔁 회귀 Regression 검사]
    F --> G[🔒 Holdout 추가 검증]
    G --> H[✅ 최종 검토]
```
   

# 2. 오늘 배운 핵심 개념

### **① Golden Dataset - 평가 기준 만들기**

Golden Dataset은 질문과 기대하는 답변 조건을 미리 정리한 평가용 데이터다.

예를 들어 식비 한도에 관한 질문이라면 다음과 같은 기대값을 설정할 수 있다.

```python
expected = {
	"terms": ["2만원", "영수증"],
	"citations": ["meal"],
	"abstain": False
}
```

- term: 답변에 반드시 포함되어야 하는 표현
- citations: 답변에 표시해야 하는 출처
- abstain: 근거가 없을 때 답변을 보류해야 하는지 여부

이번 강의에서는 평가 데이터를 **dev 4개, holdout 2개**로 구분했다.

dev는 프롬프트를 수정하면서 반복적으로 평가하는 데이터이고, holdout은 개선된 프롬프트를 별도로 검증할 때 사용하는 데이터다.

두 데이터를 나누는 이유는 AI가 특정 평가 질문에만 맞춰지는 문제를 줄이기 위해서다. 

### **② Prompt Versioning - 프롬프트 변경 관리**

두 번째로는 Langfuse를 이용해 프롬프트 버전을 관리하는 방법을 공부했다.

기존 프름포트를 Baseline, 개선하려는 프롬프트를 Candidate라고 부른다. 

```python
baseline = lf.create_prompt(
	name=name,
	type="text",
	prompt="주어진 근거를 참고하여 답하세요."
)

candidate = lf.create_prompt(
	name=name,
	type="text",
	prompt=POLICY
)

```

프롬프트를 같은 이름으로 등록하면 버전별로 관리할 수 있다.

여기서 중요한 점은 **프롬프트만 변경하고 모델, 질문, 검색 방식, 평가 기준은 동일하게 유지해야 한다**는 것이다. 

여러 조건을 동시에 변경하면 어떤 부분 때문에 성능이 개선되었는지 알기 어렵기 때문이다.

또한 latest보다 정확한 버전 번호를 사용하는 것이 실험 재현에 유리하다는 점도 배웠다. 

### **③ Task와 Evalutor - 답변 생성과 평가**

오늘 공부한 내용 중 가장 중요하다고 느낀 부분은 Task와 Evaluator의 차이였다. 

| 구분         | 역할                         |
| ---------- | -------------------------- |
| Task       | LLM에 질문을 전달하고 답변 생성        |
| Evaluator  | 생성된 답변을 정답 조건과 비교          |
| Experiment | Task와 Evaluator를 연결해 실험 실행 |
| Trace      | 모델 실행 과정과 결과를 추척           |

평가에는 네 가지 지표를 사용했다.

| 지표              | 평가내용               |
| --------------- | ------------------ |
| required_terms  | 필수 표현이 모두 포함되었는가?  |
| citation_match  | 출처가 정확한가?          |
| answer_behavior | 답변 또는 보류 행동이 올바른가? |
| rule_pass       | 세 조건을 모두 통과했는가?    |

다음 코드는 오늘 공부한 핵심 평가 로직이다. 

```python
# 필수 표현이 모두 있는지 검사
terms_ok = all(
	term in text for term in expected["terms"]
)

# 출처가 정확히 일치하는지 검사
citation_ok = citations == set(expected["citations"]
)

# 보류 행동이 기대값과 같은지 검사
behavior_ok = abstained == expected["abstain"]

# 모든 조건이 참이어야 최종 통과 
passed = terms_ok and citation_ok and behavior_ok
```

이 코드를 통해 `all( )` 함수와 and 연산자가 평가 로직에서 어떻게 활용되는지 이해할 수 있었다.

다만 문자열이 포함되어 있는지만 검사하는 방식은 문장의 실제 의미까지 판단하지 못한다는 한계가 있다.

### ④ Regression - 변경 후 성능 악화 감지

마지막으로 프롬프트를 변경한 후 성능이 오히려 악화되는 회귀(Regression) 개념을 공부했다.

예를 들어 다음과 같은 결과가 있다고 가정한다면


| 질문  | 변경 전 | 변경 후 |  변화 |
| :-: | ---: | ---: | --: |
| d01 |    0 |    1 |  +1 |
| d02 |    0 |    1 |  +1 |
| d03 |    1 |    1 |   0 |
| d04 |    1 |    0 |  -1 |

전체 평균은 개선되었지만 d04 질문에서는 성능이 악화되었다.

따라서 단순히 평균 점수만 확인하는 것이 아니라 **질문별 점수 변화까지 확인해야 한다**는 것을 배웠다.

이번 강의에서는 다음과 같은 조건으로 판정했다.

```python
# 변경 전후 점수 차이 계산
delta = {
	key: after[key]["score"]["rule_pass"] - before[key]["scores"]["rule_pass"]
	for key in before
}
# 후보가 모든 질문을 통과하고 약화된 질문이 없어야 함
accepted = passed == 4 and min(delta.values()) >= 0 
```

dev 평가를 통과한 경우에만 holdout 평가를 진행하며, holdout까지 통과하더라도 자동으로 배포하는 것이 아니라 REVIEW 상태로 추가 검토한다. 

# 3. 오늘 코드에서 새롭게 이해한 문법

| 코드                 | 의미                    |
| ------------------ | --------------------- |
| `set( )`           | 중복이 없는 집합 생성          |
| `all()`            | 모든 조건이 참인지 검사         |
| `any()`            | 하나라도 참인 조건이 있는지 검사    |
| `.get()`           | 딕셔너리에서 키에 해당하는 값 가져오기 |
| `**kwargs`         | 추가 키워드 인자 받기          |
| `len()`            | 데이터 개수 확인             |
| `hashlib.sha256()` | 데이터의 해시값 생성           |

특히 `lf, model = connect()` 코드가 기억에 남았다.

처음에는 두 변수가 어떻게 값을 받는지 헷갈렸지만, 하나의 함수가 반환한 두 값을 각각 다른 변수에 할당하는 문법이라는 것을 이해했다.

또한 리스트 컴프리헨션을 활용하면 반복문을 간결하게 작성할 수 있다는 점도 복습했다. 

# 4. 공부하면서 헷갈렸던 부분

오늘 가장 헷갈렸던 부분은 평가 점수 0점과 실행 오류의 차이였다

처음에는 AI가 답변을 잘못하거나 API 요청에 실패하더라도 모두 0점으로 처리하면 된다고 생각할 수 있었다.

하지만 두 상황은 완전히 달랐다. 

- 0점: 답변은 생성되었지만 평가 기준을 만족하지 못한 경우
- Error: 모델 실행이나 평가 과정 자체에 문제가 발생한 경우

실행 오류를 일반적인 0점으로 처리하면 어떤 부분에서 문제가 발생했는지 구분하기 어려워진다.

또한 모델 실행 실패로 결과 행 자체가 누락될 수도 있기 때문에 평가 데이터의 ID와 실제 결과 ID를 비교하는 과정도 필요하다는 것을 배웠다.

# 5. 오늘 공부한 내용은 실무에서 어떻게 사용할까?

오늘 배운 LLMOps 평가 방식은 RAG 챗봇이나 금융 상담 챗봇을 개선할 때 활용할 수 있을 것 같다.

예를 들어 금융 상담 챗봇의 프롬프트를 변경했을 때, 기존에 정확하게 답변하던 대출 관련 질문이 잘못 처리되는 문제가 발생할 수 있다. 

이때 Golden Dataset으로 평가 질문을 관리하고, Langfuse로 모델 응답과 점수를 기록하면 어떤 질문에서 문제가 발생했는지 확인할 수있다.

특히 프롬프트 개선뿐 아니라 RAG의 검색 방식이나 답변 생성 과정을 변경했을 때도 동일한 평가 원리를 적용할 수 있다는 점이 인상 깊었다. 

# 6. 오늘의 느낀점 

오늘 강의를 공부하면서 LLM을 개발하는 것과 안정적으로 운영하는 것은 다른 문제라는 생각이 들었다.

AI가 답변을 생성하도록 만드는 것도 중요하지만, 그 답변이 올바른지 평가하고 변경 이후에도 기존 성능을 유지하는지 검증하는 과정이 필요했다.

특히 개발자가 단순히 모델의 답변을 보고 판단하는 것이 아니라, 평가 기준을 코드로 작성하고 자동으로 검사할 수 있다는 점이 흥미로웠다.

아직 평가 로직과 딕셔너리 컴프리헨션 같은 Python 문법이 익숙하지는 않지만, 각 함수가 어떤 역할을 수행하는지 연결해서 공부하니 전체 흐름이 조금씩 이해되기 시작했다.

앞으로는 코드를 단순히 실행하는 것에서 끝내지 않고, **왜 이 함수를 사용하고 어떤 데이터를 입력받아 무엇을 반환하는지**를 생각하면서 공부해야겠다.

### 7-1. Langfuse와의 관계

LLMOps는 **AI 서비스를 운영하고 개선하는 전체적인 방법론이고, Langfuse는 그 과정을 실제로 관리하고 관찰할 수 있게 도와주는 도구**

Langfuse를 사용한다고 LLMOps의 모든 과정이 자동으로 완성되는 것은 아니며, Langfuse는 LLMOps 중에서도 **실행 추적, 평가, 프롬프트 관리, 실험 결과 분석**을 돕는 역할을 한다.

| 구분       | LLMOps             | Langfuse             |
| -------- | ------------------ | -------------------- |
| 정제       | 운영 방법론 및 기술 체계     | LLM개발·운영 지원 플랫폼      |
| 목적       | AI 서비스의 품질과 안정성 관리 | LLM 동작 및 평가 결과 추척·분석 |
| 범위       | 개발,평가,배포,모니터링,개선   | 관측,평가,실험,프롬프트 관리 등   |
| 직접 답변 생성 | 모델을 연결해 사용         | 강의에서는 Python이 모델 호출  |
| 관계       | 전체적인 운영과정          | 그 과정에서 사용하는 도구       |

**핵심 차이**: LLMOps는 무엇을 관리하고 어떻게 개선할 것인가에 대한 개념이고, Langfuse는 그 과정에서 발생한 데이터를 어떻게 기록하고 분석할 것인가를 도와준다. 

### **LLM 애플리케이션과 Langfuse가 연결되어 동작하는 전체 흐름도**

Langfuse의 핵심 기능 5가지

1. Dataset Management - 평가 데이터 관리
- AI에게 어떤 질문을 할지, 어떤 결과가 나와야 하는지 저장하는 기능이다.
- 이번 강의에서는 golden.json의 질문 6개를 dev 4개, holdout 2개로 나눠 등록했다. 
2. Prompt Management - 프롬프트 버전 관리
- 기존 프름프트와 개선 후보를 버전별로 저장한다.
- 예를 들어 Version 1은 간단한 답변 지시, Version 2는 근거와 출처 및 보류 규칙을 추가한 지시문이다. 
- 
3. Tracing - 실행 과정 추적
- AI에게 어떤 입력이 들어갔고, 어떤 모델과 작업을 거쳐 어떤 답변이 생성됐는지 확인한다.
- 문제가 발생하면 Trace를 보고 어떤 단계에서 잘못됐는지 분석할 수있다.
4. Evaluation - 답변 품질 평가
- AI가 생성한 답변을 기대값과 비교한다.
- required_terms, citation_match, answer_behavior, rule_pass라는 네 가지 점수를 기록했다.
5. Experiment - 실험 결과 비교
- Baseline과 Candidate가 같은 평가 데이터에서 어떤 결과를 생성했는지 비교한다.
- 어느 질문이 개선됐고 어느 질문이 악화됐는지 확인하는데 활용한다.

**LLMOps란 LLM 기반 서비스를 안정적으로 운영하기 위해 모델과 프롬프트의 성능을 평가하고, 변경 사항을 관리하며, 지속적으로 모니터링하고 개선하는 과정이다.**

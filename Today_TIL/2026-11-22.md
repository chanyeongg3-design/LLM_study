# LLMOps (LLM Operations · 대규모 언어 모델 운영)

- **정의**: LLMOps는 LLM 기반 서비스를 **관측**하고 **평가**하며, 변경 결과를 **비교**해 **적용 여부를 판단**하고, 문제를 찾아 지속적으로 **개선**하는 운영 과정

## 핵심 순환 구조

1. 측정: Measure · 기록과 지표
2. 분석: Analyze · 실패 위치 찾기
3. 비교: Compare · 같은 조건 전후 비교
4. 판단: Decide · 유지 · 보류 · 복원
5. 재검증: Re-verify · 다시 평가

**측정 → 분석 → 비교 → 판단 → 재검증**이 LLMOps 전체를 요약한다.

### 네 가지 축

1. 관측 Observability(업저베빌리티): 요청 한 건이 어디서 어떻게 처리됐는지 기록으로 확인한다.(Trace·Observation·Logs, Metrics)
2. 평가 Evaluation: 답변이 기대한 행동을 했는지 기준으로 측정한다.(Golden Dataset, Evaluator, Feedback)
3. 변경 비교 Comparison: 두 버전을 같은 질문·모델·평가 기준으로 실행해 변경 효과만 분리한다.
4. 배포 판단 Release Decision: 평균 개선과 중요 사례 실패를 함께 보고 적용 · 보류 · 롤백을 결정한다.

### WHY?

| 목적 | 설명 |
| --- | --- |
| 품질 관리 Quality | AI 답변의 정확성과 신뢰성을 평가 |
| 버전 관리 Versioning | 프롬프트와 모델의 변경 이력 관리 |
| 성능 비교 Comparision | 변경 전후의 답변 품질 비교 |
| 오류 분석 Error Analysis | 잘못된 답변과 실행 오류의 원인 파악 |
| 지속적 개선 Continuous Improvement | 평가 결과를 바탕으로 서비스 개선 |

```text
프롬프트를 바꾸고 "답변이 더 좋아 보인다"로 판단하면 안된다. 
"같은 질문과 같은 평가 기준으로 전후를 비교"해야 개선인지 알 수가 있다.
```

### LLMOps와 Langfuse의 관계

| 구분 | LLMOps | Langfuse |
| --- | --- | --- |
| 성격 | 운영 방법론·기술 체계 | LLM 개발·운영 지원 플랫폼 |
| 목적 | AI 서비스의 품질과 안정성 관리 | LLM 동작과 평가 결과의 추적·분석 |
| 범위 | 개발 · 평가 · 배포 · 모니터링 · 개선 | 관측 · 평가 · 실험 · 프롬프트 관리 |

LLMOps는 "무엇을 관리하고 어떻게 개선할지"에 대한 개념이고, Langfuse는 "그 과정의 데이터를 어떻게 기록하고 분석할지"를 도와주는 도구

Langfuse를 쓴다고 LLMOps가 자동으로 완성되지는 않는다.

## Langfuse의 핵심 기능 5가지

| 기능 | 역할 |
| --- | --- |
| Dataset Management | 평가 질문과 기대 결과 저장(golden 6문항 → dev 4 + holdout 2) |
| Prompt Management | 프롬프트를 버전별로 저장(Version 1 간단 지시 / Version 2 근거·출처· 보류 규칙 ) |
| Tracing | 입력 · 모델 · 작업 단계 · 출력 추적 |
| Evaluation | 답변을 기대값과 비교해 점수 기록 |
| Experiment | Baseline과 Candidate의 결과를 같은 데이터에서 비교 |

### Golden Dataset에서 Dev와 Holdout을 나누는 이유

- 핵심은 **모델을 개선할 때 사용하는 데이터(DEV)와 개선한 모델의 최종 성능을 확인하는 데이터(Holdout)** 을 분리 하기 위해서다.
- **왜 굳이 분리해야 할까?**: 전체를 반복 평가하면서 모델을 수정하면, 모델이 특정 문항에만 잘 맞도록 최적화될 수 있어서, 이를 **과적합(Overfitting)** 이라고 한다.

| 구분 | DEV(Development) | HOLDOUT |
| --- | --- | --- |
| 의미 | 개발·검증용 데이터 | 최종 평가용 데이터 |
| 목적 | 문제점을 찾아 개선 | 개선 결과를 객관적으로 평가 |
| 사용 시점 | 개발 중 반복 사용 | 설정 확정 후 사용 |
| 결과에 따른 수정 | 가능 | 원칙적으로 수정하지 않음 |
| 예시 | 검색 방식·프롬프트 변경 | 최종 성능 확인 |

**최종 핵심 정리**

- Golden Dataset : 정답 또는 기대 근거가 준비된 평가 데이터
- DEV : 모델·검색기·프롬프트를 반복적으로 평가하고 개선하는 데이터
- HOLDOUT : 개선 과정에서 사용하지 않고 최종 성능을 확인하는 데이터

### 답변이 틀렸을 때: 처음 문제가 생긴 위치부터 본다

| 확인 단계 | 발견되는 문제 | 수정 대상 |
| --- | --- | --- |
| 검색 | 관련 문서를 찾지 못함 | 검색 로직 |
| 입력 조립 | 문서는 찾았지만 필요한 내용이 Context에서 빠짐 | Context 구성 |
| 답변 생성 | 근거는 전달됐는데 답변에서 누락 | 프롬프트 · 출력 검사 |

```text
답변이 틀렸다고 곧바로 LLM이나 프롬프트부터 고치지 않는다. "Trace에서 처음 어긋난 단계"를 찾는 것이 먼저다. 
```

### 실패 분류 Failure Classification

| 상태 | 의미 |
| --- | --- |
| completed | 실행 기록의 정상 조건 충족 |
| incomplete | 실행 상태를 확인할 정보 부족 |
| invalid_time | 시작 · 종료 시간 정보 오류 |
| model_error | 모델 실행 실패 |
| retrieval_empty | 검색된 문서가 없음 |

```text
검색 결과가 비어 있어도 규정에 없는 질문이라면 "답변 보류가 올바른 행동일 수 있다."
"검색 결과 없음 = 잘못된 답변"이 아니다. 
```

### 기록은 남았는가: `flush()`와 서버 조회는 다르다.

**터미널에 답변 출력** → **`flush()`로 전송 처리** → **서버에 Trcae ID로 재조회**

- `flush(), 즉시반영`가 끝났다는 사실과 서버에서 조회된다는 사실은 다르다.
- `GENERATION`에 종료 시각이 있다고 답변이 정확하다는 뜻은 아니다.
- 이 과제의 `verify(검증)`는 기존 기록만 조회하고 모델을 다시 호출하지 않는다.

---

`flush()`는 임시 저장 공간(버퍼)에 쌓인 데이터를 즉시 내보내는 함수이다.

- 파일이나 로그에 저장되지 않고 대기 중인 데이터를 바로 기록할 때 사용한다.
- 한 단어로 표현한다면: 즉시 반영 이라 표현할 수 있다.
  그 이유는: **버퍼에 임시로 쌓여 있는 데이터를 기다리지 않고 바로 내보내기 때문이다.**

`Generation(제너레이션)`은 LLM이 입력된 질문이나 프롬프트를 바탕으로 새로운 내용을 생성하는 과정이다.

- 학습한 지식과 입력된 문맥을 활용하여 다음 토큰을 예측한다.
- 예측한 토큰을 순차적으로 연결해 답변, 코드, 요약 등의 결과물을 만든다.
- 한 단어로 표현: **생성**

`Verify(베리파이)`: 데이터나 결과가 올바른지 확인하는 과정이다

- 정해진 조건이나 기준에 따라 오류 또는 이상이 있는지 검사한다.
- LLMOps에서는 모델의 응답이 요구사항을 충족하는지 검증할 때 사용한다.
- 한 단어로 표현: **검증**
  이유: 단순히 결과가 존재하는지 확인하는 것이 아니라, **정해진 기준을 충족하고 올바르게 처리되었는지 판단하는 과정**이기 때문이다.

#### 개념 비교

| 구분 | 한 단어 | 역할 |
| --- | --- | --- |
| Verify | 검증 | 결과가 올바르게 처리되었는지 확인 |
| Validation | 유효성 검사 | 데이터가 정해진 조건에 맞는지 검사 |
| Pydantic | 검증 도구 | 데이터의 타입과 구조 등을 자동 검사 |

### 과제 코드에서의 관측

요청 한 건이 Trace 하나이고, 그 아래 `retrieve` → `ticket-status` → `generate` → `validate` 단계 기록이 들어간다.

- **필요한 정보를 찾고 → 문의 상태를 확인하고 → 답변을 생성하고 → 답변이 규칙에 맞는지 검사하는 과정**이다.

덕분에 실패를 세 갈래로 구분할 수 있다.

#### 각 단계의 개념

| 단계 | 개념 설명 | 한 단어 |
| --- | --- | --- |
| Retrieve | 질문에 필요한 정보를 문서나 DB에서 검색한다.<br>LLM이 답변할 때 사용할 근거를 확보한다. | 검색 |
| Ticket-status | 고객 문의(Ticket)의 현재 처리 상태를 조회한다.<br>접수·진행 중·완료 등의 상태를 확인한다. | 상태 조회 |
| Generate | 검색한 정보와 조회한 상태를 바탕으로 답변을 만든다.<br>LLM이 자연스러운 문장으로 결과를 생성한다 | 생성 |
| Validate | 생성된 답변이 정해진 형식과 규칙에 맞는지 검사한다.<br>잘못된 데이터나 규칙 위반을 확인한다 | 유효성 검사 |

- **생성 단계 실패**: 모델 호출 자체가 실패(error_stage, error_type 기록)
- **검증 단계 실패**: 응답은 나왔지만 JSON 스키마 · 출처 규칙 기반
- **평가 단계 실패**: 응답은 정상인데 사례의 기대 조건을 충족하지 못함

`generation_fields()`는 모델 출력의 연락처를 마스킹하고, 입력 · 출력 토큰 수를 `usage_details`로 묶어 기록한다.
토큰 사용량을 알 수 없으면 0이 아니라 None으로 남긴다.

#### 핵심 차이

| 구분 | `generation_fields` | `usage_details` |
| --- | --- | --- |
| 한 단어 | 생성정보 | 사용량 |
| 핵심 역할 | 생성 과정 정보 기록 | 토큰 사용량 기록 |
| 예시 | 모델명, 입력, 출력 | 입력 100, 출력 50 |
| 목적 | 실행 추적 | 사용량 및 비용 분석 |

**핵심**: `generation_fields`는 생성 정보를 모으는 변수명으로 사용될 수 있으며, `usage_details`는 Langfuse에서 토큰 사용량을 기록하는 필드
`generation_fields`에 정확히 어떤 정보가 들어가는지는 실제 코드에 따라 달라진다.

| 지표 | 평가 내용 |

## 검색 성능 평가 지표 (Retrieval)

목적: 검색기가 질문에 필요한 문서를 얼마나 정확하게 찾아오는지 평가한다.

| 평가지표 | 기능 | 언제 사용? |
| --- | --- | --- |
| Hit@k | 상위 k개 안에 정답 근거가 하나라도 있는지 확인 | 정답 문서 검색 성공 여부 |
| Recall@k | 전체 정답 근거 중 상위 k개에서 찾은 비율 | 검색 누락 정도 평가 |
| Precision@k | 상위 k개 결과 중 관련 문서의 비율 | 불필요한 검색 결과 확인 |
| MRR | 첫 번째 정답 문서가 얼마나 앞에 있는지 평가 | 첫 검색 결과의 순위가 중요할 때 |
| NDCG@k | 문서의 관련성과 검색 순위를 함께 평가 | 검색 결과의 정렬 품질 비교 |
| Context Precision | 관련성 높은 청크가 상위에 배치되었는지 평가 | RAG 검색 결과 순위 개선 |
| Context Recall | 정답에 필요한 정보가 검색 문맥에 충분히 포함되었는지 평가 | 근거 정보의 누락 확인 |

## 답변 품질 평가 지표 (Generation)

목적: LLM이 검색한 근거를 활용해 올바른 답변을 생성했는지 평가한다.

| 평가지표 | 기능 | 언제 사용? |
| --- | --- | --- |
| Faithfulness | 답변의 주장이 검색 근거와 일치하는지 평가 | 환각(Hallucination) 검사 |
| LLM-as-a-Judge | LLM이 정해진 기준으로 답변을 채점 | 여러 품질 기준을 종합 평가 |
| Answer Relevancy | 생성된 답변이 질문과 관련 있는지 평가 | 질문과 무관한 답변 탐지 |
| Answer Correctness | 생성 답변과 정답의 사실적·의미적 일치 평가 | 정답이 있는 Q&A 평가 |
| Factual Correctness | 생성 답변의 사실이 기준 정답과 일치하는지 평가 | 사실 오류 탐지 |
| Semantic Similarity | 두 답변의 의미가 얼마나 비슷한지 평가 | 표현이 달라도 의미가 같은지 확인 |
| Noise Sensitivity | 불필요한 검색 정보가 답변에 미치는 영향 평가 | 검색 문서에 잡음이 많을 때 |

## 시스템 성능 평가 지표 (Performance)

목적: RAG 서비스가 얼마나 빠르고 효율적으로 작동하는지 평가한다.

| 평가 지표 | 기능 | 언제 사용? |
| --- | --- | --- |
| Latency | 요청부터 결과 반환까지 걸린 시간 | 응답 속도 최적화 |
| Throughput | 일정 시간 동안 처리한 요청 수 | 동시 사용자 처리 능력 평가 |
| Token Usage | 입력·출력 토큰 사용량 측정 | LLM 사용량 분석 |
| Cost per Request | 요청 1건당 발생하는 비용 | API 비용 최적화 |
| P95 Latency | 요청 중 95%가 완료되는 시간의 상한 | 느린 요청까지 포함한 서비스 품질 평가 |

- Hybrid + Reranker가 검색 정확도가 높이더라도 응답 시간이 크게 늘어났다면, Recall@k와 Latency를 함께 비교해야 한다.

## 안정성 및 신뢰성 평가 지표 (Reliability)

목적: 시스템이 오류 없이 작동하고, 신뢰할 수 있는 답변을 제공하는지 평가한다.

| 평가 지표 | 기능 | 언제 사용? |
| --- | --- | --- |
| Error Rate | 전체 요청 중 오류가 발생한 비율 | 서비스 안정성 확인 |
| Citation Accuracy | 답변의 출처가 실제 주장을 뒷받침하는지 평가 | 출처가 중요한 RAG 서비스 |
| Abstention Accuracy | 답변할 근거가 없을 때 적절히 답변을 보류하는지 평가 | 근거 없는 답변 방지 |
| Tool Call Accuracy | 적절한 도구를 올바르게 호출했는지 평가 | Agent 및 도구 호출 시스템 |

Citation와 Avstention Accuracy는 평가 규칙을 직접 정의해 구현할 수 있다.
RAGAS 역시 별도의 도구 호출 평가 지표를 제공한다.

**핵심 정리**: RAG 평가에서는 검색 정확도만 높다고 좋은 시스템이 되는 것은 아니다.
**검색 품질 + 답변 품질 + 처리 성능 + 안정성**을 함께 평가해야 실제 서비스의 품질을 판단할 수 있다.

## 변경 비교 Comparison

두 버전을 같은 조건에서 실행해 "무엇을 바꿨는지"를 분명하게 한다.

### Baseline vs Candidate

Baseline · 기존: 현재 사용 중인 프롬프트(예:"주어진 근거를 참고하여 답하세요.")

Candidate · 후보: 개선 하려는 프롬프트( `candidate_policy()의 네 규칙`)

**고정할 것**: 질문 · 참고 문서 · 모델 · 출력 한도 · 평가 기준
**바꿀 것**: 프롬프트 하나. 여러 조건을 동시에 바꾸면 무엇 때문에 달라졌는지 알 수 없다.

### 지표 용어

| 용어 | 의미 |
| --- | --- |
| SLI·Service Level Indicator | 실제로 측정하는 서비스 성능 지표 |
| SLO·Service Level Objective | 서비스가 달성해야 하는 목표 |
| Latency · 지연 | 요청 처리에 걸린 시간 |
| p50 | 응답 시간의 중앙값 |
| p95 | 느린 요청까지 보는 95백분위 지연 |
| Token Usage · 토큰 사용량 | 모델이 쓴 입력 · 출력 토큰 |
| Cost Coverage · 비용 파악률 | 전체 요청 중 비용이 확인된 요청의 비율 |

#### `summarize()`의 집계 규칙

| 지표 | 계산 | 주의 |
| --- | --- | --- |
| error_rate·오류율 | 오류 요청 수 ÷ 전체 요청 | 요청 **한 건이 한행**. 재시도 횟수는 분모가 아님. 요청 0건이면 `None` |
| p95_latency_ms | 정렬한 지연의 `ceil(n x 0.95)`번째 값 | 요청 4건이면 가장 느린 요청의 시간 |
| total_tokens·cost_usd | 모두 확인되면 합계 | 하나라도 `None`이면 합계도 `None`(0으로 바꾸지 않음) |
| positive_feedback_rate | True 수 ÷ 응답한 수 | `None`은 분모 제외, `False`는 포함. 응답이 없으면 `None` |

##### ! 지연만 보지 말고 완료율 · 오류율을 함께 본다.

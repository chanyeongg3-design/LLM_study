## 2. RNN과 LSTM만으로는 부족했던 이유
### 2-1. RNN의 정보 전달 방식 
- RNN은 이전 hidden state와 현재 입력으로 새로운 hidden state를 만든다. 
- `x₁ → h₁ → h₂ → h₃ → ⋯ → hₗ`  
현재 위치의 계산이 이전 위치에 의존하므로 같은 시퀸스의 시간측은 순서대로 처리해야 한다.
배치 안의 여러 샘플이나 한 시점의 행렬 연산은 병렬화할 수 있지만, 시퀸스 내부의 시간축 의존성은 병렬화하기 어렵다. 
```Python
import torch

rnn = torch.nn.RNN(
		input_size=4,
		hidden_size=6,
		batch_first=True,
)

x = torch.randn(2, 5, 4)  # [B=2, L=5, D_in=4]
output, h_n = rnn(x)

print(output.shape) # [2, 5, 6]
print(h_n.shape)    # [1, 2, 6]
```

- 다층 또는 양방향 RNN에서는 `output[ : , -1 ]`과 `h_n[-1]` 이 항상 같은 의미라고 단정할 수 없다.
용어:
`batch_first=True` 는 입력/출력 Tensor를 `[Batch, Sequence, Feature]` 순서로 사용하기 위한 설정이며,
`[B, T, C]` 형태로 통일해서 코드를 더 직관적으로 작성하기 위해 사용한다.
왜 `batch_first=True` 를 많이 쓰나? 
- 가장 큰 이유는 다른 딥러닝 코드와 Tensor 구조를 맞추기 편하기 때문이다. 
### 2-2. 긴 문맥에서 발생하는 세 가지 문제 
장기 의존성
초반의 정보가 마지막 예측에 영향을 주려면 많은 recurrent step을 통과해야 한다. 
길이가 `L` 이라면 첫 위치에서 마지막 위치까지의 경로는 약 `L-1`  이다. 
Vanishing·Exploding Gradient
시간축 역전파 과정에서는 여러 Jacobian이 반복해서 곱해진다. 
- 작은 값이 반복해서 곱해지면 gradient가 사라진다.
- 큰 값이 반복해서 곱해지면 gradient가 폭주한다
- Gradient clipping은 폭주를 제한하지만 장거리 관계를 자동으로 학습시키지는 않는다.
정보 병목
초기 RNN Encoder-Decoder는 전체 입력을 마지막 hidden state 하나에 압축했다.
문장이 길어질수록 필요한 세부 정보가 제한된 상태 안에서 희석될 수 있다. 
### 2-3. LSTM이 해결한 것과 남긴 것 
LSTM은 gate와 cell state를 사용해 중요한 정보를 더 오래 유지한다. 

LSTM은 vanilla RNN보다 gradient 흐름과 장기 기억을 개선한다
하지만 다음 한계는 남아 있다.
- 현재 시점은 이전 시점의 계산을 기다려야 한다.
- 문맥을 제한된 크기의 상태로 계속 축약해야 한다.
- 시퀸스가 길어지면 정보 전달 경로도 길어진다.
따라서 LSTM은 문제를 완화했지만 완전히 없애지는 않았다. 
### 2-4. Transformer가 필요한 이유
Self-Attention은 한 token이 다른 위치의 token을 직접 참고하게 한다. 
```Plain Text
RNN:             1 → 2 → 3 → ⋯ → L
Self-Attention:  1 ─────────────→ L
```

Attention score 행렬의 shape는 `[L, L]` 이므로 원소 수는 `L²` 이다. 
```Python
for length in (4, 16, 128):
		rnn_path = length - 1
		attention_scores = length**2
		
		print(
				f"L={length}:"
				f"RNN path={rnn_path}, "
				f"Attention scores={attention_scores}"
		)
```
길이가 128이라면:
- RNN 의존 경로: `127`
- Attention score 원소 수: `16,384`
Transformer는 정보 경로를 짧게 만들지만 그 대가로 `L²` 의 메모리와 연산 비용을 부담한다
또한 학습에서는 여러 위치를 병렬로 계산할 수 있지만, 생성에서는 새 token이 이전에 생성된 token에 의존하므로 token별 순차 생성이 필요하다. 
## 3. 미니 LLM 워크플로우
### 3-1. 분류와 생성의 공통 입력 

```Plain Text
Raw text
→ tokenizer

→ model
→ logits

```
주요 입력과 출력은 다음과 같다.

`B`는 batch_size, `L`은 squence length `C`는 class 수, `V`는 vocabulary 크기다. 
### 3-2. Task에 따라 출력 계약이 달라진다. 

```Python
import torch

logits = torch.tensor([
		[-1.2, 2.7, 0.4],
    [1.8, 0.2, -0.5],
]) #[B=2, C=3]


# softmax로 logits를 클래스별 확률로 바꾸고
# argmax가 그 중 가장 높은 점수를 가진 클래스 ID를 선택한다. 
probabilities = torch.softmax(logits, dim=-1)
predictions = logits.argmax(dim=1)

print(probabilities.shape)   # [2, 3]
print(predictions.tolist())  # [1, 0]
print(probabilities.sum(dim=-1))  # 각 행의 합은 1
```
Softmax를 batch 축에 적용하면 서로 다른 샘플이 경쟁하게 되므로 잘못된 계산이다. 
### 3-3. Train·Validation·Test·Inforence

Test 결과를 보며 epoch나 hyperparameter를 다시 선택하면 test가 validation처럼 사용되어 
최종 성능이 낙관적으로 평가될 수 있다.
### 3-4. Forwadr와 `generate()` 의 차이

## 4. NLP 데이터와 Subword
### 4-1. Tokenizer보다 먼저 데이터를 점검한다.
Tokenizer를 실행하기 전에 다음 항목을 확인해야 한다.
- 필수 column 존재 여부
- 빈 ID, 텍스트, label
- 중복 ID
- 정규화 후 중복 테스트 
- 예상하지 못한 label
- Class 분포
- Split 사이의 동일 샘플 중복
- 개인정보, 라이선스, 민감 정보        
```Python
samples = [
    {
        "id": "n001",
        "text": "금리 인상 가능성에 시장 긴장",
        "label": "economy",
    },
    {
        "id": "n002",
        "text": "대표팀, 연장전 끝에 결승 진출",
        "label": "sports",
    },
]

required = {"id", "text", "label"}

for row in samples:
    assert required <= row.keys()
    assert row["id"]
    assert row["text"].strip()
    assert row["label"]
```
원문과 label이 잘못되면 이후 token ID와 metric도 믿을 수 없다.     
### 4-2. Token-Vocabulary-ID의 관계
- Token : Tokenizer가 모델 입력 단위로 사용하는 문자열 조각
- Vocabulary : Token 문자열과 정수 ID의 대응표
- Token ID : 특정 vocabulary에서 token을 가리키는 정수
- UNK/OOV : Vocabulary로 표현하지 못한 입력이나 단위                              
```Plain Text
문자열
→ 정규화
→ Pre-tokenization
→ subword 분할
→ token 문자열
→ vocabulary 조회
→ token ID
```
- ID 숫자 자체에는 공통된 의미가 없다.
- 동일한 IDfkeh tokenizer가 다르면 전혀 다른 token을 나타낼 수 있으므로 model과 tokenizer의 checkpoint를 맞춰야한다. 
### 4-3. Word-Character-Subword 비교

Subword는 희귀 단어를 이미 알고 있는 작은 조각으로 나눈다. 
```Plain Text
인공지능연구소
→ 인공 + ##지능 + 연구 + ##소
```
다만 `##` 와 같은 표기는 Wordpiece의 예시다. BPE와 SentencePiece 등은 다른 표시 방법을 사용할 수있다.
### 4-4. Vocabulary 크기와 길이의 관계
Vocabulary가 크면 긴 문자열을 token 하나로 표현할 가능성이 커져 sequence가 짧아질 수 있다.
하지만 다음 비용이 증가한다
- Embedding parameter
- LM head parameter
- 모델 메모리
Vocabulary가 작으면 희귀 단어를 작은 단위로 나눌 수 있지만 sequence가 길어질 수 있다.
따라서 tokenizer는 vocabulary 크기 하나만 보지 않고 다음을 함께 비교한다.
- 전체 token 길이 분포
- [UNK] 비율
- 도메인 용어 처리
- 모델 checkpoint 호환성
- 메모리와 처리 속도
### 4-5. Token ID와 Label ID는 다르다
두 값 모두 정수이지만 서로 다른 namespace에 속한다.
```Python
label2id = {
    "economy": 0,
    "sports": 1,
    "tech": 2,
}

id2label = {
    value: key
    for key, value in label2id.items()
}

assert len(label2id) == len(set(label2id.values()))
assert all(
    id2label[label2id[name]] == name
    for name in label2id
)
```
- 예측 label ID `0` : 프로젝트에서 정의한 economy
- Token ID `0` : tokenizer vocabulary에서 정의한 token
Label 매핑과 tokenizer vocabulary는 별도로 저장해야 한다.

### 5-4. Special token과 Decode
Special token은 직접 문자열에 붙이지 않고 tokenizer가 추가하게 한다. 
```Python
text = "한국어 모델은 문장을 토큰으로 나눕니다."

ids = tokenizer.encode(
    text,
    add_special_tokens=True,
)

decoded = tokenizer.decode(
    ids,
    skip_special_tokens=True,
)

print(ids)
print(decoded)
```
Decode는 의미 있는 문자열을 복원하지만 원문의 공백과 정규화를 바이트 단위로 완전히 되돌린다는 보장은 없다. 따라서 원문과의 문자열 완전 일치하는 다음을 확인해야 한다. 
- 올바른 checkpoint 사용
- Special token 포함 여부
- Token과 ID의 대응
- 입력 field와 shape
## 6. Padding-Truncation-Attention Mask
### 6-1. 세 개념의 차이
padding : 짧은 입력에 PAD token을 추가해 한 batch를 직사각형 Tensor로 만든다.
Truncation :  설정된 최대 길이를 넘은 token을 잘라낸다. 
Attention mask: 실제 token과 PAD token을 구분한다. 
```Plain Text
원래 길이:      [7, 4, 5]
max_length=6:   [6, 4, 5]
동적 padding:   [6, 6, 6]
```
Padding은 정보를 자르지 않지만 불필요한 계산을 늘린다.
Truncation은 계산량을 제한하지만 중요한 문맥을 제거할 수 있다. 
### 6-2. 정적 Padding과 동적 Padding’

권장 흐름은 다음과 같다.
```Plain Text
Dataset map
→ padding=False로 가변 길이 유지

DataLodaer 직전 collator
→ 현재 batch에서 가장 긴 샘플까지만 padding
```
### 6-3. Split을 먼저 고정해야 한다.
안전한 전처리 순서는 다음과 같다.
1. 원본 데이터의 schema와 중복을 검사한다.
1. Train·validation·test split을 먼저 고정한다. 
1. 모든 split에 같은 tokenizer 설정을 적용한다.
1. Validation으로 `max_length` 와 학습 설정을 선택한다.
1. Test는 모든 선택을 마친 후 최종 평가한다. 
전체 데이터를 tokenization한 뒤 임의로 분리하거나 중복 샘플을 허용하면 데이터 누수를 발생할 수 있다. 
### 6-4. Dataset에서는 가변 길이를 보존한다. 
```Python
def tokenize_batch(batch):
    encoded = tokenizer(
        batch["text"],
        truncation=True,
        max_length=16,
        padding=False,
    )

    encoded["labels"] = batch["label"]
    return encoded

tokenized = splits.map(
    tokenize_batch,
    batched=True,
)
```
`batched=True` 일때 `batch[”text”]`는 문자열 하나가 아니라 문자열 list이다.
반환되는 각 field의 list 길이는 입력 batch의 행 수와 같아야 한다.
### 6-5. Collator에서 동적 Padding한다.
```Python
import torch
from transformers import DataCollatorWithPadding

collator = DataCollatorWithPadding(
    tokenizer=tokenizer,
    return_tensors="pt",
)

model_input_keys = [
    "input_ids",
    "attention_mask",
    "labels",
]

if "token_type_ids" in tokenized["train"].column_names:
    model_input_keys.append("token_type_ids")

features = [
    {
        key: tokenized["train"][i][key]
        for key in model_input_keys
    }
    for i in range(4)
]

batch = collator(features)

print(batch["input_ids"].shape)       # [B, L]
print(batch["attention_mask"].shape)  # [B, L]
print(batch["labels"].shape)          # [B]
```
여기서 `L`은 전체 데이터의 최대 길이가 아니라 **현재 batch에서 Padding 후 만들어진 길**이다. 
### 6-6. PAD와 Attention Mask 검증
PAD token 위치와 `attention_mask=0` 위치는 정확히 일치해야 한다. 
```Python
pad_positions = batch["input_ids"].eq(
    tokenizer.pad_token_id
)

masked_positions = batch["attention_mask"].eq(0)

assert torch.equal(
    pad_positions,
    masked_positions,
)
```
이 검사가 실패하면 다음 문제가 생길 수 있다.
- 모델이 PAD를 실제 문맥으로 읽는다.
- 실제 token이 Attention에서 가려진다.
- 같은 데이터에서도 잘못된 표현이 만들어진다.
### 6-7. max_length 선택 기준
`max_length` 는 감으로 정하지 않고 train 데이터의 token 길이 분포를 확인해 선택한다.
살펴볼 값:
- Median
- p95
- Maximum
- 후보 길이별 truncation 비율
- GPU 메모리
- Validation 성능
정책 선택에는 train 통계와 validation 성능을 사용한다.
Test의 truncation 비율은 이미 결정된 정책의 적용 결과로만 기록하며, 이를 보고 정책을 다시 변경하지 않는다.

## 8. 실험 전에 확인할 체크리스트
### **데이터**
- 필수 column이 존재하는가?
- ID와 text가 비어 있지 않는가?
- ID가 유일한가?
- 정규화 후 중복 텍스트가 있는가?
- split 사이에 동일 샘플이 있는가
- Label 집합과 class 분포가 올바른가?
### **Tokenizer**
- Model과 tokenizer의 checkpoint가 일치하는가?
- Special token과 ID를 객체에서 읽었는가?
- token_type_ids를 무조건 가정하지 않았는가?
- Token 길이 분포를 확인했는가?
- max_length와 truncation 정책을 기록했는가?
### Batch
- input_ids와 attention_mask shape가 같은가?
- input_ids dtype이 정수형인가?
- PAD 위치와 mask 0 위치가 일치하는가?
- 동적 padding을 적용했는가?
- 원문과 sample ID를 오류 분석용으로 보존했는가?
### 평가
- Validation으로 설정과 checkpoint를 선택했는가?
- 마지막 checkpoint를 best로 가정하지 않았는가?
- Test는 선택 완료 후 평가했는가?
- Dataset·model·tokenizer version을 기록했는가?
## 9. 직접 설명해 보기
### Q1. Transformer가 RNN보다 긴 관계를 학습하기 유리한 이유는? 
RNN은 이전 hidden state를 순차적으로 거쳐 정보를 전달하기 때문에, 멀리 떨어진 토큰의 정보를 학습할 때 gradient가 여러 단계를 지나며 약해질 수 있다.
반면 Transformer은 Self-Attention을 통해 멀리 떨어진 토큰끼리도 직접 관계를 계산할 수 있기 때문에 긴 거리의 관계를 학습하는 데 더 유리하다. 
### Q2. tokenize( )와 tokenizer(…)의 차이는? 
`tokenize()` 는 입력 문장을 subword 등의 토큰 문자열로 나누는 기능이고, `tokenizer(…)` 는 tokenization 뿐 아니라 token ID 변환, special token 추가, padding, truncation, attention mask 생성 등을 수행하여 모델에 입력할 수 있는 형태로 만들어준다. 
### Q3. Dataset에서 바로 최대 길이로 Padding하지 않는 이유는?
Dataset 전체를 최대 길이로 Padding 하면 짧은 문장에 많은 **PAD 토큰이 추가**되어 **메모리와 연산이 낭비**된다.
따라서 Dataset에서는 **가변 길이를 유지**하고, DataLoader에서 **현재 batch의 최대 길이에 맞춰 동적으로 Padding 하는 것이 효율적**이다. 
### Q4. Token ID와 label ID는 왜 구분해야 하는가? 
Token ID는 입력 문장의 토큰을 vocabulary에 따라 숫자로 표현한 값이고, Label ID는 모델이 맞혀야 할 정답 클래스를 숫자로 표현한 값이다. 
두 ID는 서로 다른 의미와 체계를 가지므로 반드시 구분해야 한다. 
Token ID : 모델이 읽는 입력 번호
Label ID : 모델이 맞혀야 하는 정답 번호
### Q5. Validaiton과 Test를 분리하는 이유?
Validation 데이터는 하이퍼파라미터 조정, Early Stopping, 모델 선택 등에 사용되기 때문에 모델 개발 과정에 영향을 준다.
따라서 최종 모델의 일반화 성능을 공정하게 평가하기 위해 별도의 Test 데이터를 분리하고, 학습과 모델 선택이 모두 끝난 후 Test 데이터로 최종 평가한다. 
Train = 학습
Validation = 선택 및 튜닝
Test = 최종 평가
가장 중요한 것:
Validation을 계속 참고하면 Validation에도 간접적으로 과적합될 수 있기 때문에, 처음 보는 데이터에 대한 성능을 확인하려고 Test를 따로 둔다.

# 1. Retriever 전체 아키텍처


Retriever의 핵심 역할은 **사용자 질문과 관련된 PDF의 근거 청크를 찾아 Backend에 전달하는 것**이다.


<img width="1536" height="1024" alt="PROJECT 3 Retriever 아키텍처" src="https://github.com/user-attachments/assets/ef980275-bb2a-4421-90fb-9ca6b4d2274b" />


여기서 기억 해야 할 것은 **색인 시점과 질의 시점이 다르다**는 점이다. 

PDF 청킹·임베딩·Qdrant 색인은 미리 수행하고, BM25 메모리 인덱스는 Retriever 초기화 시 준비 한다.

사용자가 질문할 때마다 PDF를 다시 청킹하거나 BM25 전체 인덱스를 구축하진 않는다.

# 2. 세가지 검색 방식의 내부 동작
### 1) Navie (Dense)

질문의 의미와 비슷한 문서를 찾는 방식이다. E5 모델이 질문을 벡터로 변환하고, Qdrant에서 코사인 유사도가 높은 청크를 검색한다

.<img width="1536" height="1024" alt="Dense 검색(Naive) 동작 과정 인포그래픽" src="https://github.com/user-attachments/assets/c4c97042-fc00-4e81-9689-e246ed351da4" />


**장점**: 질문과 문서의 표현이 달라도 의미가 유사하면 찾을 수 있다.

**한계**: 정확한 문서 번호, 약어, 식별자처럼 키워드 일치가 중요한 경우에는 관련 근거를 놓칠 수 있다.

### 2) Hybrid (Dense + BM25)

<img width="1536" height="1024" alt="Hybrid 검색_ Dense·BM25·RRF 흐름" src="https://github.com/user-attachments/assets/3b533f15-74c2-4e7c-bd9a-b8f3d995c30c" />


RRF는 검색 점수 자체가 아닌 **순위**를 이용하므로 Dense와 BM25의 서로 다른 점수 체계를 직접 비교할 필요가 없다.

RRF = 1 / (60 + Dense 순위) + 1 / (60 + BM25 순위)

두 검색 방식에서 모두 높은 순위를 받은 문서가 유리하다. 여기서 60은 프로젝트에서 사용한 RRF 상수이다

상수를 60으로 정한이유는 RRF(Reciprocal Rank Fusion) 알고리즘에서 상수 \(k\) 값으로 60을 가장 많이 사용하는 이유는 2009년 원저자들의 논문에서 실험적으로 검증한 최적의 균형점이기 때문이다.

### 3) Hybrid + Rerank

Hybrid로 찾은 후보들 CrossEncoder가 질문과 함께 읽고 관련성을 다시 평가하는 방식이다.

<img width="1536" height="1024" alt="하이브리드 검색과 재랭킹 과정 인포그래픽" src="https://github.com/user-attachments/assets/c304441e-6477-4116-91c3-e218a8dd3448" />

**중요**: Reranker는 새로운 청크를 찾아오는 검색기가 아니다. 

앞 단계에서 가져온 후보들의 순서만 바꾼다. 

따라서 필요한 근거가 후보 50개 안에 없다면 Reranker만으로는 해결할 수 없다.

# 3. 세 방식의 실험 결과

<img width="554" height="540" alt="chart-line" src="https://github.com/user-attachments/assets/d0de9024-0b56-4db3-b6f7-21b03676000c" />

발표자료에서는 k=20의 Recall이 가장 높았지만, LLM이 전달할 청크 수와의 균형을 고려해 **Hybrid + Rerank, k = 10**을 최종 선택했다.

여기서 학습할 중요한 내용은 두 가지다. 

첫째, 검색 후보가 많다고 반드시 최종 결과가 좋은 것은 아니다.

둘째, k를 늘리면 Recall이 높아질 가능성이 있지만 LLM의 입력 토큰도 증가하므로 비용과 지연 시간을 함께 고려해야 한다.

# 4. Latency를 줄이는 방법

**Latency는 사용자가 요청한 뒤 결과가 돌아오기까지 걸리는 시간**이다.

Retriever에서는 단계별 시간을 나눠 분석해야 어디를 최적화할지 알 수 있다.

| 최적화 대상 | 개선 방법 |
| --- | --- |
| 모델 첫 로딩 | 모델 파일 캐시, 서버 시작 시 선로딩 및 워밍업 |
| Reranker 연산 | 후보 50개를 20~30개로 줄여 성능과 속도 비교 실험 |
| BM25 검색 | 인덱스를 서버 시작 시 한 번 구축하고 재사용 |
| 검색 단계 | Dense와 BM25를 병렬 실행하고 각각의 처리 시간 측정 |
| 동시 요청 | GPU 추론 대기 및 잠금 구조 점검, 배치 처리 검토 |

발표자료에서 Reranker의 **GPU 평균 재채점 시간은 50개 후보 기준 약 1.28초**이며, 모델 로딩 시간은 제외된 수치이다.

동시 요청의 잠금 대기 역시 남은 과제로 기록 되어 있다.

꼭 이해해야 할 점은 최종 **K = 10을 K = 5로 줄여도, Reranker가 여전히 50개 후보를 평가한다면 재채점 연산량은 거의 그대로**라는 것이다.

Reranker 지연을 줄이려면 최종 반환 k보다 후보 풀 크기를 먼저 살펴봐야 한다.

단, 후보를 줄이면 근거가 빠질 수 있으니 Recall과 함께 비교해야 한다.

# 5. 추가로 이해해야 할 핵심 개념

| 개념 | 프로젝트에서의 역할 |
| --- | --- |
| create_retriever() | Embedder와 Index를 주입받아 검색기 생성 |
| retrieve(request, ctx) | 질문과 모드를 받아 실제 검색 실행 |
| RetrievalRequest | 질문, 검색 모드, 최종 k 등을 전달 |
| RetrievalResult | 청크, 검색 점수, 순위, 지연 시간 등을 반환 |
| IndexManifest | 색인 조건과 모델 설정이 일치하는지 확인 |
| Hit@k | 필요한 근거를 하나라도 찾았는지 평가 |
| Recall@k | 필요한 근거 그룹 중 얼마나 찾았는지 평가 |
| CANDIDATE_POOL | Hybrid·Reranker에 전달할 최대 후보 수 (50) |

평가 쪽에서는 `Recall@k`를 특히 깊이 이해해야 한다. 

프로젝트의 골든 데이터셋은 **근거 그룹 단위**로 채점하고, 한 그룹에 여러 대체 페이지가 있으면 그중 하나만 찾아도 그 그룹은 충족된다.

이 기준으로 문항별 Recall을 계산하고 평균을 내는 구조이다.

# 6. 코드 리뷰·발표·면접에서 나올 법한 질문 10가지

### 1. Retriever는 RAG 전체 구조에서 어떤 역할을 하나요?

Retriever는 사용자 질문과 관련된 문서 청크를 검색하여 Backend에 전달하는 역할을 한다.
- 색인 단계: PDF를 파싱·청킹하고 E5로 임베딩하여 Qdrant에 저장한다.
- 검색 단계: 질문이 들어오면 관련 청크를 검색한다.
- 결과 전달: RetrievalResult에 검색된 청크, 점수, 순위, 메타데이터 등을 담아 반환한다.

Backend는 전달받은 청크로 문맥을 구성하고, LLM이 이를 근거로 답변을 생성하도록 한다.

### 2. Dense, BM25, Hybrid는 어떤 차이가 있고, 왜 함께 사용하나요?

| 검색 방식 | 원리 | 장점 | 한계 |
| --- | --- | --- | --- |
| Dense | 벡터 간 의미 유사도 검색 | 표현이 달라도 의미가 비슷하면 검색 가능 | 문서 번호나 정확한 키워드를 놓칠 수 있음 |
| BM25 | 검색어와 문서의 단어 일치도를 기반으로 점수 계산 | 정확한 용어·식별자 검색에 유리 | 표현이 다른 유사 의미 검색에 약함 |
| Hybrid | Dense + BM25 결과를 RRF로 결합 | 두 방식의 장점을 함께 활용 | 검색 단계와 연산 비용 증가 |

PROJECT 3에서는 의미 검색과 키워드 검색의 단점을 서로 보완하기 위해 Hybrid를 사용했다.

### 3. Hybrid에서 RRF를 사용하는 이유는 무엇이며, 중복 청크는 어떻게 처리하나요?

Dense와 BM25는 점수 계산 방식이 다르기 때문에 원래 점수를 직접 합산하기 어렵다.

RRF(Reciprocal Rank Fusion)는 점수 대신 검색 결과의 순위를 이용해 두 결과를 결합한다.
- Dense와 BM25에서 각각 상위 50개를 가져온다.
- 같은 chunk_id를 가진 청크는 하나로 합친다.
- 두 검색 결과에서 해당 청크가 받은 RRF 점수를 합산한다.
- 최종 점수가 높은 순서대로 정렬한다.

따라서 양쪽 검색에서 모두 높은 순위를 받은 청크가 유리해진다.

### 4. Reranker는 Dense 검색과 무엇이 다르고, 왜 더 많은 시간이 필요한가요?

Dense는 빠르게 후보를 찾고, Reranker는 후보의 관련성을 더 정밀하게 평가한다.

| 구분 | Dense (Bi-Encoder) | Reranker (CrossEncoder) |
| --- | --- | --- |
| 입력 | 질문과 문서를 각각 벡터화 | 질문과 문서를 한 쌍으로 입력 |
| 처리 | 벡터 유사도 계산 | 두 텍스트를 함께 분석 |
| 속도 | 상대적으로 빠름 | 상대적으로 느림 |
| 목적 | 관련 후보 검색 | 후보 재정렬 |

PROJECT 3에서는 `bge-reranker-v2-m3`를 사용했다.

후보 청크 50개를 질문과 각각 비교해야 하므로 연산량이 많으며, 발표자료 기준 GPU에서 50개 후보를 재채점하는데 평균 약 1.28초가 걸렸다. 모델 로딩 시간은 제외한 수치다.

### 5. Dense와 BM25에서 각각 50개를 뽑고 Reranker에는 50개만 전달하는 이유는 무엇인가요?

검색 정확도와 처리 비용 사이에서 균형을 맞추기 위해서이다.

1. Dense에서 최대 50개, BM25에서 최대 50개 검색
2. RRF로 결합하고 중복 청크 제거
3. 결합 결과에서 상위 50개를 선정
4. Reranker가 50개를 재채점
5. 최종 상위 10개 반환

후보가 너무 적으면 필요한 근거가 빠질 수 있고, 너무 많으면 Reranker 연산 시간이 증가한다.

다만 50개가 최적이라는 비교 실험 결과는 없으므로, 20개, 30개, 50개 등을 비교하여 적절한 후보 수를 검증할 필요가 있다.

### 6. Retriever의 Latency가 높아진다면 어느 단계부터 확인하고 어떻게 개선하겠는가?

먼저 **각 단계의 처리 시간을 측정해 병목 구간을 찾는다**.


| 확인 단계 | 개선 방법 |
| --- | --- |
| 모델 초기 로딩 | 캐시 활용, 선로딩, 워밍업 |
| Dense 검색 | 임베딩 시간과 Qdrant 검색 시간 분리 측정 |
| BM25 검색 | 초기화 시 인덱스를 한 번 구축하고 재사용 |
| RRF | 후보 수와 결합 연산 확인 |
| Reranker | 후보 수 축소, 배치 처리 검토 |
| 동시 요청 | GPU 잠금 대기와 추론 처리 방식 점검 |

특히 Reranker 후보를 50개에서 30개로 줄이는 실험을 진행해 볼 수 있다.

단순히 응답 속도만 줄이는 것 아니라 **Recall@k가 얼마나 유지되는지도 함께 평가**해야 한다.

### 7. 검색 평가에서 Hit@k보다 Recall@k를 더 중요하게 본 이유는 무엇인가요?

Hit@k는 필요한 근거를 **하나라도 찾았는지** 평가하지만, Recall@k는 **전체 근거 중 얼마나 찾았는지**를 평가한다.

| 지표 | 결과 |
| --- | --- |
| Hit@k | 1.0 (성공) |
| Recall@k | 0.5 (50%) |

Hit@k만 보면 검색에 성공했다고 판단할 수 있지만, 실제로는 필요한 근거의 절반을 놓쳤다.

PROJECT 3은 여러 문서의 근거를 종합해 답변해야 하므로 **근거 확보 수준을 측정하는 Recall@k를 주요 지표로 선택**했다

### 8. 형태소 분리로 BM25 후보의 근거가 늘었는데도 최종 Recall이 거의 변하지 않는 이유는 무엇인가요?

BM25 검색 결과가 좋아져도 **RRF 결합과 Reranker 재정렬을 거치면서 최종 순위가 달라질 수 있기 때문**이다.

| 방식 | BM25 후보 근거 그룹 | 최종 Recall@10 |
| --- | --- | --- |
| regex | 133개 | 76.5% |
| josa | 136개 | 76.8% |
| kiwi | 144개 | 76.4% |

Kiwi는 BM25 후보 단계에서 더 많은 근거를 확보했지만, 최종 Recall은 거의 동일했다.

이 결과만으로 원인을 확정할 수는 없다. 후보에 추가된 근거가 **RRF 상위 50개에 남았는지, Reranker 최종 10개에 포함됐는지**를 추적해야 정확한 원인을 알 수 있다.

### 9. Qdrant와 BM25 인덱스는 언제 생성되며, 색인 설정이 맞지 않으면 어떻게 되나요?

Qdrant 색인과 BM25 인덱스는 준비 시점이 다르다.
- **Qdrant**: PDF 청킹과 임베딩을 완료한 뒤 벡터를 저장하는 색인 단계에서 생성한다.
- **BM25**: Retriever 초기화 시 저장된 청크 텍스트를 읽어 메모리에 구축하고 재사용하낟.
- **질의 시점**: 이미 준비된 인덱스를 활용해 검색만 수행한다.

또한 `IndexManifest`에는 임베딩 모델, 차원, 정규화 방식 등 색인 관련 설정이 기록된다.

검색에 사용하는 설정이 기존 색인과 일치하지 않으면 `IndexNotReadyError`**를 발생시켜 잘못된 조건으로 검색하지 않도록 방지**한다.


### 10. 현재 Retriever의 가장 큰 한계는 무엇이며, 시간이 더 있다면 어떤 실험을 먼저 하겠습니까?

현재 가장 큰 한계는 **필요한 근거를 모두 찾지 못하는 질문이 여전히 존재한다는 점**이다.

최종 Hybrid + Rerank의 페이지 기준 Recall@10은 76.5%이다.

개선한다면 다음 순서로 진행하고 싶다.
1. **검색 실패 원인 분석**: 근거가 Dense, BM25 후보 단계에서 누락됐는지, RRF, Reranker에서 밀려놨는지 확인
2.** 검색 구조 개선**: 복잡한 질문을 하위 질문으로 분해하여 여러 번 검색하는 방식 실험
3. **검색 결합 방식 개선**: RRF 설정과 후보 수를 변경하여 성능 비교
4. **평가 데이터셋 확장**: 다양한 질문 유형으로 개선 효과 검증

가장 먼저 검색 실패 원인을 분석하고, 이를 바탕으로 **복합 질문 분해와 검색 골과 결합 방식 개선**을 진행하겠습니다.

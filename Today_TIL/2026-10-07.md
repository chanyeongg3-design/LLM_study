## 2-1. 모델 선택과 Checkpoint 복원

### 정의

여러 학습 실험 중 **Validation 성능을 비교하여 실제 사용할 모델을 선택하고**, 선택된 모델의 Checkpoint를 다시 불러오는 과정이다.

### 쉽게 말하면

여러 번 학습시킨 모델 중에서:

> **"실제 예측에 이 모델을 사용하겠다."**

라고 하나를 고르는 과정이다.

---

## selected.json

### 정의

`selected.json`은 실제 모델 가중치를 저장한 파일이 아니다.

어떤 실험의 모델을 사용할지 알려주는 **선택 기록 파일**이다.

```text
selected.json
= 사용할 모델이 어디 있는지 알려주는 주소표
```

예:

```json
{
  "run_name": "lr2e5",
  "run_learner": "learner01",
  "validation_macro_f1": 1.0,
  "selected_by": "validation_macro_f1"
}
```

실제 모델 가중치는 다음과 같은 Checkpoint 안에 존재한다.

```text
learner01/
└── lr2e5/
    ├── config.json
    ├── validation_metrics.json
    └── checkpoint/
        ├── model.safetensors
        └── tokenizer 관련 파일
```

### 연결 흐름

```text
Validation 점수
      ↓
실험 후보 비교
      ↓
가장 좋은 후보 선택
      ↓
selected.json
      ↓
실험 폴더 찾기
      ↓
checkpoint
      ↓
모델 + tokenizer 복원
```

### 왜 필요한가?

학습한 모델을 사용할 때마다 다시 학습하면:

- 시간이 오래 걸리고
- GPU 자원을 다시 사용해야 하고
- 같은 모델을 안정적으로 재사용하기 어렵다.

Checkpoint를 저장해 두면:

```text
한 번 학습
   ↓
Checkpoint 저장
   ↓
여러 번 추론
```

이 가능하다.

### 장점

- 다시 학습할 필요가 없음
- 동일한 모델 재사용 가능
- 배포 환경에서 바로 추론 가능
- 실험 결과를 비교해 모델 선택 가능

### 주의점

`selected.json`만 다른 컴퓨터로 옮긴다고 모델을 사용할 수 있는 것은 아니다.

`selected.json`은 모델 위치를 알려줄 뿐이므로 실제:

- Checkpoint
- Tokenizer
- Config

파일도 필요하다.

# 2-2. 분류 모델의 추론 흐름

저장한 BERT 분류 모델에 새로운 문장을 넣으면 다음 흐름으로 라벨을 결정한다.

```text
사용자 문장
   ↓
Tokenizer
   ↓
input_ids
   ↓
BERT
   ↓
logits
   ↓
softmax
   ↓
argmax
   ↓
label
```

---

## Tokenizer

### 정의

사람이 사용하는 문장을 모델이 처리할 수 있는 **숫자 토큰으로 변환하는 도구**다.

예:

```text
"배송이 늦어요"
      ↓
Tokenizer
      ↓
[101, 3254, 7812, ...]
```

### 역할

```text
문자열
→ 숫자
```

로 변환하여 BERT가 입력을 처리할 수 있도록 만든다.

---

## input_ids

Tokenizer가 문장을 변환한 **토큰 번호 목록**이다.

예:

```python
input_ids.shape
```

```text
[1, 30]
```

이라면:

- `1` → 문장 1개
- `30` → 토큰 30개

라는 의미다.

---

## Logits

**Logits(로짓)**은 모델이 각 라벨에 대해 계산한 **원시 점수**다.

예:

```text
shipping : 2.1
refund   : 0.8
account  : -0.4
```

이 값 자체는 확률이 아니다.

### 쉽게 말하면

> **모델이 각 정답 후보에 얼마나 점수를 줬는지 나타내는 값**

---

## Softmax

### 정의

Logits를 **합이 1인 값들로 변환**하는 함수다.

예:

```text
Logits
[2.1, 0.8, -0.4]

      ↓ Softmax

[0.72, 0.20, 0.08]
```

결과:

```text
shipping = 0.72
refund   = 0.20
account  = 0.08
```

### 중요한 특징

```text
0.72 + 0.20 + 0.08 = 1.0
```

---

## Argmax

### 정의

여러 값 중 **가장 큰 값의 위치(index)**를 반환한다.

예:

```text
[0.72, 0.20, 0.08]
   ↑
```

가장 큰 값은 위치 `0`이다.

```python
index = probabilities.argmax()
```

결과:

```text
index = 0
```

그리고:

```python
labels[0]
```

을 확인하면:

```text
shipping
```

이 된다.

---

## 전체 분류 흐름

```text
"배송이 늦어요"
      ↓
Tokenizer
      ↓
input_ids
      ↓
BERT
      ↓
logits
[2.1, 0.8, -0.4]
      ↓
softmax
[0.72, 0.20, 0.08]
      ↓
argmax
0
      ↓
labels[0]
      ↓
shipping
```

---

## Confidence

예:

```python
{
    "label": "shipping",
    "confidence": 0.6360
}
```

여기서 `confidence=0.6360`을:

```text
정답 확률 = 63.60%
```

라고 단정하면 안 된다.

### 왜?

이 값은 모델이 계산한 출력 분포의 크기이지:

> 실제 정답일 통계적 확률을 자동으로 보장하는 값

은 아니기 때문이다.

따라서:

```text
confidence
= 모델이 해당 라벨에 준 상대적인 출력 점수
```

라고 이해하는 것이 안전하다.

---

## model.eval()

```python
model.eval()
```

### 역할

모델을 **학습 모드에서 추론 모드로 변경**한다.

예를 들어 Dropout 같은 학습용 동작이 추론 방식으로 바뀐다.

---

## torch.inference_mode()

```python
with torch.inference_mode():
    logits = model(**features).logits
```

### 역할

추론 과정에서 **Gradient를 계산하지 않도록 한다.**

즉:

```text
학습
→ gradient 필요

추론
→ gradient 필요 없음
```

### 중요한 점

```text
model.eval()
```

과

```text
torch.inference_mode()
```

는 서로 역할이 다르다.

둘 중 하나가 다른 하나를 대신하는 것이 아니다.

# 2-3. 생성형 LLM 호출과 Structured Output

분류 모델에서 얻은:

```text
shipping
```

이라는 라벨은 사용자가 원하는 답변이 아니다.

라벨은 단지:

> **이 문의가 어떤 종류인지**

판단한 결과다.

실제 자연어 답변을 만들기 위해 생성형 LLM을 사용한다.

---

## 생성 모델에 전달하는 정보

Prompt는 크게 다음 정보를 포함한다.

```text
안내 기준
+
출력 형식
+
사용자 원문
      ↓
Prompt
```

그리고 이 Prompt를:

```text
Ollama
또는
OpenAI
```

에 전달한다.

---

## Prompt

### 정의

LLM에게:

- 어떤 역할을 해야 하는지
- 어떤 규칙을 따라야 하는지
- 어떤 형식으로 출력해야 하는지
- 사용자가 무엇을 입력했는지

전달하는 입력 문자열이다.

예:

```text
한국어로 배송 확인 방법을 안내한다.

배송 날짜나 실제 조회 완료 여부를 지어내지 않는다.

출력은 JSON 객체 하나이며
필드는 answer와 next_steps뿐이다.

사용자 입력:
"배송 상태가 준비 중입니다."
```

### 중요한 점

`build_prompt()`의 반환값은:

```python
str
```

즉 **문자열 하나**다.

---

# JSON

## 정의

**JSON(JavaScript Object Notation)**은 데이터를 키와 값 형태로 표현하는 표준 형식이다.

예:

```json
{
  "answer": "배송 상태를 확인해 주세요.",
  "next_steps": [
    "운송장 번호를 확인하세요."
  ]
}
```

### 쉽게 말하면

> **프로그램끼리 데이터를 주고받기 좋은 정해진 데이터 작성 형식**

---

## 생성 결과

LLM이 반환한 결과가 다음과 같다고 하자.

```python
result["text"]
```

실제 타입은:

```python
str
```

이다.

내용:

```text
'{"answer":"배송 상태를 확인하세요.","next_steps":[]}'
```

겉으로 보면 JSON처럼 생겼지만 아직 Python에서는 **문자열**이다.

---

## json.loads()

JSON 문자열을 Python 객체로 변환한다.

```python
payload = json.loads(result["text"])
```

변환:

```text
JSON 문자열
      ↓
json.loads()
      ↓
Python dict
```

그 이후:

```python
payload["answer"]
```

처럼 접근할 수 있다.

---

# Pydantic 출력 검증

출력 구조를 다음과 같이 정의할 수 있다.

```python
class AnswerPayload(BaseModel):
    model_config = ConfigDict(extra="forbid")

    answer: str = Field(min_length=1)
    next_steps: list[str]
```

### 검사 가능한 것

Pydantic은 다음을 검사할 수 있다.

- JSON 문법
- `answer` 필드 존재 여부
- `next_steps` 존재 여부
- 자료형
- 빈 문자열
- 요청하지 않은 추가 필드

예:

```json
{
  "answer": "",
  "next_steps": []
}
```

`answer`가 비어 있으므로 실패할 수 있다.

---

## extra="forbid"

```python
ConfigDict(extra="forbid")
```

는 정의하지 않은 필드가 추가되는 것을 금지한다.

예:

```json
{
  "answer": "확인하세요.",
  "next_steps": [],
  "debug": true
}
```

여기서 `debug`는 스키마에 정의되어 있지 않으므로 검증 실패가 된다.

---

# 형식 검증과 내용 검증

이 둘은 반드시 구분해야 한다.

예:

```json
{
  "answer": "주문을 조회했습니다. 내일 도착합니다.",
  "next_steps": []
}
```

구조만 보면:

```text
answer = str ✅
next_steps = list ✅
```

이므로 형식 검증을 통과할 수 있다.

하지만 실제 주문 조회 기능이 없다면:

```text
"주문을 조회했습니다."
"내일 도착합니다."
```

는 근거 없는 내용이다.

따라서:

> **형식 검증 통과 ≠ 답변 내용이 정확함**

이다.

# 2-4. 분류 → 정책 → Prompt → 생성 연결

오전에는:

```text
분류
```

와

```text
생성
```

을 따로 실행했다.

오후에는 두 기능을 하나로 연결했다.

---

## 전체 흐름

```text
사용자 문의
    ↓
BERT 분류
    ↓
label
    ↓
POLICIES[label]
    ↓
정책 선택
    ↓
Prompt 구성
    ↓
생성 LLM 호출
    ↓
답변
```

---

# POLICIES

라벨별 정책을 저장한 딕셔너리다.

```python
POLICIES = {
    "shipping": "배송 관련 안내 기준",
    "refund": "환불 관련 안내 기준",
    "account": "계정 관련 안내 기준",
}
```

예를 들어:

```python
label = "shipping"
```

이면:

```python
policy = POLICIES[label]
```

결과:

```text
배송 관련 안내 기준
```

을 사용한다.

---

## 왜 정책을 나눌까?

사용자가 물어보는 질문 종류에 따라 답변 기준이 다르기 때문이다.

```text
배송 문의
→ 배송 정책

환불 문의
→ 환불 정책

계정 문의
→ 계정 정책
```

즉:

> **분류 모델이 생성 모델이 어떤 기준으로 답할지 결정한다.**

---

# LCEL 연결

LangChain에서는 다음처럼 두 함수를 연결할 수 있다.

```python
chain = (
    RunnableLambda(classify)
    | RunnableLambda(apply_policy)
)
```

`|`는:

> **왼쪽 단계의 출력을 오른쪽 단계의 입력으로 전달**

한다.

---

## classify()

예:

```python
def classify(text):
    text = text.strip()

    classification = predict_text(
        text,
        classifier
    )

    return {
        "text": text,
        "classification": classification
    }
```

입력:

```text
"배송이 늦어요"
```

출력:

```python
{
    "text": "배송이 늦어요",
    "classification": {
        "label": "shipping",
        "confidence": 0.72
    }
}
```

---

## 왜 label만 반환하지 않을까?

잘못된 구조:

```python
return classification["label"]
```

결과:

```text
shipping
```

만 남는다.

그렇게 되면 다음 단계에서:

> 사용자가 정확히 무엇을 물어봤는지

알 수 없다.

그래서:

```python
{
    "text": text,
    "classification": classification
}
```

처럼 **원문도 함께 전달**한다.

---

# apply_policy()

분류 결과의 label을 읽는다.

```python
label = item["classification"]["label"]
```

그리고:

```python
policy = POLICIES[label]
```

로 정책을 선택한다.

마지막으로 Prompt를 만든다.

```python
return {
    **item,
    "policy": policy,
    "prompt": prompt
}
```

---

## {**item, ...}

기존 딕셔너리 내용을 유지하면서 새로운 값을 추가한다.

입력:

```python
{
    "text": "...",
    "classification": {...}
}
```

출력:

```python
{
    "text": "...",
    "classification": {...},
    "policy": "...",
    "prompt": "..."
}
```

### 장점

앞 단계 결과를 잃어버리지 않고 다음 단계에 계속 전달할 수 있다.

---

# 전체 LCEL 데이터 흐름

```text
사용자 text
    ↓
classify()
    ↓
{
 text,
 classification
}
    ↓
apply_policy()
    ↓
{
 text,
 classification,
 policy,
 prompt
}
```

# generate_prepared()

분류와 Prompt 구성이 끝난 데이터를 생성 모델로 전달한다.

```python
def generate_prepared(prepared, provider):
    return call_model(
        provider,
        prepared["prompt"]
    )
```

여기서 실제 LLM 호출이 시작된다.

---

## 중요한 구분

```python
prepared = chain.invoke(INPUT_TEXT)
```

가 끝났다고 생성 답변까지 만들어진 것은 아니다.

여기까지는:

```text
분류
+
정책 선택
+
Prompt 구성
```

까지 완료된 것이다.

실제 생성은:

```python
generate_prepared(...)
```

에서 시작된다.

# 2-5. Ollama와 OpenAI 호출

같은 Prompt를 서로 다른 LLM Provider에 전달할 수 있다.

```text
Prompt
 ├─→ Ollama
 └─→ OpenAI
```

---

## Provider

**Provider(프로바이더)**는 모델을 제공하거나 실행하는 주체를 의미한다.

예:

```text
ollama
openai
```

---

# Ollama

로컬 컴퓨터에서 모델을 실행한다.

예:

```text
http://127.0.0.1:11434
```

### 특징

- 로컬 모델 사용
- API 사용료 없음
- 인터넷 없이 사용 가능한 경우가 있음
- PC 성능 영향을 많이 받음

---

# OpenAI

클라우드 API를 이용한다.

### 특징

- 외부 서버의 모델 사용
- API 사용량에 따라 비용 발생 가능
- 네트워크 연결 필요
- API Key 필요

---

# call_model()

Provider에 따라 실제 호출 함수를 선택한다.

```python
if provider == "ollama":
    output = call_ollama(prompt)
else:
    output = call_openai(prompt)
```

그러나 호출 결과는 같은 구조로 맞춘다.

예:

```python
{
    "text": ...,
    "model": ...,
    "usage": ...,
    "generation_complete": ...,
    "finish_reason": ...
}
```

이렇게 하면 뒤쪽 코드는 Provider에 상관없이:

```python
result["text"]
```

를 읽을 수 있다.

---

# Response

**Response(리스폰스)**는 Request에 대한 응답이다.

```text
Request
"배송 문의"

    ↓

서버 / 모델

    ↓

Response
"배송 상태를 확인해 주세요."
```

---

# 오류도 같은 형식으로 기록

모델 호출 실패 시에도 프로그램을 바로 깨뜨리지 않고 동일한 구조로 결과를 저장한다.

예:

```python
{
    "text": "",
    "model": None,
    "usage": {
        "input_tokens": None,
        "output_tokens": None
    },
    "generation_complete": False,
    "finish_reason": "error",
    "error": "ConnectError"
}
```

### 장점

성공과 실패 데이터를 같은 방식으로 분석할 수 있다.

# Request

**Request(리퀘스트)**

사용자가 서버에 보내는 요청이다.

예:

```json
{
  "text": "배송 조회가 안 됩니다.",
  "provider": "openai"
}
```

---

# Pydantic 요청 모델

```python
class TextRequest(BaseModel):
    text: str = Field(
        min_length=1,
        max_length=MAX_INPUT_CHARS
    )
```

공백만 있는 문자열도 막기 위해 Validator를 사용한다.

```python
@field_validator("text")
@classmethod
def nonblank(cls, text):
    if not text.strip():
        raise ValueError(
            "공백만 입력할 수 없습니다."
        )

    return text.strip()
```

---

# GenerateRequest

```python
class GenerateRequest(TextRequest):
    provider: Literal[
        "ollama",
        "openai"
    ] = "ollama"
```

즉:

```text
ollama ✅
openai ✅
other ❌
OpenAI ❌
```

이다.

`Literal`이므로 정확한 문자열만 허용된다.

# HTTP 상태 코드

## 200

```text
HTTP 200
```

→ API 호출 과정에서 처리 가능한 오류 없이 결과를 반환했다.

하지만:

```text
HTTP 200
≠
LLM 답변 내용이 정확함
```

이다.

200이어도 다음을 확인해야 한다.

- 생성 완료 여부
- JSON 형식
- 답변 내용
- 정책 준수
- 근거 없는 주장

---

## 422

```text
HTTP 422
```

→ Request 데이터가 Pydantic 검증에 실패했다.

예:

```json
{
  "text": "   "
}
```

또는:

```json
{
  "provider": "other"
}
```

이 경우 실제 처리 함수에 들어가기 전에 거절된다.

---

## 502

```text
HTTP 502
```

→ 생성 모델을 호출하는 과정에서 오류가 발생했다.

예:

- Ollama 서버 꺼짐
- OpenAI API 연결 오류
- API Key 문제

- 분류 결과
- Policy
- Prompt

# lifespan

FastAPI 서버가 시작될 때 실행되는 생명주기 처리다.

예:

```python
@asynccontextmanager
async def lifespan(app):
    classifier = load_classifier()

    app.state.chain = create_chain(
        classifier
    )

    yield
```

---

## 왜 서버 시작 시 모델을 불러올까?

잘못된 방식:

```text
요청 1
→ 모델 파일 읽기
→ 예측

요청 2
→ 모델 파일 읽기
→ 예측

요청 3
→ 모델 파일 읽기
→ 예측
```

좋은 방식:

```text
서버 시작
→ 모델 파일 읽기 1회

요청 1 → 예측
요청 2 → 예측
요청 3 → 예측
```

### 장점

- 요청마다 파일을 읽지 않음
- 요청 속도 향상
- 메모리에 모델 재사용
- 모델 로딩 실패를 서버 시작 시 확인 가능

# 4. 개념 간 차이

## selected.json vs Checkpoint

| 개념 | 역할 |
|---|---|
| **selected.json** | 어떤 실험을 사용할지 기록 |
| **Checkpoint** | 실제 모델 가중치와 Tokenizer 저장 |

쉽게 말하면:

```text
selected.json
= 주소표

Checkpoint
= 실제 모델
```

---

## Logits vs Softmax

| 개념 | 의미 |
|---|---|
| **Logits** | 모델의 원시 점수 |
| **Softmax** | Logits를 합이 1인 분포로 변환 |

---

## Softmax vs Argmax

| 개념 | 역할 |
|---|---|
| **Softmax** | 각 후보의 상대적인 값 계산 |
| **Argmax** | 가장 큰 값의 위치 선택 |

---

## 분류 모델 vs 생성 모델

| 구분 | 분류 모델 | 생성 모델 |
|---|---|---|
| 예 | BERT | Qwen / GPT |
| 입력 | 사용자 문장 | Prompt |
| 출력 | Label | 자연어 답변 |
| 역할 | 종류 판단 | 답변 생성 |

쉽게 말하면:

```text
BERT
→ 어떤 문의인가?

LLM
→ 어떻게 답할까?
```

---

## Request vs Response

| 개념 | 의미 |
|---|---|
| **Request** | 사용자가 서버에 보내는 데이터 |
| **Response** | 서버가 사용자에게 돌려주는 데이터 |

---

## 형식 검증 vs 내용 검증

| 구분 | 형식 검증 | 내용 검증 |
|---|---|---|
| 확인 | JSON, 필드, 타입 | 사실성, 정책 준수 |
| 도구 | Pydantic | 사람 평가 / 별도 평가 |
| 예 | answer가 문자열인가? | 없는 배송일을 만들었나? |

# 5. Validation과 Test

모델 평가 데이터를 다음처럼 구분한다.

```text
Train
→ 학습

Validation
→ 모델 선택

Test
→ 최종 평가
```

---

## Train

모델의 **가중치를 실제로 업데이트**하는 데이터다.

---

## Validation

학습 중:

- Epoch 선택
- Learning Rate 비교
- 실험 비교
- 최종 모델 선택

등에 사용한다.

---

## Test

모든 모델 선택과 설정이 끝난 후:

> **최종적으로 이 모델이 어느 정도 성능인지 확인**

할 때 사용한다.

### 중요한 점

Test 점수를 확인한 뒤:

```text
모델 변경
Prompt 변경
학습 설정 변경
```

을 반복하면 Test 데이터가 개발 과정에 영향을 주게 된다.

따라서:

> **Test는 최종 확인용으로 사용해야 한다.**

# 6. JSONL 결과 기록

## JSONL

**JSON Lines**

```text
한 줄
=
하나의 JSON 객체
```

예:

```json
{"case_id":"q1","provider":"ollama"}
{"case_id":"q1","provider":"openai"}
{"case_id":"q2","provider":"ollama"}
```

---

## 왜 JSONL을 사용하는가?

LLM 호출 결과를 한 줄씩 저장하면:

- 호출별 결과 확인
- Provider별 분석
- 실패 기록 보존
- Python에서 한 줄씩 읽기
- 대량 실험 결과 관리

가 편하다.

---

# 실패 결과도 저장해야 한다

예:

```text
성공
→ 기록

실패
→ 기록
```

실패를 삭제하면:

```text
실제 오류율
```

을 알 수 없게 된다.

예를 들어 실제 4번 호출 중 1번 실패했다면:

```text
오류율 = 1 / 4 = 25%
```

이다.

그 실패 행을 삭제하고 성공 3건만 보면:

```text
오류율 = 0%
```

처럼 잘못 보일 수 있다.

# 7. 자동 평가 지표

## 오류율

```text
오류 수
───────
전체 호출 수
```

---

## 형식 유효율

```text
형식 검증 성공 수
─────────────
전체 호출 수
```

---

## 평균 응답 시간

자료에서는 **예외가 없는 호출만** 평균 계산에 사용한다.

```text
성공한 호출의 응답 시간 합
──────────────────
성공 호출 수
```

---

## 왜 분모가 다를까?

예를 들어 네 번 호출했다고 하자.

```text
1초 → 성공
2초 → 성공
3초 → 성공
30초 → 오류
```

### 오류율

```text
1 / 4
= 25%
```

### 평균 응답 시간

오류를 제외한다.

```text
(1 + 2 + 3) / 3
= 2초
```

# 8. Human Evaluation

자동 지표만으로는 LLM 답변의 실제 품질을 판단하기 어렵다.

예를 들어 두 답변이 모두:

```text
HTTP 200
JSON 형식 정상
```

이라고 하더라도 한 모델이 없는 정보를 만들어냈을 수 있다.

그래서 사람이 실제 답변을 읽고 평가한다.

---

## 평가 기준

| 항목 | 의미 |
|---|---|
| **policy_correct** | 정책과 원문에 맞게 답했는가 |
| **required_points** | 필요한 안내를 포함했는가 |
| **no_unsupported_claims** | 근거 없는 사실을 만들지 않았는가 |
| **clarity** | 답변이 이해하기 쉬운가 |

---

## 점수 예시

```text
0점
→ 중요한 오류 또는 요구사항 미충족

1점
→ 일부 충족, 수정 필요

2점
→ 요구사항 충족
```

---

## 중요한 원칙

```text
형식 유효율
≠
내용 품질
```

예:

```json
{
  "answer": "환불 처리가 완료됐습니다.",
  "next_steps": []
}
```

JSON 형식은 완벽할 수 있다.

그러나 실제 환불 처리를 확인하지 않았다면 내용은 잘못됐다.

# 9. 실제 LLM 프로젝트에서는 어떻게 사용되는가?

예를 들어 **쇼핑몰 고객 상담 AI**를 만든다고 하자.

| 단계 | 구성 요소 | 역할 |
|---|---|---|
| 1 | 사용자 | 문의 입력 |
| 2 | FastAPI | HTTP Request 수신 |
| 3 | Pydantic | 입력 검증 |
| 4 | BERT | 문의 종류 분류 |
| 5 | Label | shipping/refund/account 결정 |
| 6 | Policy Router | 라벨에 맞는 정책 선택 |
| 7 | Prompt | 정책 + 원문 + 출력 규칙 |
| 8 | LLM | 답변 생성 |
| 9 | Pydantic | 출력 구조 검사 |
| 10 | Response | 사용자에게 결과 반환 |
| 11 | JSONL | 호출 기록 저장 |
| 12 | Metrics | 오류·형식·시간 평가 |
| 13 | Human Evaluation | 실제 답변 내용 평가 |

# 11. 장점과 단점

| 기술/구조 | 장점 | 단점 / 주의점 |
|---|---|---|
| **BERT 분류** | 빠르게 문의 종류 판단 | 오분류 가능 |
| **Label → Policy** | 질문 종류별 답변 제어 | 라벨이 틀리면 정책도 틀림 |
| **Checkpoint** | 재학습 없이 모델 재사용 | 모델 파일 관리 필요 |
| **Structured Output** | 프로그램에서 결과 사용 쉬움 | 내용 정확성 보장 X |
| **Pydantic** | 데이터 구조 검증 가능 | 사실성 검증 X |
| **Ollama** | 로컬 실행 | 하드웨어 성능 영향 |
| **OpenAI API** | 강력한 클라우드 모델 사용 | 비용·네트워크 필요 |
| **FastAPI** | LLM 기능을 서비스로 제공 | 운영·오류 처리 필요 |
| **JSONL** | 실험 결과 기록 쉬움 | 데이터가 많아지면 분석 도구 필요 |
| **자동 지표** | 빠른 대량 비교 | 의미적 품질 판단 한계 |
| **사람 평가** | 실제 내용 품질 판단 | 시간과 인력 필요 |

# 12. 같이 알아두면 좋은 관련 개념

## Inference

학습된 모델의 가중치를 바꾸지 않고 새로운 입력에 대한 결과를 계산하는 과정.

```text
Training
→ 가중치 변경

Inference
→ 가중치 변경 X
```

---

## Model Serving

학습된 모델을 API 서버 등에 올려 외부 프로그램에서 사용할 수 있게 만드는 과정.

이번 학습에서는:

```text
BERT
+
FastAPI
```

구조가 Model Serving의 기초가 된다.

---

## Routing

입력에 따라 다른 처리 경로를 선택하는 것.

이번 프로젝트에서는:

```text
BERT Label
      ↓
Policy 선택
```

이 Routing 역할을 한다.

---

## Structured Output

LLM이 자유로운 자연어가 아니라 프로그램이 처리하기 쉬운 일정한 구조로 출력하도록 만드는 방식.

예:

```json
{
  "answer": "...",
  "next_steps": []
}
```

---

## Observability

실제 서비스에서:

- 오류
- 응답 시간
- 토큰 사용량
- 실행 결과

등을 기록하고 관찰하는 개념이다.

이번 `results.jsonl` 기록도 기본적인 Observability 관점과 연결된다.

## 📚 오늘 배운 것:
### 1. Responses API 기본 구조 
LLM API의 기본 흐름을 배웠다. 
```Plain Text
사용자 입력 
→ Responses API 요청
→ 모델 처리 
→ Response 객체
→ 결과 사용
```
기본 요청에서는 주로 다음 값을 사용한다.
- model: 사용할 모델
- input: 실제 사용자 요청
- instructions: 모델이 따라야 할 상위 규칙
- max_output_tokens: 최대 출력량
응답에서는 다음 값을 확인한다.
- response.output_text: 최종 텍스트
- response.status: 요청 상태
- response.output: message, tool call 등의 전체 출력
- response.usage: token 사용량
- response.id: 응답 식별자  
> API Key는 코드에 직접 넣지 않고 환경 변수나 Colab Secrets로 관리한다.
### 2. Developer Prompt
사용자 질문과 애플리케이션 규칙을 분리해야 한다.
```Plain Text
Developer Prompt
→ 모델의 역할 / 범위 / 규칙 / 출력 형식

User Prompt
→ 이번에 처리할 실제 질문 
```
좋은 Developer Prompt는 다음 요소를 가진다.
- 역할
- 맥락 
- 작업 범위
- 제약
- 불확실성  처리
- 출력 형식
- 성공 기준
```Plain Text
단순히 "정확하게 답하세요" 라고 하는 것보다 모르면 추측하지 않는다.
출력은 핵심 설명 → 예시 → 확인 순서로 작성한다. 

처럼 검사 가능한 행동을 명시하는 것이 중요하다. 
```
### 3. Baseline과 Few-shot Prompt
프롬프트는 감으로 수정하는 것이 아니라 실험으로 개선한다. 
기본흐름:
```Plain Text
Baseline
→ 결과 평가
→ 실패 원인 분석
→ 한 가지 요소 수정
→ 다시 실행
→ 결과 비교
```
Baseline은 가장 단순한 기준점이다.
Few-shot은 모델에게 **“입력 → 정답”**  예시를 보여주는 방법이다. 
특히 다음 상황에서 유용하다
- 분류 기준이 애매할 때 
- 출력 형식이 복잡할 때
- 사내 용어를 사용할 때
- 경계 사례가 있을 때 
프롬프트 실험에서는 가능하면 
- 모델
- 테스트 데이터
- 평가 기준
을 고정하고 Prompt만 변경해야 한다. 
### 4. 평가 루브릭
모델 출력은 단순히 “좋다/나쁘다” 가 아니라 기준을 만들어 평가한다. 
예: 정확성, 형식 준수, 일관성, 불확실성 처리 
가능하면 코드로 검사할 수 있는 것은 자동 평가한다.
```Python
correct = int(prediction == expected)
format_ok = int(prediction in ALLOWED_LABELS)
```
Prompt 버전 뿐 아니라
- model
- input
- output
- score
- token
- latency
- request_id
도 함께 기록하는 것이 좋다
### 5. JSON Schema와 Structured Output
자연어 출력은 프로그램에서 다루기 어렵기 때문에 JSON Schema로 출력 계약을 정의한다**.**
**중요한 키워드:**
- type
- properties
- required
- enum
- items
- additionalProperties
```Python
{
"category": "delivery",
"priority": 2,
"needs_review": false
}
```
여기서 반드시 구분해야 한다.
```Python
JSON 문법이 올바르다
≠
Schema를 만족한다
≠
내용이 사실이다
```
즉 Structured Output은 형식 안정성을 높여주지만 내용의 정확성까지 보장하지 않는다. 
### 6. Pydantic
JSON Schema를 Python 코드로 편리하게 관리하기 위해 Pydantic을 사용할 수 있다.
핵심요소:
- Baseline
- Field
- Literal
- ConfigDict
예:
```Python
class Ticket(BaseModel):
		model_config = ConfigDict(extra="forbid")
		
		category: Literal["delivery", "refund", "account"]
		priority: int = Field(ge=1, le=3)
```
중요 함수: `model_validate()` 
외부 데이터를 검증한다. `model_dump()`
Pydantic 객체를 dict로 바꾼다. `model_json_schema()` 
Pydantic 모델을 JSON Schema로 변환한다.
OpenAI에서는 `client.responses.parse(…)` 와 `response.output_parsed` 를 사용하면 Structured Output을 Pydantic 객체로 바로 받을 수 있다. 
### 7. Tool Calling
Tool Calling에서 중요한 점은 **모델이 함수를 직접 실행하는 것이 아니라는 것**이다.
 
```Plain Text
사용자 요청
→ 모델이 Tool 선택
→ arguments 생성
→ 애플리케이션이 검증
→ 실제 Python 함수 실행
→ 결과를 모델에게 전달
→ 최종 답변
```
모델이 만드는 것은 
```Python
{
	"name": "get_delivery_status",
	"arguments": {
	"order_id": "ORD-2026-0713"
	}
}
```
같은 **함수 실행 요청**이다. 
### 8. Function Call 구조
response.output에서 다음을 확인한다.
```Python
item.type
item.name
item.arguments
item.call_id

특히

item.arguments 는 JSON 문자열이므로 json.load(item.arguments)로 Python dict로 변환한다.
하지만 바로 함수에 넣으면 안된다.
```
```Python
arguments
→ JSON 파싱
→ Pydantic 검증
→ 권한/업무 규칙 확인
→ 함수 실행
순서로 처리해야 한다.
```
### 9. 안전한 Tool 실행
모델 출력은 **신뢰할 수 없는 외부 입력**처럼 취급한다.
사용하면 안되는 방식: 
```Python
eval(…)
globals()[tool_name]
```
대신 allowlist router를 사용한다.
```Python
TOOL_ROUTER = {
		"get_delivery_status": get_delivery_status
}
```
즉 등록된 함수만 실행 가능하게 만든다
Tool 실행 결과도 일정한 구조를 사용한다. 
성공:
```Python
{
	"ok": true,
	"status": "in_transit"
}
```
실패: 
```Python
{
	"ok": false,
	"error_code": "order_not_found",
	"retryable": false,
	"message": "해당 주문을 찾을 수 없습니다."
}
```
### 10. function_call_output
함수 실행 결과를 다시 모델에게 보내야 한다.
```Python
{
  "type": "function_call_output",
  "call_id": "...",
  "output": "..."
}
```
call_id는
```Python
모델의 function_call ↔ 애플리케이션의 function_call_output
```
을 연결한다.
전체 흐름:
```Python
사용자 질문
→ 모델
→ function_call
→ 함수 실행
→ function_call_output
→ 모델
→ 최종 자연어 답변
```
### 11. Tool Loop
한 번의 Tool Call로 끝나지 않을 수도 있다.
예:
주문 ID 검색
- 주문 상태 조회
- 배송사 조회
- 최종 답변
그래서 반복 횟수를 제한해야 한다.
- max_rounds
- timeout
- token 제한
- 비용 제한
- 동일 호출 반복 검사 
등의 종료 조건이 필요하다. 
### 12. 부작용 Tool
조회 기능과 실제 상태를 변경하는 Tool은 다르게 처리해야 한다.
부작용 Tool에는 다음이 중요하다
- Confirmation
- Permisson
- Idempotency
- Audit Log
특히 같은 요청이 여러 번 실행되는 것을 막기 위해 idempotency key를 사용한다.
### 13. 멀티모달 입력 
Responses API에서 텍스트뿐 아니라 이미지를 같이 넣을 수 있다.
input_text → 모델에게 분석 방법을 알려줌
input_image → 실제 시작 정보를 제공
이미지 전달방법:
- URL
- Base64 data URL
- File ID
이미지의 detail 수준도 설정할 수있다.
- low, high, original, auto
작은 글자나 문석 분석에서는 high 또는 original을 비교할 수있다.
### 14. 이미지 분석에서 관찰과 추론 
이미지에서는 보이는 것과 해석한 것을 분리해야 한다. 
읽을 수 없는 값은 확인 불가, null, unknown 등으로 처리하고 추측하지 않는다.
### 15. 멀티모달 Structured Output
이미지 결과도 Pydantic으로 구조화할 수있다. 
```JSON
{
  "merchant": "SPARTA CAFE",
  "date": null,
  "total": 9000,
  "currency": "KRW",
  "review_required": true
}
```
중요한 불확실성 필드:
```Plain Text
null
unknown
review_required
review_reason
evidence
```
evidence는 이미지에서 실제 읽은 내용을 기록해 결과 검토에 활용한다.
### 16. 구조 검증과 비지니스 검증
Pydantic이 성공했다고 결과 전체가 맞는 것은 아니다.
예:
```Plain Text
quantity = 2
unit_price = 4500

계산 결과 = 9000

그런데 모델이
total = 10000

이라고 읽었다면 Schema는 맞아도 내용 관계가 틀렸다
그래서

Pydantic 구조 검증
→ 숫자 계산
→ 비지니스 규칙 검증
을 따로 수행한다.
```
### 17. 비용과 Latency 기록
API를 사용할 떄 품질만 보지 않고 다음도 기록해야 한다.
- input_tokens
- output_tokens
- latency_ms
- request_id
- cost
특히 이미지의 detail 수준이 달라지면 
- 품질
- token
- latency
- 비용
도 함께 비교해야 한다.
가격은 코드에 직접 넣기보다 환경 변수나 설정 파일로 관리한다.

## 왜❓:
### 1. 왜 Developer Prompt와 User Prompt를 나눌까?
서비스의 규칙과 사용자의 실제 질문을 분리하기 위해서다. 
- Developer = 서비스 규칙
- User = 실제 요청
이렇게 해야 여러 요청에서도 동일한 정책을 유지할 수 있다.
### 2. 왜 Baseline이 필요할까?
처음 성능을 알아야 개선된 Prompt가 실제로 좋아졌는지 비교할 수 있기 때문이다
### 3. 왜 Few-shot을 사용할까?
모델에게 단순 설명뿐 아니라 “이 입력이면 → 이렇게 답해야 한다” 라는 실제 기준을 보여줄 수 있기 떄문이다.
### 4. 왜 JSON Schmea와 Pydantic을 사용할까?
자연어는 표현이 계속 달라질 수 있기 때문이다.
자연어
- 프로그램에서 처리 어려움
Structured Output
- 필드가 일정함
- 코드에서 사용하기 쉬움
### 5. 왜 Tool Arguments를 다시 검증할까?
모델이 만들어 준 값도 틀릴수 있기 때문이다.
모델 출력 ≠ 신뢰 가능한 내부 데이터 
따라서 JSON → Pydantic → 업무규칙 → 권한 순서로 확인해야 한다.
### 6. 왜 function_call_output을 모델에게 다시 보낼까?
python 함수가 반환하는 내부 데이터를 사용자가 이해하기 좋은 문장으로 바꾸기 위해서다. 
### 7. 왜 이미지에서 null을 사용할까?
읽을 수 없는 값을 억지로 채우면 실제 값처럼 보일 수 있기 때문이다. 
모름 → null 로 표현하면 downstream 코드에서도 쉽게 구분할 수 있다.
### 8. 왜 이미지 결과도 다시 검증할까?
이미지에서 숫자를 잘 읽어도 서로 관계가 맞는지는 별도 문제이기 때문이다. 
구조가 올바름 ≠ 계산 결과가 올바름
## 🧩 어려웠던 점
### 1. Response와 Tool Call의 관계
처음에는 모델이 Tool을 직접 실행한다고 생각하기 쉽다.
실제로는 
모델 → 이 함수를 이런 인자로 실행해 주세요
애플리케이션 → 실제 함수 실행
### 2. arguments와 실행 결과 구분
`item.arguments` 는 함수 실행 결과가 아니다.
arguments = 함수 실행에 필요한 입력값
function_call_output = 실제 함수 실행 결과
### 3. strict의 두 가지 의미
Pydantic strict와 OpenAI Structured Output의 strict가 헷갈릴 수 있다.
Pydantic strict → 자동 형 변환 제한
OpenAI strict → Schema에 맞는 출력 생성 강화
둘은 같은 설정이 아니다.
### 4. JSON / Schema / 사실성 구분
다음 세가지를 구분하는 것이 중요했다.
JSON 문법이 맞다 ≠ Schema ≠ 내용이 맞다
### 5. 이미지 관찰과 추론
이미지에 실제 보이는 내용과 모델이 해석한 내용을 구분해야 한다. 
- 보임 → 관찰
- 해석 → 추론
- 안보임 → 확인 불가
이 원칙이 멀티모달 작업에서 중요했다.
### 6. 구조 검증과 업무 검증
Pydantic 객체가 만들어졌다고 모든 작업이 끝난 것이 아니다.
Pydantic → 데이터 구조 검사
비지니스 로직 → 실제 관계와 규칙 검사
예를 들어 영수증에서는 수량 x 단가 와 총액을 다시 계산해야 한다. 
### 7. Tool Calling 전체 흐름 연결
처음에는 각각의 코드가 따로 보였지만 전체적으로 연결하면 다음 흐름이다.
```Plain Text
Tool Schema 정의
        ↓
모델이 Function Call 생성
        ↓
arguments 파싱
        ↓
Pydantic 검증
        ↓
Allowlist Router
        ↓
실제 Python 함수 실행
        ↓
function_call_output
        ↓
모델에게 결과 전달
        ↓
최종 사용자 답변

이 흐름을 하나로 연결해서 이해하는 것이 오늘 학습에서 가장 중요한 부분이었다. 
```

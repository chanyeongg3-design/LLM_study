# [프롬프트 입력 구성] 같은 질문·문서로 기본 지시와 상세 지시를 비교하기

📅 날짜: 2026-11-26 | 🏷️ 태그: #Python #딕셔너리 #프롬프트

## 1. 배경(WHY)

기본 지시와 상세 지시를 비교하는 실습에서, 지시문은 바꾸되 질문과 근거 문서는 같게 유지 해야 했다. `build_messages(casem explicit)`가 어떤 값을 받아서 어떤 메시지를 반환하는지 살펴봤다. 

## 2. 핵심 내용 및 구현 (What & How)

- `explicit`이 `False`면 `simple_instruction`, `True`면 `explicit_instruction`을 선택한다.
- 함수의 입력인 `case`에서 문자열 키 `question`과 `document`로 값을 꺼낸다.
- 반환값은 메시지 딕셔너리 두 개를 담은 리스트다. 첫 번째 `system` 메시지에 지시문을, 두 번째 `user`메시지에 질문과 문서의 JSON 문자열을 넣는다.
- `check_message_inputs(cases)`는 메시지 순서와 지시문이 맞는지 확인하고, 두 버전의 `user` 메시지가 같은지 검사한다.
#### 확인한 변수명과 키를 한 함수로 정리한 예시

```python
def build_messages(case, exlicit):
	instruction = explicit_instruction if explicit else simple_instruction
	model_input = {
	"question": case["question"],
	"documents": case["documents"],
	}
	return [
		{"role": "system", "content": instruction},
		{"role": "user", "content": json.dumps(model_input,
		ensure_ascii=False)},
	]
```

## 3. 트러블슈팅 / 시행착오

- 함수 안에 둔 `print()`의 출력이 보이지 않아 함수 정의와 실제 호출을 구분해 확인했다.
- 대문자 지시문 이름에서 `NameError`가 발생했다. `globals()`로 확인했을 때 대문자 이름 세 개는 모두 `False`, 소문자 `explicit_instruction`과 `simple_instruction`은 모두 `True`였다.
- `question`을 그래로 쓰거나 `case[question]`으로 접근했을 때도 `NameError`가 났다.
  자가 점검 코드의 `case["question"]`, `case["document"]`를 기준으로 키 접근을 확인했다.

## 4. 느낀 점 및 다음 할일 (Retrospective)

- 함수의 반환값을 따라가니 같은 입력으로 비교한다는 조건을 코드에서 어디서 검사하는지 확인할 수 있었다.

# [응답 검증] JSON 객체·스키마·인용 ID를 단계별로 확인하기

📅 날짜: 2026-11-26 | 🏷️ 태그: #JSON #응답검증 #테스트

## 1. 배경 (Why)

모델 응답을 검사하는 `inspect_response(raw, source_ids`의 플래그 세 개가 각각 무엇을 뜻하는지 살펴봤다. 준비된 테스트 응답인 `fixture_responses`에 검사 함수를 적용하고, 실제 결과를 `expected_checks`와 대조했다.

## 2. 핵심 내용 및 구현 (What & How)

- **`json_object`** · `json.loads(raw)`로 원문을 읽고 결과가 딕셔너리인지 검사한다.
- **`schema_ok`** · `status`, `answer`, `citations`의 필드와 값의 조건을 확인한다.
  `answered`에는 인용이 있어야 하고, `abstained`에서는 인용 목록이 비어 있어야 한다.
- **`citation_ids_ok`** · 인용 ID가 제공된 문서 ID 집합인 `source_ids`에 들어 있는지 검사한다.
- 공유한 실행 출력에서 **형식은 맞지만 경계 판단이 틀린 예**도 세 플래그가 모두 `True`였다.

코드에서 다룬 JSON 파싱과 상태별 인용 조건을 발췌했다. 두 블록 사이에는 필드·자료형 검사가 들어간다.

```python
try:
	response = json.loads(raw)
	
except json.JSONDecodeError:

	return result
	
if not isinstance(response, dict):

	return result
	
result["json_object"] = True

# 필드와 자료형 검사가 통과한 뒤 실행
if response["status"] == "answered" and not response["citations"]:
	return result
	
if response["status"] == "abstained" and response["citations]:
	return result
```

## 3. 트러블슈팅 / 시행착오

- `json.loads(raw, dict):`로 작성한 부분에서 JSON 읽기와 딕셔너리 타입 검사를 각각 어떻게 쓰는지 확인했다.
- `response["abstained]`를 리스트로 검사하다가 `KeyError: 'abstained`가 났다. 
  `abstained`는 `status`에 들어가는 값이고, 리스트로 검사할 필드는 `citations`다
- **없는 문서 ID를 인용한 예**에서 실제 검사값과 기대값이 달라 `AssertionError`가 발생했다. 이후 `cid in source_ids`가 무엇을 검사하는지 짚었다.

## 4. 느낀점 및 다음 할일 (Retrospective)

- 형식이 맞고 실제 문서 ID를 인용해도 숙박비 한도 같은 규정 판단은 틀릴 수 있다.

# [후속 조치 분기] 자동 검사와 사람의 의미 검토를 함께 사용하기

📅 날짜: 2026-11-26 | 🏷️ 태그: #조건문 #딕셔너리 #의미검토

## 1. 배경 (Why)

검사 결과를 받은 뒤 어떤 확인을 먼저 하고, 사람의 의미 검토에 따라 어떤 학습 조치를 남길지 정하는 코드를 살펴봤다.

## 2. 핵심 내용 및 구현 (What & How)

- `plan_learning_action(checks, review_kind, length_limited=False)`는 검사 결과, 사람이 선택한 검토 유형, 출력 길이 제한 여부를 받는다.
- `followup`은 **길이 제한 → 형식 실패 → 의미 검토** 순서로 우선 확인할 항목을 고른다.
- `learning_action`은 `review_kind`를 기준으로 선택했다. 테스트에는 형식이 틀려도 사람이 확인한 경계 오답에는 `boundary_pair`를 유지하는 조건이 있었다.
- 아래는 내가 올린 오류 기록에서 확인한 테스트의 기대값이다. 

```python
assert plan_learning_action(fenced_checks, "not_reviewed", True) == {
	"followup": "check_length",
	"learning_action": "read_first",
}
```

## 3. 트러블슈팅 / 시행착오

- `learning_action = learning_action[review_kind]`는 지역 변수에 값이 들어가기 전에 그 변수를 읽어서 `UndoundLocalError`가 발생했다.
- 매핑 키를 `"not_review"`로 적었지만 테스트는 `"not_reviewed"`를 전달해 `KeyError`가 발생했다. 입력 문자열과 딕셔너리 키가 정확히 일치해야 한다. 

## 4. 느낀 점 및 다음 할일 (Retrospective)

먼저 무엇을 확인할지 정하는 `followup`과, 사람의 검토 결과를 학습에 어떻게 반영할지 정하는 `learning_action`의 역할을 구분했다.

# [모델 생성] 생성 설정과 EOS 종료 조건 읽기

📅 날짜: 2026-11-26 | 🏷️ 태그: #GenerationConfig #토큰 #EOS

## 1. 배경 (Why)

기본 지시와 상세 지시를 반복해서 실행하는 코드에소 생성 설정이 무엇을 제어하는지, 생성 결과가 종료 토큰으로 끝났는지 어떻게 판단하는지 살펴봤다.

## 2. 핵심 내용 및 구현 (What & How)

- `for variant, explicit in …`에서 첫 번째 반복의 값은 `"simple`, `False`, 두 번째는 `"explicit, True`다. `variant`는 실험이름, `explicit`은 지시를 고르는 불리언이다.
- `do_sample=False`는 무작위 샘플링을 끄고, `repetition_penalty=1.1`은 이미 등장한 토큰의 반복을 억제하는 설정이다.
- `eos_token_id`는 생성을 끝내는 토큰 ID, `pad_token_id`는 길이를 맞추기 위한 패딩 토큰 ID다.
- `set(eos_ids or [])`는 EOS ID 목록을 집합으로 바꾸고, 값이 비어 있으면 빈 집합으로 처리한다.
- `inputs["input_ids"].shape[1]`은 `[배치 크기, 입력 시퀀스 길이]`에서 두 번째 축의 길이이며, 생성된 부분만 분리하는 기준이 된다. 

```python
ended_with_eos = bool(
	len(new_tokens) and new_tokens[-1].item() in eos_ids
)
```

## 3. 트러블슈팅 / 시행착오

`and`의 왼쪽은 **생성 토큰의 존재 여부**를 판단한다. 토큰이 있을 때만 오른쪽을 계산해 **마지막 토큰 ID**가 `eos_ids`에 있는지 검사한다. 새 토큰이 비어 있으면 마지막 원소에 접근하지 않고 `False`가 된다

## 4. 느낀 점 및 다음 할 일 (Retrospective)

입력 길이, 새로 생성한 토큰, 마지막 토큰의 ID를 각각 구분하니 종료 조건을 한 문장으로 설명할 수 있었다.

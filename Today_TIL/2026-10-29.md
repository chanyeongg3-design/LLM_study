# RAG 전체 학습 노트

RAG(Retrieval-Augmented Generation, 검색 증강 생성)는 **질문과 관련된 문서를 검색하고, 찾은 근거를 모델에 전달해 답변을 만드는 방식**이다. 
검색한 문서를 입력에 추가하며, 모델을 다시 학습시키지는 않는다.

## 1) RAG 이해와 아키텍처

- **필요성**: 최신 정보, 비공개 문서, 근거 없는 답변 문제를 보완한다.
- **Indexing**: 문서를 미리 처리해 검색할 수 있는 색인을 만든다.
- **Query**: 질문이 들어오면 검색하고, 근거를 모아 답변한다.
- **역색인**: 단어마다 해당 단어가 등장한 문서 ID를 연결한다.
- **2-Step RAG**: 검색 후 생성하는 기본 흐름이다.
- **방식 구분**: RAG는 근거를 찾는 방식, Long Context는 긴 입력을 처리하는 능력, CAG는 공통 입력의 계산 상태를 재사용하는 접근이다. 

| 구분    | 문서 준비 과정             | 질문 처리 과정            |
| ----- | -------------------- | ------------------- |
| 강의 용어 | Indexing             | Query               |
| 시작점   | 원본 문서                | 사용자 질문              |
| 주요 작업 | 로딩·정제·청킹·임베딩·색인 저장   | 검색·Context 구성·생성·검증 |
| 결과물   | 검색할 수 있게 준비된 데이터     | 근거에 기반한 답변 또는 보류    |
| 실행 시점 | 처음 준비하거나 문서·설정이 바뀔 때 | 질문이 들어올 때           |

## 2) 문서 로딩과 데이터 품질

- **문서 로딩**: TXT, HTML, PDF에서 본문을 추출한다. 파일 형식에 따라 추출 결과가 달라진다.
- **Document**: 본문인 page_content와 부가 정보인 metadata를 묶는다.
- **Metadata**: 제목·버전·적용 상태·출처 등을 저장해 필터링과 추적에 사용한다.
- **정제**: 공백, 반복되는 틀 문구, 중복, 빈 본문을 처리하되 금액·조건·부정 표현은 보존한다.
- **본문 해시**: 본문의 변경 여부를 확인한다. 상태만 바뀌면 본문 해시는 같을 수 있다.
- **JSONL**: 한 줄에 문서 하나를 저장하고, 오류가 발생한 행을 확인한다.


## 3) 청킹 전략

- **chunk**: 검색과 임베딩에 사용할 문서 조각이다.
- **Size-Overlap**: 조각 크기와 겹치는 범위다. 이동 간격은 size - overlap이다.
- **Fixed**: 정해진 문자 위치에서 나눈다.
- **Recursive**: 문장·공백 등의 경계를 우선 사용하고, 긴 부분을 더 작게 나눈다.
- **Token 기준**: 모델이 처리하는 토큰 단위로 길이를 측정한다. 문자 수와 토큰 수는 다르다. 
- **구조 기반**: 제목·절·표·목록의 관계를 유지하며 나눈다.
- **비교 기존**: 청크 수뿐 아니라 필요한 조건의 보존 여부와 저장량을 확인한다. 청크가 바뀌면 임베딩과 색인도 갱신한다. 


## 4) 임베딩과 Dense 검색 

- **임베딩**: 텍스트를 의미 비교에 사용할 숫자 벡터로 바꾼다.
- **Pooling**: 여러 토큰의 벡터를 하나로 모은다.
- **정규화**: 벡터 길이를 1로 맞춘다. 정규화된 벡터끼리는 내적이 코사인 유사도와 같다.
- **Dense 검색**: 질문 벡터와 청크 벡터의 유사도로 후보를 찾는다.
- **Tok-k·Threshold**: 반환할 최대 개수와 점수 하한을 정한다. 필요한 근거가 제외될 수도 있다.
- **모델 비교**: 문서·청크·질문·검색 조건을 고정하고 모델을 비교한다. 유사도 점수는 정답 확률이 아니다.

| 모델         | 하는 일                       | 출력     |
| ---------- | -------------------------- | ------ |
| **임베딩 모델** | 질문과 청크를 의미 비교가 가능한 형태로 바꾼다 | 숫자 벡터  |
| **생성 모델**  | 질문과 전달받은 근거를 읽고 답변을 작성한다   | 답변 텍스트 |
- 문서 청크의 벡터는 미리 만들어 둘 수 있고, 질문이 들어오면 질문 벡테를 만들고, 저장된 청크 벡터들과 비교한다.
- 이때 문서와 질문은 **같은 임베딩 모델의 규칙에 맞게 처리해야 한다.** 벡터 차원이 같더라도 서로 다른 모델의 벡터를 섞으면 같은 의미 공간에서 비교한다고 볼 수 없다. 
- 또한 임베딩 모델은 **실제로 입력한 문자열만** 처리한다. 메타데이터에 제목을 저장했다고 해서 제목이 임베딩에 자동 반영되지 않는다.
- **벡터는 근거를 찾기 위한 표현이고, 답변에 사용할 근거는 청크의 실제 본문이다**


## 5) Qdrant와 검색 조건

- **Point: id + vecotor + payload**로 구성하는 저장 단위다. Payload에는 본문과 메타데이터 등을 담는다.
- **Collection**: 같은 벡터 설정을 사용하는 Point 묶음이다.
- **Upsert**: ID가 없으면 추가하고, 있으면 갱신한다.
- **조회 구분**: retrieve는 ID 조회, query_points는 유사도 검색, scroll은 조건에 맞는 데이터 나열이다.
- **Filter**: 적용 상태·분류 등의 조건으로 검색 후보 범위를 제한한다.
- **갱신**: 새 청크를 등록하고 old_ids - new_ids에 해당하는 옛 청크를 제거한다.
- **ANN**: 일부 후보를 탐색하는 근사 최근접 이웃 검색이다. 전수 검색 재현율과 정답 문서 검색 재현율은 구분한다. 


## 6) 기본 RAG와 출처·보류

- **Context**: 모델이 답변할 때 참고하도록 실제로 전달하는 근거다.
- **중복 제거**: 같은 문서의 다른 근거가 사라지지 않도록 chunk_id를 기준으로 처리한다.
- **예산 관리**: 본문뿐 아니라 제목·출처 라벨도 입력 길이를 포함한다.
- **처리 흐름**: prepare에서 검색과 Context를 준비하고, invoke_model에서 생성하며, finish에서 응답을 검사한다.
- **Citation**: 이번 Context의 출처 라벨을 실제 청크와 원문 정보에 연결한다.
- 보류: 필요한 사실이 부족하거나 질문이 모호하면 부족한 항목을 구체적으로 안내한다.


## 7) 위 내용 반복: 검증 기준

- 검색 결과에 있어도 **Context 예산 때문에 빠질수 있다.**
- 출처 ID가 유효해도 **답변의 금액·단위·조건이 틀릴 수 있다.**
- JSON 형식 검사를 통과해도 **내용의 정확성까지 보장하지 않는다.**
- insufficient는 근거 부족, system_error는 통신 등의 오류, invalid_output은 응답 파싱·검사 실패다. 


## 8) 검색 개선

- **BM25**: 단어의 등장 빈도·희소성·문서 길이를 이용한다. 토큰화 방식에 영향을 받는다.
- **Hybrid Search**: BM25와 Dense 등 서로 다른 검색 방식의 후보를 함께 사용한다.
- **RRF**: 서로 다른 점수를 직접 더하지 않고, 각 검색기의 순위를 이용해 결합한다.
- **Re-ranking**: 질문과 후보 청크를 함께 읽어 관련성을 다시 평가한다. 후보에 없는 근거를 새로 찾지는 못한다.
- **Query Rewrite**: 검색에 맞게 질문 표현을 바꾼다.
- **Multi-Query**: 같은 정보 요구를 여러 표현으로 검색하고 청크를 합친다. 최종 답변에는 원질문을 사용한다. 


## 9) RAG 평가

- **Golden Dataset**: 질문·참고 답변·근거 문서·답변 가능 여부를 정리한 평가 자료다. 
- **dev·test**: 개발용 자료로 설정을 고르고, 최종 확인용 자료로 평가한다.
- **Hit@k**: 상위 검색 결과에 정답 문서가 하나라도 있는지 확인한다.
- **Recall@k**: 필요한 정답 문서 중 찾은 비율이다.
- **Faithfulness**: 답변의 주장을 Context가 뒷받침하는지 확인한다.
- **Answer Relevancy**: 답변이 질문에 적합한지 확인한다.
- **Context Precision-Recall**: 유용한 근거의 순위와 필요한 사실의 포함 여부를 평가한다.
- **개선 비교**: 조건을 고정하고 하나씩 바꾸며, 평균과 질문별 실패를 함께 확인한다. 


## 10) RAG 확장

- Parent-Child: 작은 청크로 검색하고, 연결된 더 넓은 원본을 답변 근거로 가져온다.
- Context Comprssion: 필요한 문장을 남겨 입력을 줄인다. 답을 바꾸는 조건이 빠지지 않아야 한다.
- Corrective-Agentic RAG: 검색 결과를 검토하고 재검색·답변·보류 등의 다음 동작을 정한다. 반복 방지와 종료 조건이 필요하다.
- GraphRAG: 개체와 관계를 이용한다. Local은 관련 개체 주변, Global은 커뮤니티 보고서 종합, DRIFT는 보고서와 후속 탐색을 활용한다.
- Multimodal RAG: 텍스트뿐 아니라 표·페이지 이미지도 근거로 다룬다.
- ColPail·Maxsim: 페이지를 여러 벡터로 표현하고, 질문 벡터별 최대 유사도를 합산해 페이지를 검색한다.

##  궁금증 - RAG 탐구 질문: 필요한 근거를 더 정확하게 찾으려면?

RAG의 기본 흐름을 공부하면서, LLM과 검색 시스템이 어떻게 역할을 나누는지 더 길이 이해하고 싶어졌다.

### 1. **LLM과 RAG는 어떻게 연결되는가?**
**Q1.** LLM이 외부·내부 문서를 참고할 때, 모델과 검색 도구, RAG 시스템은 각각 어떤 역할을 맡는가?

**A1.** 
LLM은 전달받은 질문과 자료를 읽고 답변을 생성한다. 문서를 검색하거나 파일을 여는 실제 작업은 연결된 프로그램과 도구가 수행한다.

RAG(Retrieval-Augmented Generation, 검색 증강 생성)는 필요한 정보를 검색하고, 그 결과를 LLM의 입력에 추가해 답변 근거로 사용하는 구조다. 

### 2. **검색 기술들은 어떻게 다른가?**
**Q2.**
BM25와 Dense 검색은 어떤 기준으로 근거를 찾는가? 

Hybrid Search와 RRF는 검색 결과를 어떻게 결합하는가? 검색용 Tok-k와 생성용 Top-p는 어떻게 다른가?

**A2.** 
각 기술은 검색 과정에서는 맡은 역할이 다르다. 

| 기술            | 역할과 기준                                            |
| ------------- | ------------------------------------------------- |
| BM25          | 질문과 본문에 등장한 단어를 비교한다.<br>단어 빈도·희소성·청크 길이 등을 반영한다. |
| Dense 검색      | 질문과 청크를 벡터로 표현하고 의미적 유사도를 비교한다.                   |
| Hybrid Search | 단어 기반 검색과 의미 기반 검색 등 서로 다른 검색 방식을 함께 사용한다.        |
| RRF           | 각 검색기의 결과를 원래 점수 대신 순위에 따라 결합한다.                  |
| 검색용 Tok-k     | 검색 결과로 반환할 최대 청크 수를 정한다.                          |
| 생성용 Tok-p     | 문장을 생성할 때 다음 토큰 후보를 누적 확률 기준으로 제한한다.              |
BM25는 정확한 표현 일치에 유용하지만 토큰화와 표현 차이의 영향을 받는다. Dense는 표현이 달라도 의미가 가까운 청크를 찾을 수 있지만, 주제만 비슷하고 답은 없는 청크를 선택할 수도 있다.

Hybrid Search는 이처럼 다른 판단을 함께 활용하는 접근이다. RRF는 그 결과를 합치는 방법 중 하나다.

**검색 점수가 높다는 것은 관련성이 높게 계산되었다는 뜻이며, 답이 존재하거나 정확하다는 보장은 아니다.** **Tok-p는 문서 검색이 아닌 생성 단계의 설정이다.**

### 3. 질문을 바꾸면 검색이 어떻게 달라지는가?

**Q3.** 
Query Rewrite, Multi-Query, 질문 분해는 각각 무엇을 바꾸며, 어떤 상황에서 필요한가? 

질문의 원래 의도를 유지하면서 검색을 개선하려면 무엇을 확인해야 하는가?

**A3.**
세 방법 모두 질문을 검색에 활용하는 방식을 조정하지만 목적이 다르다.

| 방법            | 만드는것                 | 필요한 상황                        |
| ------------- | -------------------- | ----------------------------- |
| Query Rewrite | 검색에 적합하게 다듬은 질의      | 표현이 불명확하거나 대화의 앞 내용을 보완해야 할 때 |
| Multi-Query   | 같은 정보 요구를 표현한 여러 질의  | 하나의 표현으로 관련 근거를 놓칠 때          |
| 질문 분해         | 각각 다른 부분을 담당하는 하위 질문 | 여러 정보나 문서의 근거를 함께 모아야 할 때     |
여기서 출력은 **최종 답변이 아니라 검색에 사용할 질의**다. 검색 질의는 사람이 정한 규칙이나 LLM을 이용해 만들 수 있다.

질의를 바꿀 때는 원래 질문의 대상·기간·조건·부정 표현을 유지해야 한다. 확인되지 않은 금액이나 추측한 답을 질의에 추가하면, 그 추측에 맞는 자료만 찾게 될 수 있다.

Multi-Query에서는 여러 질의가 찾은 결과를 chunk_id로 중복 제거한다. 질문 분해에서는 각 하위 질문에 필요한 근거를 모으고, 최종적으로 원질문의 요구를 충족하는지 확인한다.

**검색 표현을 바꾸더라도 사용자가 알고 싶은 내용은 유지해야 한다.**

### 4) 청크와 벡터를 어떻게 설계해야 하는가?

**Q4.**
청킹 방식, 임베딩 모델, 메타데이터 필터, 재정령, Context 구성을 어떻게 조합해야 답에 필요한 근거를 더 정확하고 빠짐없이 가져올 수 있는가? 

개선 효과는 어떤 지표와 실험으로 확인해야 하는가?

**A4.** 
정확한 검색은 벡터 유사도만으로 결정되지 않는다. 

**원문에서 필요한 정보를 보존하고, 검색한 근거를 모델에게 전달하는 전체 과정**을 설계해야 한다.

| 단계         | 설계·확인할 내용                                       |
| ---------- | ----------------------------------------------- |
| 청킹         | 문장·제목·표의 구조를 고려하고, 규칙과 예외·금액과 단위가 끊기지 않는지 확인한다. |
| 임베딩        | 질문과 문서에 호환되는 모델·입력 규칙을 사용한다. 입력 잘림도 확인한다.       |
| 저장         | 각 벡터가 그 벡터를 만든 청크의 본문·ID·출처와 정확히 연결되게 한다        |
| 필터         | 적용 상태와 범주 등을 제한하되, 필요한 근거를 잘못 제외하지 않는지 확인한다.    |
| 후보 검색      | 필요한 근거에 후보가 들어오는지 보고, 필요하면 Hybrid나 질의 변형을 시험한다. |
| 재정렬        | 검색된 후보를 질문과 함께 평가해 순서를 다시 정한다.                  |
| Context 구성 | 필요한 근거와 조건을 예산 안에 담고 출처를 연결한다.                  |
작은 청크로 잘 찾더라도 답변에 필요한 조건이 끊길 수 있다. 이때 Parent-Child 방식으로 더 넓은 원문을 가져오거나 인접 구간을 함께 전달하는 방법을 검토할 수 있다.

또한 처음 검색할 후보 수와 최종적으로 전달할 청크 수는 구분해야 한다. 재정렬은 후보에 없는 근거를 되살릴 수 없고, 검색한 청크도 Context 예산 때문에 빠질 수 있기 때문이다. 

개선효과는 다음과 같이 나눠 확인한다. 

| 평가 항목          | 확인하는 것                      |
| -------------- | --------------------------- |
| Hit@k          | 정답 근거를 하나라도 찾았는가            |
| Recall@k       | 필요한 정답 근거 중 얼마나 찾았는가        |
| Precision@k    | 선택한 결과 중 관련 근거가 얼마나 되는가     |
| Context의 근거 충족 | 답에 필요한 사실이 실제 입력에 모두 포함되었는가 |
| 답변 품질          | 질문에 답하고 원문의 의미·조건을 유지했는가    |
| 실행 비용          | 처리 시간·호출량·자원이 얼마나 늘었는가      |
문서 기준과 청크 기준의 평가는 구분해야 한다. 올바른 문서를 찾았어도 답이 담긴 청크가 빠질 수 있다.

실험에서는 질문의 정답 근거를 고정하고, 청킹·검색 방식·재정렬 등을 하나씩 바꾼다. 개발용 자료로 설정을 선택하고 최종 확인용 자료에서 평가하며, 평균뿐 아니라 개선·악화한 질문을 함께 살핀다.

최적의 조합은 자료와 질문에 따라 달라지므로, 실제 실패를 관찰하고 같은 기준으로 비교해서 선택한다. 

### 5) RAG를 어디까지 응용할 수 있는가?

**Q5.** 
문서 질의응답을 넘어 여러 자료의 비교·분석, 개인 학습, 업무 지원에 어떻게 활용할 수 있는가?

**A5.** 
RAG는 자료에서 근거를 찾아 수행하는 작업에 활용할 수 있다. 

검색한 뒤 무엇을 하도록 설계하느냐에 따라 결과물이 달라진다.

| 응용 분야          | 활용 방식                          |
| -------------- | ------------------------------ |
| 문서 질의응답        | 관련 근거를 찾아 출처와 함께 답한다.          |
| 여러 문서 비교       | 같은 항목의 근거를 모아 공통점·차이·누락을 정리한다  |
| 개인 학습          | 강의자료와 학습 기록을 찾아 설명·복습 자료를 구성한다 |
| 보고서 작성 지원      | 주제별 근거를 수집하고 인용 가능한 초안을 만든다    |
| 업무 지원          | 규정·메뉴얼과 업무 시스템의 조회 결과를 연결한다    |
| GraphRAG       | 여러 문서에 흩어진 개체와 관계를 따라 근거를 모은다  |
| Multimodal RAG | 텍스트와 함께 표·페이지 이미지 등의 근거를 활용한다. |
이러한 작업에서도 검색과 후속 거리를 구분해야 한다. 비교에는 항목 정렬이, 계산에는 계산 도구가, 실제 업무 실행에는 별도의 실행 도구와 권한 처리가 필요하다.

**RAG는 필요한 근거를 공급하는 역할을 맡고, 그 근거를 이용한 분석·계산·실행은 다른 처리와 결합해 수행한다.**

### **탐구 목표**

RAG의 기술 이름을 아는 데서 나아가, 각 기술이 해결하는 문제와 한계를 이해하고, 실제 근거와 평가 결과로 설계 선택을 설명할 수 있게 되는 것이다.

이를 위해 한 질문에 대해 **원문 → 검색 후보 → 최종 Context → 답변**을 따라가며, 필요한 정보가 처음 빠지거나 잘못 해석된 위치를 기록한다.

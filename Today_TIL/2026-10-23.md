# 1. 이번 프로젝트를 진행하면서

이번에는 기업 개발팀의 개발환경 설정과 장애 문의를 지원하는 AI 챗봇 DevDesk 프롬프트 엔지니어링 과제를 진행했다.

처음에는 사내 문서를 참고해 사용자의 질문에 답변하는 챗봇이라고 생각했다. 하지만 코드를 분석하면서 단순히 답변을 생성하는 것뿐 아니라 **답변의 근거를 확인하고, 잘못된 응답을 검증하며, 오류가 발생했을 때 처리하는 과정**까지 필요하다는 것을 알게 되었다.

특히 AI가 생성한 답변을 실제 기업 업무에서 어디까지 신뢰할 수 있을지 고민하게 되었다.

# 2. 프로젝트의 전체적인 흐름 

```text
[사용자 질문]
      ↓
[Policy + 사내 문서]
      ↓
[LLM API 호출]
      ↓
[필요 시 티켓 조회]
      ↓
[AI 답변 생성]
      ↓
[JSON Schema + 출처 검증]
      ↓
[오류 시 수정 요청 / Fallback]
      ↓
[토큰 사용량 및 비용 기록]
      ↓
[최종 결과 반환]
```

이 프로젝트는 개발자가 Python 버전이나 환경 설정 방법을 문의하거나, 기존 장애 티켓의 상태를 확인할 때 사용할 수 있따.

전체 실행 과정은 run_pipeline( )이 관리하며, 각 함수가 정책 생성, 도구 호출, 답변 검증, 오류 처리 등의 역할을 나누어 수행한다. 

# 3. 과제를 하면서 배운 점 

### JSON Schema와 답변 검증

처음에는 JSON Schema를 통과하면 AI의 답변도 정확하다고 생각했다.

하지만 validate_answer( )를 분석하면서 **데이터 형식을 검사하는 것과 답변 내용을 정확성을 검사하는 것은 다르다**는 점을 알게 되었다.

Draft202012Validator로 JSON 구조를 확인하고, any( ), set( ), .strip( ) 등을 사용해 존재하지 않는 출처나 중복 출처, 빈 답변을 검사한다는 점이 흥미로웠다.

### 직접 작성한 Policy Prompt

Policy에는 역할, 업무 범위, 근거, 비밀정보, 담당자 확인, 출력 형식을 작성했다.

그래서 사내 문서와 티켓을 근거로 답변하고, 정보가 부족하면 추측하지 않으며, 필요한 경우 담당자 확인을 안내하도록 작성했다.

이후 Policy를 검토하면서 JSON 출력 조건과 근거 부족 시 처리 기준을 더 구체적으로 작성할 필요가 있다는 점도 배웠다. 

### Tool Calling과 Retry

tool_roundtrip( )을 통해 AI가 직접 티켓을 조회하는 것이 아니라, 도구 사용을 요청하고 Python 프로그램이 실제 조회를 수행한다는 구조를 이해했다. 

또한 call_with_retry( )를 공부하면서 두 개념의 차이를 알게 되었다.
- Retry: API 전송에 실패했을 때 다시 요청
- Repair: AI 답변이 검증 규칙을 위반했을 때 수정 요청

오류가 발생했다고 무조건 다시 실행하는 것이 아니라, 오류의 종류에 따라 처리 방법을 다르게 설계해야 한다는 것을 배웠다.

### 4. 고민했던 점과 앞으로 궁금한 것

이번 과제에서 가장 고민했던 부분은 AI의 답변을 어떻게 검증할 것인지였다.

현재 코드는 출처 ID가 존재하는지 확인할 수 있지만, 해당 문서의 내용을 AI가 정확하게 해석했는지까지 보장하지는 않는다.

또한 baseline과 reasoning 프롬프트를 비교하면서 지침을 추가하는 것이 항상 좋은 결과로 이어지는지도 궁금해졌다.

앞으로 동일한 질문을 대상으로 답변, 정확성, 출처 일치 여부, 토큰 비용 등을 비교해 보고 싶다.

그리고 사내 문서가 많아지는 경우 모든 문서를 프롬프트에 포함하기보다, 이전에 공부한 RAG의 청킹, 임베딩, 벡터 검색을 활용하면 더 효율적으로 처리할 수 있을지도 알아보고 싶다. 

### 5. 오늘의 회고

이번 과자를 진행하며 프롬프트 엔지니어링은 단순히 AI에게 질문을 잘 작성하는 기술이 아니라는 것을 느꼈다.

AI가 어떤 근거로 답변하고, 어떤 상황에서 답변을 제한해야 하며, 오류가 발생했을 때 어떻게 처리할지까지 설계하는 과정이라는 점이 인상 깊었다.

아직 실제 테스트로 확인해야 할 부분이 남아 있지만, 이번 과제를 통해 **LLM의 답변 생성 과정뿐 아니라 전체 시스템의 흐름을 이해하는 것**이 중요하다라는 것을 배웠다.

```python
if variant == "reasoning"

	답변을 작성하기 전에 확인된 사실과

	질문의 상황을 파악하고 관련 근거를 확인한다.
	근거의 적용 조건과 제약을 확인하고

	"""
	
	# 사내 문서를 doc_id 기준으로 정렬하고 JSON 문자열로 변환
	corpus = json.dumps(
	sorted(documents, key=lambda item: item["doc_id"]),
	ensure_ascii=False,    # 한글 그대로 유지
	sort_keys=True         # JSON의 키 순서 일정하게 정렬
	)

		+ "\n<reference_documents>"

```

배운 점: AI에게 단순히 답변을 요청하는 것이 아니라, 업무 범위와 근거 사용 규칙을 명확하게 정의해야 한다는 것을 배웠다. 또한 baseline과 reasoning의 차이가 추가 검토 지침에 있다는 점을 이해했다. 

### 2. Validation -- AI 답변 검증


```python
def validate_answer(raw, known_ids):
	
	# JSON 문자열을 Python 딕셔너리로 변환
	answer = json.loads(raw)
	
	# AI 응답이 지정된 JSON Schema를 따르는지 검사
	Draft202012Validator(
		
		
		answer_format()["format"]["schmea"]).validate(answer)
		
		# 스키마 검사 이외의 추가 검증 조건
		rules = [
			
			# 빈 문자열 또는 공백으로만 된 답변인지 검사 
			(not answer["answer"].strip(), "blank answer"),
			
			# 실제 존재하지 않는 문서 ID가 포함됐는지 검사 
			(
			any(
			source_id not in known_ids
			for source_id in answer["source_ids"]
			),
			"unknown source_id"
		),
		
		# 근거가 없는데 담당자 확인도 불필요한 경우 
		(
			len(answer["source_ids"])
			!= len(set(answer["source_ids"])),
			"duplicate source_id"
		),
		
		(
			not answer["source_ids"]
			and answer["nees)human"] is False,
			"unsupported answer requires human"
		)
	]
	
	# 검증 조건을 하나씩 확인
	for invalid, message in rules:
		if invalid:
		riase ValueError(message)
	
	# 모든 검사를 통과하면 답변 변환 
	return answer
```

배운 점: JSON Schema는 자료형과 구조를 확인하고, 추가 검증 로직은 업무 규칙을 확인한다는 차이를 배웠다. 특히 any( ), set( ), strip( )이 실제로 데이터를 검증하는데 어떻게 사용되는지 이해했다.

```python
# AI 응답에서 도구 호출 요청만 추출
calls = [
	item
	for item in output
	if item.get("type") == "function_call"
]

# 도구 호출 요청이 없으면 현재 응답 반환
if not calls:
	return request, response

# 각 도구 호출 처리 
for call in calls:
	
	# Python에서 실제 티켓 조회 함수 실행
	result = execute_tool(
		call.get("name"),           # 호출할 도구 이름
		call.get("arguments"),      # AI가 전달한 인수
		tickets                     # 기존 티켓 데이터 
	)
	
	# 도구 실행 결과를 AI 요청에 추가 
	request["input"].append({
		"type": "function_call_output",
		
		# 요청과 결과를 연결하는 고유 식별자
		"call_id": call["call_id"],
		
		# Python 데이터를 JSON 문자열로 변환 
		"output": json.dumps(result, ensure_ascii=False)
	})
```

배운 점: AI가 직접 Python 함수를 실행하는 것이 아니라, 도구 호출을 요청하면 프로그램이 실행하고 결과를 다시 AI에게 전달하는 구조를 이해했다.

### 4. Retry -- API 오류 발생 시 재시도
```python

# 최대 3번 API 호출 시도
for attempt in range(1, 4):
	
	# API 호출 시작 시간 측정
	started = time.perf_counter()
	
	try:
		# 실제 API 요청
		response = send(request)
		
	except support.TransportError as error:
		
		# 발생한 HTTP 상태 코드 확인
		status = error.status_code
		
		# 재시도가 가능한 오류인지 판단
		retryable = (
			status is None
			or status in {408, 409, 429}
			or (
				isinstance(status, int)
				and 500 <= status <= 599
			)
		)
		
		# 재시도 대상이고 아직 3회 미만일 떄 
		retry_now = retryable and attempt < 3
		
		# 재시도가 불가능한 실패 반환
		if not retry_now:
			return None
	
			# 다음 요청까지 대기할 시간 계산
			delay = support.delay_for(attempt)
			
			# 일정 시간 대기후 다시 시도
			sleep(delay)
	else:
		# 전송 과정에서 예외가 없다면 응답 반환
		return response
	
	
```

배운 점: 모든 오류가 무조건 재시도하는 것이 아니라, HTTP 상태 코드를 확인하여 재시도 가능여부를 판단해야 한다는 점을 배웠다. 특히 API 전송 오류를 처리하는 Retry와 잘못된 AI 답변을 수정하는 Repair의 차이를 이해했다. 


### 5. Pipeline -- 전체 실행 흐름 연결

```python

# 정책 프롬프트 및 캐시 설정 생성
settings = cache_settings(documents, variant)

# AI API에 전달할 기본 요청 생성
request = support.base_request(
	settings["instructions"],
	question,
	variant
)

# 요청에 정책과 캐시 정보 추가
request.update(settings)
# AI 응답의 JSON 출력 형식 지정
request["text"] = answer_format()
# 티켓 조회 도구 등록
request["tools"] = [tool_schema()]
# 질문과 선택적 이미지 입력 구성
request["input"][0]["content"] = image_content(
question, image_path
)

# 필요하면 도구를 호출하며 AI 응답 생성
final_request, response = tool_roundtrip(
	reliable_send, request, tickets, events
)
# 응답 검증 및 필요한 경우 수정 처리 
result = finish_answer(
	reliable_send,
	final_request,
	response,
	{document["doc_id"] for document in documents},
	events
)
# 최종 답변과 실행 정보 반환 
return result
```

배운 점: run_pipeline( )이 모든 기능을 직접 구현하는 것이 아니라,, 각 함수를 순서대로 호출해 전체 시스템을 동작시킨다는 점을 이해했다. 함수를 역학별로 분리하면 코드의 실행 흐름을 파악하고 문제를 해결하기 쉬워진다는 것도 알게 되었다. 

1. `build_instructions( )` : 직접 작성한 Policy와 프롬프트 설계 과정
2. `validate_answer( )` : AI 답변의 신뢰성과 검증 로직 학습
3. `run_pipeline( )` : 프로젝트 전체 실행 흐름 이해
4. `tool_roundtrip( )` : LLM과 외부 도구의 연결 방식
5. `call_with_retry( )` : 실제 서비스의 장애 대응 방시

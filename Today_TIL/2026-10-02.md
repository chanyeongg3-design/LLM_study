# 2. 핵심 개념 정리

## 2-1. RUN_LIVE

정의: 실제 API 호출을 실행할지 말지를 결정하기 위해 만든 Boolean 변수다.

```
RUN_LIVE = True 
→ 실제 API 호출

RUN_LIVE = False
→ 실제 API 호출 안함
```

쉽게 말하면 API 호출의 전원 스위치다. 

### 왜 필요한가? 
- 실습 중 코드를 여러 번 실행하면 API 요청이 반복될 수 있다.
  실제 요청 여부를 제어하기 위해 사용한다. 
### 어디에 쓰이는가? 
- LLM API 실습
- 테스트 코드
- 개발 환경
- API 비용 제어
- 실제 호출 / 로컬 테스트 분리 

### 어떤 역할을 하는가?
- 실제 LLM 요청이 실행되는 조건을 제어한다. 

## 2-2. os.getenv( )

정의: 운영체제나 실행 환경에 저장된 환경변수(Environment Variable) 값을 가져오는 함수다. 

```
api_key = os.getenv("OPENAI_API_KEY")
```

쉽게 말하면 코드에 직접 적지 않고 밖에 저장해 둔 값을 꺼내오는 함수다. 

### 왜 필요한가? 
- API Key와 같은 비밀값을 코드에 직접 작성하지 않기 위해 사용한다.

``` 
좋지 않은 방식
api_key = : "실제 API KEY"
```

대신: 

```
api_key = os.getenv("OPENAI_API_KEY")
```

처럼 가져올 수 있다.

### LLM 프로젝트에서의 역할
- LLM API 인증 정보를 안전하게 불러오는 역할을 한다. 

## 2-3. getpass( )

정의: 사용자로부터 값을 입력받되 입력 내용을 화면에 그대로 표시하지 않는 함수이다.

```
from getpass import getpass

api_key = getpass("API 키: ")
```

쉽게 말하면 비밀번호 입력창처럼 입력 내용을 숨겨서 받는 함수이다.

### 왜 필요한가?
- API Key 같은 민감한 값을 화면에 그대로 노출하지 않기 위해 사용한다. 

```
api_key = os.getenv("OPENAI_API_KEY") or getpass("API 키: ")
```

의미는: 

환경변수에 API Key가 있는가? 

있으면 → 그대로 사용
없으면 → getpass( )로 직접 입력

## 2-4. ask( ) 함수

실습에서 LLM API 호출을 반복해서 사용하기 위해 만든 핵심 함수이다. 

```python
def ask(prompt, instructions="친절하고 정확하게 답하세요."):

	# 안전장치: RUN_LIVE 플래그가 꺼져 있으면 실제 API 호출을 막는다.
	# 노트북을 실수로 실행해도 요금이 청구되지 않도록 하기 위한 장치
    if not RUN_LIVE:
        raise RuntimeError(
            "실제 API 호출은 RUN_LIVE=True로 바꾼 후 실행하세요."
        )
	
	# Responses API로 모델에 요청을 보낸다.
	# model: 사용할 모델 이름
	# instructions: 모델의 역할/말투를 정하는 시스템 지침
	# input: 사용자가 실제로 묻는 내용 
    response = client.responses.create(
        model=MODEL,
        instructions=instructions,
        input=prompt
    )

	# 응답 검증: 정상완료되지 않았거나 
	# 출력 텍스트가 비어 있거나 공백뿬이면 오류로 처리한다.
    if response.status != "completed" or not response.output_text.strip():
        raise RuntimeError(
            "완료된 텍스트 응답이 없습니다. 응답 상태를 확인하세요."
        )

	# 검증을 통과한 경우, 모델이 생성한 최종 텍스트만 반환한다. 
    return response.output_text
```

역할

```
질문 받기
↓
LLM API 호출
↓
응답 상태 확인
↓
텍스트 반환 
```

핵심부분:
- client.responses.create(...) → 실제 모델 요청을 보낸다.
- model=MODEL → 사용할 모델을 지정한다. 
- instructions=instructions → 모델이 따라야 하는 행동 규칙을 넣는다. 
- input=prompt → 이번 요청에서 실제로 처리할 질문이나 데이터를 넣는다.
- return response.output_text → 최종 모델 답변 문자열을 반환한다. 

## 2-5. instructions

정의: 모델에게 **어떤 역할을 하고 어떤 규칙을 따라야 하는지** 알려주는 고정 지시다.

쉽게말하면 instructions는 모델에게 주는 행동 규칙이다.

```text
instructions
→ 어떻게 행동할 것인가?

input
→ 이번에 무엇을 처리할 것인가?
```

### 왜 분리하는가?

고정된 규칙과 매번 변하는 데이터를 분리하면 코드와 프롬프트의 역할이 명확해진다. 

```text
[고정 규칙]
instructions
      ↓
     LLM
      ↑
[이번 질문]
input
```

정의: 문자열 안에 변수 값을 넣을 수 있는 Python 문법이다.

**역할**

```text
고정 프롬프트

```

## 2-7. Basic / Rule / Few-shot Prompt

### Basic Prompt: 간단한 요청만 주는 방식
- 장점은 간단하지만, 애매한 상황에서는 모델이 원하는 기준과 다르게 판단할 수 있다.

### Rule Prompt: 모델이 판단할 명확한 규칙을 적어준다. 

### 왜 필요한가?
- 하나의 문의에 여러 내용이 포함될 경우 모델의 판단 기준을 명확히 하기 위해서이다. 

### Few-shot Prompt: 규칙과 함께 실제 입력/출력 예시를 몇 개 제공하는 방식이다.

쉽게 말하면: "이런 문제가 들어오면 이런 식으로 답해" 라고 예제를 보여주는 방식이다.

주의: Few-shot은 모델을 다시 학습시키는 것이 아니다 

실습에서는 Basic Prompt보다 규칙과 Few-shot을 추가했을 때 복합 문의의 분류가 원하는 업무 규칙과 맞는지 비교했다. 

## 2-8. JSON과 `json.loads()`

```text
JSON 문자열
       ↓
json.loads()
       ↓
Python 자료형
```

단, 항상 `dict`가 되는 것은 아니다.

|JSON|Python|
|---|---|
|`{}`|`dict`|
|`[]`|`list`|
|`null`|`None`|
|`true`|`True`|
|`false`|`False`|
따라서 정확한 설명은: json.loads( )는 JSON 문자열을 알맞는 Python 자료형으로 변환한다. 

## 2-9. format_rate

정의: 모델이 우리가 요구한 출력 형식을 제대로 지킨 비율이다.

예를 들어 허용 출력이:

```python
LABELS = ["배송", "반품", "결제", "기타"]
```

라면:

```text
결제
```

는 성공이다.

하지만:

```text
이 문의는 결제입니다.
```

는 내용은 맞을 수 있어도 라벨 하나만 출력하라는 형식은 지키지 않았다.

```
format_ok = prediction in LABELS
```

로 확인한다.

구조는 다음과 같다. 

```text
DEV_ROWS
   ↓

   ↓

   ↓

   ↓
format 검사
   ↓
accuracy 계산

```

반환값:

```python
{
    "accuracy": ...,

}
```

그리고 각 문제별 결과도 함께 저장한다.

def save_results(path, rows):

## 2-13. FAQ 기반 답변

문의에 그냥 자유롭게 답하게 하지 않고 제공된 FAQ 내용만 근거로 답변하도록 하는 방식을 실습했다.

예:

```python
FAQ_BY_CATEGORY = {
    "배송": "...",
    "반품": "...",
    "결제": "...",
    "기타": "..."
}
```

정책:

```text
제공된 FAQ만 근거로 답하세요.
FAQ에 답이 없으면
"자료에서 확인할 수 없습니다."
```

라고 지시한다.

**역할**

LLM이 없는 정보를 지어내는 것을 줄이기 위한 간단한 근거 기반 답변 구조다.
이 실습 자체는 검색 시스템이나 RAG 구현이 아니라, 필요한 자료를 직접 프롬프트에 넣는 방식이다. 

마지막으로 앞에 배운 기능들을 연결했다.

```python
def reply(question):

	# 1. 사용자의 질문을 분류
	# FINAL_PROMPT에 정의된 규칙에 따라
	# "배송", "결제", '기타' 중 하나의 라벨을 받는다.
    label = classify(question, FINAL_PROMPT)
	
	# 2. 분류 결과가 우리가 준비한 FAQ 카테고리에 없는 값인지 확인
	# 모델이 "환불 문의" 처럼 예상하지 못한 값을 반환한 경우
    if label not in FAQ_BY_CATEGORY:
        ...
	
	# 3. 분류된 라벨에 맞는 FQA 자료를 가져옴
	# 예: label == '반품' 이면 반품 관련 FAQ 문자열을 가져옴
    faq = FAQ_BY_CATEGORY[label]
	
	# 4. 사용자의 질문과 선택된 FAQ를 LLM에 전달해 답변을 생성
	# FAQ 내용을 근거로 답하도록 하는 단계
    answer = answer_faq(question, faq)
	
	# 4. 최종 결과를 python dict 형태로 반환한다. 
    return {
	    "question": question,   # 사용자가 입력한 원래 질문
        "category": label,      # 분류된 카테고리
        "answer": answer        # FAQ를 바탕으로 생성한 최종 답변 
    }
```

**쉽게 말하면**

```text
사용자 질문
     ↓
문의 분류
     ↓
카테고리 결정
     ↓
해당 FAQ 선택
     ↓
FAQ를 근거로 답변
     ↓
결과 반환
```

하나의 LLM 호출로 모든 것을 처리하는 것이 아니라 Python 코드가 LLM 호출 여러 개를 연결한다는 것이 핵심이다. 

# 개념 간 차이

#### **instructions vs input**

| 개념           | 역할         | 예                |
| ------------ | ---------- | ---------------- |
| instructions | 모델 행동 규칙   | 사실만 답하기, 두 문장 이내 |
| input        | 실제 처리할 데이터 | 사용자 질문, FAQ 자료   |
#### **Raw vs Rarsed Data**

| 상태          | 의미                      |
| ----------- | ----------------------- |
| raw         | 가공하지 않은 모델 원본 응답        |
| parsed data | 프로그램에서 사용할 수 있게 변환된 데이터 |
#### **Basic vs Rule vs Few-shot**

| 방식       | 특징         | 사용 상황            |
| -------- | ---------- | ---------------- |
| Basic    | 간단한 지시만 제공 | 기준이 단순할 때        |
| Rule     | 판단 규칙을 명시  | 업무 규칙이 있을 때      |
| Few-shot | 예시까지 제공    | 경계 사례를 보여주고 싶을 때 |
#### **Accuracy vs Format Rate**

| 지표          | 확인하는 것          |
| ----------- | --------------- |
| Accuracy    | 정답을 맞혔는가        |
| Format Rate | 요구한 출력 형태를 지켰는가 |

#### **json.loads( ) vs parse_order( )**

| 함수             | 역할                       |
| -------------- | ------------------------ |
| json.loads( )  | JSON 문법을 Python 자료형으로 변환 |
| parse_order( ) | 변환 + 구조 + 값까지 검증         |

# 5. 실제 LLM 프로젝트에서는 어떻게 사용되는가? 

| 단계  | 실제 프로젝트 구성        | 이번 실습                    |
| --- | ----------------- | ------------------------ |
| 1   | 사용자 입력            | 문의 문장                    |
| 2   | Prompt 구성         | f-string                 |
| 3   | 시스템 정책            | instructions             |
| 4   | 모델 호출             | responses.create( )      |
| 5   | 원본 응답             | raw                      |
| 6   | Output Parsing    | .strip( ), json.loads( ) |
| 7   | Validation        | parse_order( )           |
| 8   | Routing           | classify( )              |
| 9   | Knowledge 선택      | FAQ_BY_CATEGORY[label]   |
| 10  | Answer Generation | answer_faq( )            |
| 11  | 평가                | evaluate( )              |
| 12  | 로그 저장             | CSV / JSON               |

## 6. 같이 알아두면 좋은 관련 개념

- **Environment Variable**  
    코드 밖에 설정값이나 비밀정보를 저장하는 방식
    
- **API Key**  
    API 사용자를 인증하기 위한 비밀 키
    
- **Prompt Engineering**  
    모델이 원하는 방식으로 동작하도록 입력과 규칙을 설계하는 것
    
- **Zero-shot**  
    예시 없이 지시만 주는 방식
    
- **Few-shot**  
    프롬프트 안에 몇 개의 예시를 제공하는 방식
    
- **Parsing**  
    데이터를 프로그램에서 사용 가능한 구조로 해석하는 것
    
- **Validation**  
    데이터 구조와 값이 조건에 맞는지 확인하는 것
    
- **JSON**  
    시스템 간 데이터를 전달할 때 자주 사용하는 데이터 표현 형식
    
- **Routing**  
    입력에 따라 다음 처리 경로를 선택하는 것
    
- **Grounding**  
    주어진 자료를 근거로 답하게 하는 방식
    
- **RAG**  
    관련 문서를 검색해 LLM에 함께 제공하는 구조  
    이번 실습에서는 검색까지 구현하지 않고 FAQ를 직접 넣었다.
    
- **Structured Output**  
    모델 출력을 일정한 데이터 구조로 받는 방식  
    이번 실습은 JSON 문자열을 요청한 뒤 Python에서 검증하는 방식이다.

## 8. 내가 설명할 수 있어야 하는 질문 + 정답

1. **`instructions`와 `input`은 왜 분리하는가?**  

    `instructions`는 모델이 따라야 할 **고정 규칙**이고, `input`은 매번 바뀌는 **실제 질문이나 자료**입니다. 둘을 분리하면 역할이 명확해지고, 같은 규칙을 여러 입력에 재사용하기 쉽습니다.
    
2. **`raw` 응답과 `json.loads(raw)` 이후 데이터의 차이는 무엇인가?**  

    `raw`는 모델이 그대로 반환한 **문자열 원본**입니다.  
    `json.loads(raw)`를 거치면 JSON 문자열이 Python의 `dict`, `list`, `None` 같은 자료형으로 변환됩니다.
    
3. **`json.loads()`가 성공했는데도 별도 Validation이 필요한 이유는 무엇인가?**

    JSON 문법이 맞는 것과 **내용이 우리가 원하는 구조와 값인지**는 다르기 때문입니다.  
    예를 들어 `'[]'`는 정상 JSON이라 파싱은 되지만, 주문 정보는 `dict`여야 한다면 잘못된 결과입니다.
    
4. **Rule Prompt와 Few-shot Prompt는 어떤 차이가 있는가?**  

    Rule Prompt는 **판단 규칙을 글로 설명**하는 방식이고, Few-shot Prompt는 규칙에 더해 **입력-출력 예시를 보여주는 방식**입니다.  
    Few-shot은 모델을 다시 학습시키는 것이 아니라, 현재 프롬프트 안에서 예시를 제공하는 것입니다.
    
5. **Accuracy와 Format Rate를 따로 측정해야 하는 이유는 무엇인가?**  

    모델이 **정답을 맞혔는지**와 **출력 형식을 지켰는지**는 서로 다른 문제이기 때문입니다.  
    예를 들어 정답이 `결제`인데 모델이 `"이 문의는 결제입니다."`라고 답하면 내용은 맞아도 라벨 하나만 출력하라는 형식은 어긴 것입니다.
    
6. **개발용 데이터와 최종 평가 데이터를 나누는 이유는 무엇인가?**  

    개발용 데이터는 프롬프트를 수정하고 비교하는 데 사용하고, 최종 데이터는 **처음 보는 데이터에서도 잘 동작하는지 확인**하기 위해 따로 둡니다.  
    최종 데이터를 보면서 계속 수정하면 진짜 성능을 제대로 평가하기 어렵습니다.
    
7. **`reply()` 함수에서는 왜 LLM API가 두 번 호출될 수 있는가?**  

    첫 번째 호출은 `classify()`에서 질문의 카테고리를 분류하기 위해 사용하고, 두 번째 호출은 `answer_faq()`에서 선택된 FAQ를 근거로 답변을 만들기 위해 사용합니다.
    
8.  **FAQ에 없는 정보를 모델이 지어내지 않게 하기 위해 어떤 규칙을 사용했는가?**  

    `FAQ_POLICY`에서 **제공된 FAQ만 근거로 답하고**, FAQ에 답이 없으면 `"자료에서 확인할 수 없습니다."`라고 답하도록 지시했습니다. 또한 실시간 조회나 실제 처리를 했다고 말하지 않도록 제한했습니다.
    
9. **`os.getenv()`와 `getpass()`는 API Key를 다룰 때 각각 어떤 역할을 하는가?**  

    `os.getenv()`는 환경변수에 미리 저장된 API Key를 가져옵니다.  
    `getpass()`는 환경변수에 값이 없을 때 사용자가 직접 API Key를 입력하게 하되, 화면에 입력값이 보이지 않도록 합니다.
10. **오늘 실습의 `FAQ_BY_CATEGORY` 방식과 실제 RAG는 어떤 점이 다른가?**  

	오늘 실습은 Python `dict`에 FAQ를 미리 넣고, 분류 결과에 따라 **정해진 FAQ 문자열을 직접 선택**합니다. 반면 RAG는 보통 질문에 맞는 문서를 **검색(Retrieval)**해서 관련 문맥을 찾아 LLM에 전달합니다.

# 1. 오늘 공부한 것

오늘은 지금까지 배운 LangChain의 개별 기능을 실제 문서 Q&A 애플리케이션으로 통합하는 과정을 공부했다.

- HumanMessage / AIMessage / Chat History
- session_id
- MessagesPlachholder
- Streaming / Callback
- Tracing / Langfuse
- Retry / Fallback
- Graceful Degradation 
- Document Q&A 통합 설계
- QAResponse / 출처 검증
- LCEL과 LangGraph의 사용 경계

전체적으로 보면:

```
개별 LangChain 기능 학습
		↓
	대화 기억
		↓
실시간 출력과 실행 관찰
		↓
	오류 복구
		↓
Retriever + Memory + Model 통합
		↓
검증된 문서 Q&A 앱
		↓
복잡해지면 LangGraph 검토 
```

# 2. 핵심 개념 정리

오늘 내용은 너무 잘게 나누기보다 6개의 큰 개념으로 묶어서 이해하는 것이 좋다.

### 2-1. 대화 기록과 Session History

정의: LangChain에서는 대화를 일반 문자열로만 저장하지 않고 역할이 포함된 메시지 객체로 표현한다.

- HumanMessage : 사용자 질문
- AIMessage : AI의 답변
- SystemMessage : 모델 역할과 원칙

한 세션의 메시지는 InMemoryChatMessageHistory에 순서대로 저장한다

쉽게 말해 History = 지금까지 나눈 대화 기록 

InMemoryChatMessageHistory는 LangChain과 같은 AI 프레임워크에서 대화의 메시지 기록을 애플리케이션의 RAM(메모리)에 임시로 저장하는 데 사용되는 핵심 유틸리티 클래스이다. 

예:

```
HumanMessage("제 이름은 민지입니다.")
        ↓
AIMessage("민지님 반갑습니다.")
        ↓
HumanMessage("제 이름이 뭐였죠?")
```

## session_id란?

session_id는 대화 자체가 아니라 **어떤 대화 기록을 가져올지 찾는 키**이다.

```
student - a
	↓
History A
	↓
student - b
	↓
History B
```

즉: **session_id가 다르면 서로 다른 대화 기록을 사용한다.**

예:

```
사용자 A: "내 이름은 민지야"
사용자 B: "내 이름은 철수야"
```

session을 구분하지 않으면 모델이 누구의 이름인지 혼동할 수 있다. 

### 왜 필요한가? 
- 여러 사용자가 같은 챗봇을 사용하면 대화가 섞이면 안되기 떄문에

예:

```
사용자 A: "내 이름은 민지야"
사용자 B: "내 이름은 철수야"
```

session을 구분하지 않으면 모델이 누구의 이름인지 혼동할 수있다. 

장점
- 사용자별 대화 분리
- 이전 질문과 답변 유지
- 자연스러운 연속 대화 가능

단점 / 주의점

InMemoryChatMessageHistory는 현재 Python 프로세스 메모리에만 존재한다.
| 프로그램을 종료하면 기록도 사라진다.

실제 서비스에서는 이후 Redis, DB 등의 영구 저장소가 필요할 수 있다. 

## 2-2. MessagesPlaceholder와 실제 대화 기억

History를 저장했다고 LLM이 자동으로 기억하는 것은 아니다.
다음 요청을 보낼 때 이전 메시지를 다시 Prompt에 넣어야 한다.

### MessagePlaceholder

**MessagePlaceholder**(메시지 플레이스 홀더)는 Prompt 안에서:
| 여기에 이전 메시지 목록을 넣어주세요 라는 자리이다.

```python
prompt = ChatPromptTemplate.from_message([
	("system", "친철하게 답하세요"),
	Messagesplaceholder(variable_name="history"),
	("human", "{question}")	
])
```

흐름:

```
SystemMessage
	↓
이전 History
	↓
현재 질문
```

자료에서는 **system → history → 현재 질문** 순서로 사용한다.

전체 대화 처리 과정

```
session_id
	↓
History 조회
	↓
MessagesPlaceholder에 이전 대화 넣기
	↓
현재 질문 추가
	↓
LLM 호출
	↓
답변 생성
	↓
현재 질문 + 답변 Histroy 저장
```

실무 사용
- 고객 상담 챗봇
- 개인 AI 비서
- 학습 튜터
- 상담 기록 기반 후속 질문 

## 2-3. Streaming, Callback, Tracing

이 세 개는 비슷해 보이지만 역할이 다르다.

| 개념        | 역할                    |
| --------- | --------------------- |
| Streaming | 답변을 생성되는 대로 사용자에게 보여줌 |
| Callback  | 실행 중 발생한 이벤트를 관찰      |
| Tracing   | 전체 실행 흐름과 측정값을 기록     |

### Streaming 
Stream( )은 최종 답변 전체를 기다리지 않고 문자열 조각을 순서대로 받는 방식이다.

```
"Lang"
"Chain"
"은 "
"프레임워크입니다."
```

	↓

```
LangChain은 프레임워크입니다
```

사용자는 답변이 끌날떄 까지 기다리지 않아도 된다.

장점
- 체감 응답 속도 향상
- ChatGPT 같은 UX 구현
- 긴 답변에 효과적

단점
- 조각을 합치는 코드 필요
- 조각의 크기나 경계가 일정하지 않음

자료에소는 스트리밍 조각을 화면에 즉시 출력하면서 리스트에 저장한 뒤 마지막에 "".join( )으로 전체 문자열을 다시 만들 수 있다고 설명한다. 

### Callback
Callback은 답변을 만드는 기능이 아니다
| 실행 중 어떤 일이 발생했는지 바라보는 관찰자

```
on_chat_model_start()
		↓
on_llm_new_token()
		↓
on_llm_end()
		↓
	오류 발생
		↓
on_llm_error()
```

Callback이 결과를 반영하지 않고 모델의 시작, 출력, 완료, 오류 이벤트를 관찰한다. 

### Tracing
**Tracing은 한 요청이 어떤 단계를 거쳤는지 연결해서 기록하는 것이다.**

```
질문
 ↓
Prompt
 ↓
Model
 ↓
Parser
 ↓
답변
```

여기에:
- 실행 시간
- 입력 토큰
- 출력 토큰
- 오류 
- 실행 경로
등을 함께 기록한다. 

### Langfuse
Langfuse 는 이런 Trace를 외부 서비스에서 확인할 수 있도록 도와주는 관측 도구이다.

```
LangChain 실행
	↓
Callback
	↓
Langfuse
	↓
Trace 확인
```

Langfuse를 선택 기능으로 취급한다.
Langfuse 연결에 실패하더라도 핵심 앱은 계속 동작해야 한다. 

## 2-4. Retry 와 Fallback

오늘 가장 중요한 안정성 개념이다

### Retry
Retry는 **같은 경로를 다시 실행**한다.

예:

```
Model 호출
	↓
일시적 서버 오류
	↓
다시 Model 호출
```

Retry는 모든 오류에 사용하는 것이 아니다. 

| 오류           | Retry |
| ------------ | ----- |
| 순간 서버 장애     | 가능    |
| 일시 연결 오류     | 가능    |
| 빈 질문         | X     |
| 잘못된 자료형      | X     |
| 코드 TypeError | X     |
**다시 실행하면 회복될 가능성이 있는 오류에만 Retry를 적용**하도록 설명

### with_retry( )

```python
model_step.with_retry(
	retry_if_exception_type=(TemporaryModelError,),
	stop_after_attempt=2
)
```

stop_after_attempt=2 : 최초 호출 + Retry를 합쳐 최대 2번

### Fallback
Fallback : Primary가 계속 실패하면 다른 경로를 사용 

```
Primary Model
	↓
   실패
    ↓
   Retry
    ↓
계속 실패
	↓
Fallback Model / 기능
```

Retry와 비교하면:
- Retry = 같은 길 다시 재시도
- Fallback = 다른 길로 우회

### Graceful Degradation
Fallback이 실행됐다고 정상 결과인 척하면 안된다.

예:

```python
status="degraded"
route="fallback"
```

즉, **서비스는 계속 제공하지만 기능이 제한되었다는 사실을 명확하게 알려주는 것**
이 **Graceful Degradation(우아한 기능 저하)**이다.

## 2-5. Document Q&A 통합 앱
지금까지 따로 배운 기능들이 오늘 실제 앱 구조로 합쳐졌다.

Document Q&A 앱을 다음 책임으로 분리한다.

```
입력 확인
↓
History 조회
↓
Retriever
↓
Prompt
↓
Model
↓
Structured Parser
↓
출처 검증
↓
History 저장
```

### QAResponse
모든 결과를 같은 Pydantic 객체로 관리한다.

```python
class QAResponse(BaseModel):
	status: Literal["grounded", "not_found"]
	answer : str
	sources: list[str]
```

### 상태
grounded

```
문서를 찾음
→ 문서 근거로 답변
→ sources 존재
```

### not_found

```
관련 문서를 찾지 못함
→ 모델 호출하지 않음
→ sources=[]
```

grounded 결과에는 최소 하나의 출처가 필요하고, not_found에는 출처가 없어야 한다는 규칙까지 Pydantic 으로 검증한다.

## 왜 검색 결과 0건으로 LLM을 호출하지 않는가?

```
Retriever
↓
검색 결과 없음
↓
LLM 호출 X
↓
not_found
```

문서가 없는데 LLM을 호출하면 모델이 일반 지식으로 답변할 수 있기 때문에 
이건 RAG에서 굉장히 중요한 설계이다.

## History와 Context의 차이
오늘 반복해서 나온 핵심 구분이다.

| 개념      | 내용                  |
| ------- | ------------------- |
| History | 현재 사용자와 이전에 나눈 대화   |
| Context | Retriever가 찾은 외부 문서 |
두 값은 서로 대신할 수 없다고 명확히 구분한다. 

예:

```
History
"아까 내 이름은 민지라고 했어."

Context
"Retriever는 질문과 관련된 Document를 검색합니다."
```

Prompt에는 둘을 함께 넣을 수 있습니다.

```
이전 대화:
{history}

문서 근거:
{context}

현재 질문:
{question}
```

## 출저 검증
Parser가 성공했다고 해서 모델이 주장한 sources가 실제 검색 문서라는 뜻은 아니다.

따라서:
LLM: sources=["doc-999"]

Retriever: ["doc-003"]

이라면 잘못된 결과이다. 그래서 실제 Retriever 결과와 비교한다.

```python
if not set(result.sources).issubset(allowed_sources):
	raise ValueError(...)
```

구조화 검증 + 실제 출처 검증을 별도로 수행한다. 
그리고 이 검증이 모두 끝난 뒤에만 History에 저장한다. 

## 2-6. LCEL과 LangGraph 관계
오늘 마지막 단계에서는:
"LangChain LCEL로 계속 만들 것인가, LangGraph로 넘어갈 것인가"를 판단했다

LCEL이 적합한 경우

```
입력
↓
검색
↓
모델
↓
검증
↓
출력
```

처럼 한 방향으로 진행되고 끝나는 흐름이다.

다음 조건이면 LCEL로 충분하다
- 한 요청 안에서 시작하고 끝남
- 순서가 앞에서 뒤로 진행
- Retry 횟수가 명확하게 제한
- 사람 승인을 기다리지 않음
- 프로세스 종료 뒤 상태 복원 필요 없음

### LangGraph가 필요한 상황
다음 중 하나라도 필요하면 LangGraph를 검토한다.

| 요구               | 예시                  |
| ---------------- | ------------------- |
| Loop             | 검색 결과가 안좋으면 다시 검색   |
| Resume           | 작업 중단 후 나중에 다시 시작   |
| Human Approval   | 담당자 승힌 후 계속 진행      |
| Persistent State | 서버 재시작 후에도 진행 상태 복원 |
### 한눈에 비교

|        | LCEL                    | LangGraph                |
| ------ | ----------------------- | ------------------------ |
| 구조     | 직선/단순 분기(DAG)           | 그래프(루프 가능)               |
| 상태     | 입출력 전달 위주               | 명시적 공부 State             |
| 적합한 용도 | RAG, 요약, 번역 등 정해진 파이프라인 | 에이전트, 멀티 에이전트, 복잡한 워크플로우 |
| 난이도    | 쉬움                      | 상대적으로 높음                 |

### 언제 뭘 쓰나?

- **순서가 정해진 단순한 흐름** → LCEL
- **LLM이 스스로 판단해서 반복·분기하는 에이전트** → LangGraph

둘은 경쟁 관계가 아니라 같이 쓴다. 
LangGraph의 각 노드 안에서 LCEL 체인을 호출하는 식이 흔하다.

# 5. 실제 LLM 프로젝트에서는 어떻게 사용되는가?
예를 들어 사내 문서 Q&A 챗봇

| 단계  | 구성 요소              | 역할                        |
| --- | ------------------ | ------------------------- |
| 1   | 사용자                | 질문                        |
| 2   | session_id         | 사용자 대화 구분                 |
| 3   | History            | 앞선 대화 불러오기                |
| 4   | Retriever          | 사내 문서 검색                  |
| 5   | Context            | 검색 문서를 prompt용으로 변환       |
| 6   | Prompt             | 질문 + History + Context 결합 |
| 7   | LLM                | 문서 기반 검증                  |
| 8   | Pydantic Parser    | 답변 구조 검증                  |
| 9   | Source Validation  | 실제 검색 문서 출처 확인            |
| 10  | Retry              | 일시 모델 장애 재시도              |
| 11  | Fallback           | 모델 장애 지속시 제한된 대체 결과       |
| 12  | Callback / Tracing | 실행 시간, 경로 관찰              |
| 13  | History 저장         | 검증된 답변만 저장                |
| 14  | Streaming/UI       | 사용자에게 답변 표시               |
이 구조가 바로 지금까지 배운 내용을 실제 서비스로 연결한 형태이다.
통합 앱을 
입력확인 → 검색 → History → Prompt → Model/Parser → 출처 검증 → 저장 → UI 표시 
순서로 구현한다. 

# 6. 같이 알아두면 좋은 관련 개념 
- Redis → 대화 History를 메모리 밖에 저장할 때 자주 사용하는 저장소
- Vector DB → Embedding 기반 문서 검색 저장소
- Semantic Search → 키워드가 아니라 의미 기반 검색
- Reranking → 검색된 문서의 순위를 다시 평가
- LangSmith → LangChain/LangGraph 실행 관찰, 평가 플랫폼
- Langfuse → 범용 LLM Tracing, 평가, Prompt 관리 플랫폼
- Persistence → 프로그램 종류 뒤에도 상태를 유지하는 기능
- Human-in-the-loop → AI 실행 중 사람이 승인하거나 수정하는 구조 
- Observability → 서비스 내부에서 무슨 일이 일어났는지 확인할 수 있게 만드는 것

# 7. 용어 핵심 정리

1. session_id
- 어떤 대화 History인지 찾는 키
- 사용자별 채팅 기록 분리

2. History
- 이전 대화 저장
- 대화 맥락 유지

3. MessagesPlaceholder
- 이전 메시지를 Prompt에 삽입
- LLM이 앞선 대화를 참고

4. Streaming 
- 생성되는 답변을 바로 전달
- 실시간 채팅 UI

5. Callback
- 실행 이벤트 관찰
- 시작, 완료, 오류 확인

6. Tracing
-  한 요청의 실행 경로 기록
- 디버깅, 운영 관측

7. Retry
- 같은 경로 다시 실행
- 일시적인 오류

8. Fallbacxk
- 대체 경로 실행
- 문서 Q&A 결과 검증

9. LCEL
- 직선적인 LLM 파이프라인
- 일반적인 Q&A / RAG

10. LangGraph
- 상태, 반복, 재개, 승인이 있는 흐름
- 복잡한 Agent 시스템 

# 8. 내가 설명할 수 있어야 하는 질문

1. **`session_id`와 `History`는 어떤 차이가 있는가?**

- session_id는 대화를 구분하는 식별자(키)이고, History는 그 키에 저장된 실제 메세지 목록(값)이다. 딕셔너리의 Key와 value 관계라고 보면된다. 

2. **History를 저장했는데도 `MessagesPlaceholder`가 필요한 이유는 무엇인가**?

- 저장과 주입은 별개 문제이다. 저장소에 메시지가 있어도 프롬프트에 자리가 만들어 두지 않으면 모델에게 전달되지 않는다. 

3. **Retriever의 `Context`와 대화 `History`는 왜 서로 다른가?**

- 섞이면 안되는 이유는 출처 검증 때문이다. Context는 sources로 인용할 수 있어야 하는데, 대화 내용이 섞이면 "무엇이 근거 문서인지"가 흐려진다. 그래서 프롬프트에서도 별도 슬롯으로 분리한다.

4. **Streaming과 Callback은 각각 사용자와 개발자에게 어떤 역할을 하는가?**

- Streaming은 사용자용이다. 토큰이 생성되는 대로 플려보내 체감 대기시간을 줄인다.

- Callback은 개발자용이다. 각 단계의 입력, 출력, 지연시간 , 토큰 사용량, 에러를 기록해서 디버깅과 비용 분석에 쓴다.

- 사용자는 응답을 보고, 개발자는 그 응답이 만들어진 과정을 본다. 서로 대체 관계가 아니라 동시에 켜져 있다. 

5. **Retry와 Fallback은 어떤 기준으로 구분하는가?**

- "기준은 같은 시도를 반복하면 성공할 가능성이 있는가" 이다 
- Retry는 일시적 오류에 쓴다. 
  네트워크 타임아웃, 429 rate limit, 일시적 5xx 처럼 다시 하면 풀릴수 있는 경우이다
  대기시간을 늘려가며(backoff) 같은 모델을 재시도한다.
- Fallback은 지속적 실패에 쓴다. 
  해당 모델 장애, 컨텍스트 초과, 지속적인 파싱 실패처럼 같은 방식으로는 계속 실패하는 경우이다
  다른 모델이나 다른 경로로 바꾼다. 
- 그래서 순서가 Retry → (계속 실패) → Fallback이다. 입력 자체가 잘못된 400류 에러는 둘 다 의미가 없어서 바로 에러로 처리하는게 맞다. 

6. **검색 결과가 0건일 때 LLM을 호출하지 않는 이유는 무엇인가?**

- 환각 방지: 근거가 없는 상태로 호출하면 모델이 학습된 지식이나 추측으로 그럴듯하게 답한다.
  RAG의 전제인 "문서 기반 답변"이 깨진다.
- 비용, 지연 절약: 어차피 쓸 수없는 답을 위해 토큰을 쓰는 셈이다.
- 예측 가능한 응답: "관련 문서를 찾지 못했습니다" 라는 정해진 응답을 줄 수 있다. 
- 이 분기는 LCEL에서는 RunnableBrach로, 복잡해지면 LangGraph의 조건부 엣지로 구현한다.

6. **Pydantic Parser를 통과한 뒤에도 `sources`를 다시 검증해야 하는 이유는 무엇인가?**

- Pydantic은 형태(타입, 필수 필드)만 검증하고, 내용의 진실성은 검증하지 못한다.
- 모델이 존재하지 않는 문서 ID를 sources에 만들어 넣어도 파서는 통과시킨다. 
  그래서 별도로 "이 source가 실제 검색된 문서 목록에 있는가"를 대조해야 한다. 
- 파서는 문법 검사, 출처 검증은 사실 검사이다. 

6. LCEL로 충분한 상황과 LangGraph가 필요한 상황은 무엇인가?****

- LCEL로 충분한 경우: 순서가 고정된 파이프라인이다. 이번 그림처럼 병렬(Retriever + History), 단순 분기(0건이면 종료), Retry/Fallback 정도는 LCEL로 가능하다.
- LangGraph가 필요한 경우: 아래처럼 루프와 상태 기반 제어가 필요할 때이다.
- 출처 검증 실패 시 재생성하고, 최대 N회까지 반복
- 검색 결과가 부족하면 쿼리를 바꿔 재검색
- LLM이 도구 사용 여부를 스스로 결정(에이전트)
- 사름 승인 대기 후 중단 / 재개 (humman-in-the-loop)

판단 기준은 "흐름이 위에서 아래로만 가는가, 되돌아 가는 구간이 있는가"이다.
되돌아가야 하면 LangGraph, 아니면 LCEL이다. 

# 9. 오늘의 한줄

- 오늘은 LangChain의 Prompt, Model, Parser, Retriever, History, Streaming, Tracing, Retry, Fallback을 하나의 문서 Q&A 앱으로 연결하고, 단순한 직선 흐름은 LCEL로 유지하되 반복, 재개, 사람 승인, 영속 상태가 필요해지면 LangGraph를 검토하는 기준까지 배웠다.

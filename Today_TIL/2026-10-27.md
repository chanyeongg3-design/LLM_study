# RAG - 평가 기준을 만들고, 실패 원인에 맞게 개선하기

## 평가와 개선 전체 흐름

오늘은 오전에 **RAG가 얼마나 잘 동작하는지 평가하는 방법**을 배우고, 오후에는 평가에서 발견한 문제를 개선하는 방법을 공부했다.



### 1. 오늘은 무엇을 공부했을까?

Golden Dataset: 질문과 참고 답변, 근거 문서를 모아 평가 기준을 만든다.

Hit@k: 상위 k개 검색 결과에서 필요한 문서를 하나라도 찾았는지 확인한다.
 
Recall@k: 필요한 문서 전체 중 몇 개를 찾았는지 확인한다.
 
RAGAS: 답변이 근거에 맞는지, 질문과 관련 있는지 등을 여러 지표로 평가한다.

Parent-Child / Context Compression: 검색한 위치의 문맥을 넓히고 필요한 문장을 남긴다. 

Corrective / Agentic RAG: 검색 결과를 확인하고 재검색하거나 다음 행동을 선택한다.

GraphRAG / Multimodal RAG: 문서 사이의 관계와 표·이미지의 구조를 검색 근거로 활용한다. 

오늘은 RAG 시스템에서 **검색과 답변의 품질을 평가하고, 발견한 문제의 원인에 맞춰 개선하는 방법**을 공부했다. 

오전 8장에서는 질문과 정답 기준을 만들고 검색 결과의 답변을 나누어 평가했다. 오후 9장에서는 그 평가에서 드러난 빈틈을 Parent 확장, 재검색, 그래프, 시각 자료 검색으로 보완하는 흐름을 배웠다. 

두 수업을 연결하면서 가장 중요하게 정리한 것은 점수가 좋아졌는지 확인하는 것과 함께, 필요한 정보가 최종 답변까지 전달됐는지 살펴봐야 한다는 점이었다. Context는 이 과정에서 모델에 실제로 전달하는 근거 문장이다. 

답변 하나가 괜찮아 보이는지만 확인하기보다, 질문과 정답 기준을 먼저 정해 두고 같은 조건에서 비교해야 한다는 점을 배웠다.

특히 검색 평가 점수가 높더라도 답변에 필요한 문장이 실제 Context에 들어 있는지는 따로 확인해야 한다. Context는 답변을 만들 때 모델에 실제로 전달하는 근거 문장이다. 

### 2. 최종 핵심 요약

- Golden Dataset : 질문·참고 답변·근거 문서·답변 가능 여부를 정리한 평가 자료
- dev / test : 설정을 고치고 개발용 자료와 마지막에 확인하는 평가용 자료
- Hit@k / Recall@k : 근거를 하나라도 찾았는지와 필요한 근거를 얼마나 찾았는지 구분
- Faithfulness : 답변 주장이 Context에 의해 뒷받침되는지 평가
- Answer Relevancy : 답변이 사용자의 질문과 관련 있는지 평가
- Context Procision / Recall : 유용한 근거가 앞에 있는지와 필요한 사실이 Context에 있는지 평가
- 전후 비교 : 같은 질문과 조건을 유지하며 바꾼 요소의 효과를 확인
- Parent-Child : 검색용 작은 청크와 답변용 넓은 문맥을 분리
- Context Compression : 문맥을 줄이면서 금액·단위·부정·승인 조건 보존
- Corrective RAG : 검색 품질을 확인하고 부족한 결과를 보정하는 접근
- Agentic RAG : 다음 검색 문장·도구·답변·중단 여부를 선택하는 흐름
- Graph RAG : 개체와 관계, 조건과 출처를 연결해 탐색
- Local / Global / DRIFT : 개체 주변 탐색·전체 보고서 종합·후속 질문으로 상세 탐색
- Multimodal RAG : 표와 이미지의 구조까지 근거로 활용
- Colpali / maxSim : 페이지를 여러 벡터로 표현해 질문과 잘 맞는 부분을 비교
### 2-1. Golden Dataset - 평가에 사용할 정답 기준

**정의**: 평가용 질문과 원문을 확인해 작성한 참고 답변, 근거 문서 ID 등을 모든 자료다. 

**사용이유**: 검색 방법을 바꿀 때마다 서로 다른 질문으로 비교하면 무엇이 좋아졌는지 판단하기 어렵기 때문이다.

**작동 원리**: 
- 질문마다 필요한 사실과 근거 문서를 정한다.
- 답할 수 있는 질문과 자료로 확인할 수 없는 질문을 구분한다.
- 개발용 dev와 최종 확인용 test를 나눈다.
- 같은 평가 자료로 여러 방법의 결과를 비교한다. 

강의의 golden.jsonl은 질문 20개를 dev 12개와 test 8개로 나눴다. 답변 가능한 질문은 16개, 자료로 답할 수 없는 질문은 4개다.

**출장비 질문의 정답에는 식비 1일 3만원, 숙박비 1박당 12만원, 두 한도 합산 불가**가 함께 들어가야 한다.
금액만 맞고 단위나 조건이 바뀌면 정답으로 보기 어렵다. 

검색에는 질문만 보낸다. 참고 답변과 정답 문서 ID는 평가에만 사용한다.


## 2-2. 검색·답변 평가와 개선 전후 비교

### 1) Hit@k와 Recall@k - 필요한 문서를 찾았는지 평가

**정의**: 상위 k개 검색 결과에 필요한 근거가 얼마나 포함됐는지 확인하는 지표다. 강의에서는 **청크 k개를 먼저 고른 뒤 문서 ID**로 비교했다

**사용이유**: 관련 문서를 하나 찾은 것과 답변에 필요한 문서를 모두 찾은 것을 구분하기 위해 사용한다.

계산 방법: 
- Hit@k : 정답 문서를 하나라도 찾으면 1, 없으면 0
- Recall@k : 찾은 정답 문서 수 + 필요한 정답 문서 수 

| 필요한 문서: meal·travel | Hit | Recall |
| ------------------- | --- | ------ |
| meal만 찾음            | 1   | 0.5    |
| meal과 travel을 모두 찾음 | 1   | 1.0    |
Hit가 1이어도 숙박비 근거가 없을 수 있다. 또 k를 늘려 무관한 문서가 추가돼도 Recall은 내려가지 않을 수 있어, 잡음과 Context 길이도 함께 봐야 한다.

### 2) RAGAS - 답변과 근거의 관계 평가

**정의**: RAG의 답변과 검색 근거를 여러 관점에서 평가하는 지표 모음이다.

**사용 이유**: 문서를 찾았어도 답변의 금액이 틀리거나 질문과 다른 내용을 말할 수 있기 때문이다.

| 지표                | 확인하는 내용                      |
| ----------------- | ---------------------------- |
| Faithfulness      | 답변의 주장이 실제 Context에 근거하는가?   |
| Answer Relevancy  | 답변이 사용자의 질문과 관련 있는가?         |
| Context Precision | 유용한 근거가 검색 결과 앞쪽에 있는가?       |
| Context Recall    | 참고 답변에 필요한 사실이 Context에 있는가? |
강의에서는 숙박비 한도와 증빙을 묻는 질문에 사람이 작성한 답변 A·B·C를 비교했다.

- A: 숙박비 1박당 12만원과 숙박 영수증을 모두 설명
- B: 영수증은 맞지만 숙박 한도를 30만원으로 설명
- C: 식비 1일 3만원을 설명해 숙박비 질문에 답하지 않음

수동으로 주장을 나누어 확인한 근거 일치 비율은 A 1.0 , B 0.5 , C 1.0 이었다. 이 비율은 RAGAS 실행 점수와 구분해야 한다.

C는 근거에 맞는 사실을 말했지만 질문에 답하지 않았다. 근거 일치와 질문 적합성을 따로 봐야 하는 이유다. 평가에도 모델이 실제로 받은 Context를 사용해야 검색이나 압축 과정의 누락을 확인할 수 있다. 

### 3) 개선 전후 비교 - 같은 조건에서 하나씩 변경

**정의**: 질문과 정답 기준 등을 고정하고 바꾼 요소가 결과에 어떤 영향을 주는지 비교하는 과정이다. 

**사용 이유**: 검색 방법과 청크 크기, k를 동시에 바꾸면 어떤 변경이 효과를 냈는지 알기 어렵기 때문이다.

강의에서는 질문·정답·80자 청크와 20자 겹침·현행 필터·k=3을 고정하고 검색 방법을 바꿨다. 


| 강의의 검색 평가                         | BM25 | Dense | Hybrid |
| --------------------------------- | ---- | ----- | ------ |
| 답변 가능한 dev10<br>개: Hit@3·Recall@3 | 0.9  | 1.0   | 1.0    |
| 답변 가능한 test 6개:<br>Hit@3·Recall@3 | 1.0  | 1.0   | 1.0    |
dev의 0.1차이는 교육비 정산 증비을 묻는 q10 한 질문에서 나왔다. 평균을 질문별로 풀어 봐야 개선 지점을 알 수 있었다.

하지만 교육비 문서 ID를 찾은 것과 수료증·영수증 문장이 든 청크를 확보한 것은 다르다. 작은 평가셋의 1.0을 서비스 전체 성공률로 확대해서도 안 된다.

### 4) Corrective / Agentic RAG - 결과를 보고 다시 검색

**정의**: 검색 결과를 확인하고 부족하면 보정하거나 다음 행동과 종류 여부를 선택하는 접근이다.

**사용이유**: 첫 검색이 실패했다고 해서 자료에 답이 없다고 판단할 수는 없기 때문이다.

강의의 흐름:
- 교육비 정산 증빙은 무엇인가요? 로 검색 -> 빈 결과
- 교육비 지원 수강 완료 후 제출합니다 로 재검색
- education@60에서 수료증과 영수증 문장 확보
- 반복 질의의 검색 횟수 제한을 확인하며 종료

| 종료 상태            | 뜻                 |
| ---------------- | ----------------- |
| candidates_ready | 검토할 후보가 생김        |
| repeated_query   | 같은 질의의 반복을 발견해 중단 |
| search_limit     | 정해 둔 검색 횟수에 도달    |

### 5) GraphRAG와 Multimodal RAG - 관계와 시각 정보 활용

**GraphRAG - 여러 규정의 관계 연결**

**정의**: 규정·승인자·증빙 같은 대상을 노드로, 대상 사이의 관계를 간선으로 표현해 탐색하는 방법이다.

**사용 이유**: 여러 문서에 흩어진 관계를 함께 따라가야 하는 질문에 활용할 수 있기 때문이다.

예를 들어 **“영수증을 제출하는 규정과 각 규정의 승인자는?”**에는 다음 관계를 살펴봐야 한다.

- 교육비: 영수증·수료증 제출, 팀장 승인 시점은 수강 전
- 출장 숙박: 숙박 영수증 제출, 한도 초과 숙박 예약 전 담당 임원 서면 승인
- 출장 식비: 영수증 제출, 해당 문서·그래프에 승인자 명시 없음

| 탐색 방식  | 사용하는 정보                            |
| ------ | ---------------------------------- |
| Local  | 질문과 관련된 개체 주변의 관계와 원문              |
| Global | 여러 커뮤니티의 요약 보고서                    |
| DRIFT  | 관련 보고서에서 시작해 후속 질문과 Local 탐색으로 상세화 | 

## 3. 공부하면서 고민했던 부분

오늘 가장 고민했던 부분은 **검색 평가 점수가 낲아도 답변이 충분하지 않을 수 있다는 점**이다.

문서 Recall이 1.0 이면 필요한 정보가 모두 들어왔다고 생각하기 쉬웠다. 하지만 이번 지표는 문서 ID를 비교했다. 같은 교육비 문서라도 앞 청크에는 한도와 신청 조건만 있고, 뒤 청크에 수료증과 영수증이 있을 수 있다. 문서 ID를 찾은 뒤에도 본문과 최종 Context를 확인해야 했다.

답변 C처럼 근거에 맞는 말을 하면서 질문에는 답하지 않는 경우도 있었다. 지표의 숫자뿐 아니라 무엇을 기준으로 계산했는지와 실제 답변 문장을 함께 읽어야겠다고 정리했다.

이 문제는 문맥을 넓히고 줄이는 과정과도 연결됐다. Parent 전체를 가져오면 조건을 복원할 수 있지만 Context가 길어진다. 반대로 압축하면서 승인 조건을 빼면 같은 질문의 답이 달라질 수 있다.

결국 개선 방법을 고르기 전에 원문 → 청크 → 검색 결과 → 최종 Context 중 어디에도 정보가 처음 빠졌는지부터 확인하는 것이 중요했다.

## 4. 오늘 느낀 점

오늘은 RAG의 평가와 개선이 하나의 흐름으로 이어진다는 것을 배웠다.

평가 기준이 분명해야 어떤 문제가 있는지 찾을 수 있고, 문제의 원인을 알아야 적절한 방법으로 고칠 수 있었다. 잘린 조건은 Parent로 확장하고 질문 표현이 맞지 않으면 재검색하고, 관계가 필요하면 그래프를 살피고, 표와 이미지가 중요하면 시각 구조를 보존해야 했다.

좋아 보이는 답변 하나를 고르는 것 보다 같은 질문으로 어떤 오류가 줄었고, 필요한 근거가 끝까지 남았는지 설명하는 과정이 중요하다고 느꼈다. 새로운 기술의 이름을 아는 것과 함께 왜 질문에 그 방법이 필요한지도 설명할 수 있어야겠다.

앞으로 실험 결과에는 평균 점수뿐 아니라 질문 수와 평가 단위, 실패한 질문의 예시, 금액, 단위, 조건의 오류도 남겨야겠다고 생각했다.

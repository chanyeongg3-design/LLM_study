# LangChain 기본 체인부터 Retrieval Chain까지

## 1. 오늘 공부 한것
오늘은 LangChain에서 LLM 애플리케이션의 데이터 흐름을 구성하는 방법을 공부했다.

- **LCEL / Runnable**
- `invoke()` / `batch()` / `stream()`
- `Sequence` / `Parallel`
- `RunnableLambda` / `Passthrough` / `assign()`
- **Structured Output / Pydantic**
- **Document / Retriever**
- **Retrieval Chain**

오늘 학습의 핵심은 여러 LangChain 구성 요소를 연결해 

| 입력 → 처리 → 검색 → LLM → 검증 → 답변 |
|:---:|

형태의 LLM 애플리케이션 흐름을 만드는 것이다.

## 2. 핵심 개념 정리
### 2-1. LCEL과 Runnable

정의: **LCEL** (LangChain Expression Language)은 LangChain의 여러 구성 요소를 | 연산자로 연결하는 방식이다.

```
chain = prompt | model | parser
```

**Runnable**은 입력을 받아 처리하고 결과를 반환할 수 있는 LangChain의 공통 실행 단위이다. 

| 의 의미는: 왼쪽 단계의 출력을 오른쪽 단계의 입력으로 전달한다. 

쉽게 말하면 
- Runnable = 부품
- LCEL = 부품을 연결하는 파이프

### 왜 필요한가? 
- LLM 애플리케이션은 모델 호출 하나로 끝나지 않고 Prompt 생성, 모델 호출, 결과 반환 등의 여러 단계를 거치기 때문이다.

### 실무에서는

```
[사용자 입력]
	↓
[Prompt]
	↓
[Model]
	↓
[Parser]
	↓
[최종 결과]
```

같은 LLM 처리 파이프라인을 구성할 때 사용한다.

### 실행 방법

|    메서드    |     사용 상황      |
| :-------: | :------------: |
| invoke( ) |   요청 한 건 처리    |
| batch( )  |  여러 독립 요청 처리   |
| stream( ) | 답변을 생성되는 대로 전달 |



### 2-2. invoke / batch / stream

LangChain에서는 작업의 관계에 따라 Runnable을 여러 방식으로 조합한다.

**Sequence** : 앞 단계의 결과를 다음 단계가 사용할 때 사용한다.

```
[입력]
  ↓
[전처리]
  ↓
[Prompt]
  ↓
[Model]
```

**Parallel** : 같은 입력으로 여러 독립 작업을 수행할 때 사용한다.

```text
             ┌→ [요약]
[문서] ──────┤
             └→ [키워드 추출]
```

**데이터 가공 도구**

| 도구                  | 역할                   |
| ------------------- | -------------------- |
| RunnableLambda      | Python 함수를 Chain에 연결 |
| RunnablePassthrough | 기존 입력 유지             |
| assign( )           | 기존 dict에 새 정보 추가     |
예:

```text
question
   ↓
clean_question 추가
   ↓
context 추가
   ↓
answer 추가
```

**실무에서는** 전처리, 검색, 분류, 요약처럼 여러 작업을 하나의 LLM 파이프라인으로 연결할 때 사용한다. 

## 2-3. Structured Output와 Pydantic

LLM은 기본적으로 자유로운 자연어를 생성한다. 하지만 실제 프로그램에서는 다음처럼 정해진 
구조가 더 사용하기 쉽다.

```python
{
    "category": "오류",
    "summary": "KeyError 관련 질문",
    "needs_code": True
}
```

|     필드     |        뜻        |
| :--------: | :-------------: |
|  category  |     질문의 분류      |
|  summary   |   질문의 한 줄 요약    |
| needs_code | 답변에 코드가 필요한지 여부 |
즉, 이 dict는 "사용자가 KeyError에 대해 물어봤고, 오류 분류이며, 코드가 필요한 질문" 이라는 **LLM의 분석 결과**이다.

Pydantic을 이용하면 필요한 필드와 타입을 정의할 수 있다.

```python
class QuestionClassification(BaseModel):
    category: Literal["개념", "코드", "오류"]
    summary: str
    needs_code: bool = False
```

**주요 역할**

|            개념             |          역할           |
| :-----------------------: | :-------------------: |
|         BaseModel         |       데이터 구조 정의       |
|          Literal          |        허용값 제한         |
| with_structured_output( ) |  LLM 결과를 구조화 객체로 받음   |
|   PydanticOutputParser    | JSON 문자열을 검증 후 객체로 변환 |
검증에 실패하면 잘못된 결과를 그대로 사용하지 않고:

```text
첫 출력
 ↓
검증
 ↓
실패
 ↓
수정 요청 1회
 ↓
재검증
 ↓
성공 / 최종 실패
```

처럼 처리한다.

**실무에서는**
- 분류 결과
- API 응답
- DB 저장 데이터
- 조건 분기
- 자동화 시스템

처럼 LLM 결과를 프로그램이 직접 사용해야 할 때 중요하다. 

### 2-4. Document → Retriever → Retrieval Chain

#### Document

외부 문서를 LangChain에서 일정한 형태로 다루기 위한 객체다.

```python
Document(
    page_content="실제 본문",
    metadata={
        "document_id": "doc-001",
        "title": "Retriever 설명",
        "source": "guide.md"
    }
)
```

|영역|역할|
|---|---|
|`page_content`|LLM이 참고할 실제 본문|
|`metadata`|ID, 제목, 출처 등의 부가정보|

### Retriever

사용자 질문과 관련된 `Document`를 찾는 역할이다.

```text
질문 str
   ↓
Retriever
   ↓
list[Document]
```

Retriever는 **답변을 만드는 모델이 아니라 검색 담당**이다.

### Retrieval Chain

검색한 문서를 실제 LLM 답변까지 연결한다.

```text
[사용자 질문]
      ↓
[Retriever]
      ↓
[관련 Document]
      ↓
[context 생성]
      ↓
[Prompt]
      ↓
[Model]
      ↓
[Parser]
      ↓
[답변]
```

`context`는 검색된 Document를 LLM이 읽기 좋은 문자열로 바꾼 것이다.

**실무에서는**

- 사내 문서 Q&A
    
- FAQ 챗봇
    
- 제품 매뉴얼 검색
    
- 교육자료 질의응답
    

같은 **문서 기반 LLM 서비스의 기본 구조**로 사용한다.

# 3. 전체 구조에서의 위치

| 단계  |       구성 요소       |         역할         |
| :-: | :---------------: | :----------------: |
|  1  |      사용자 질문       |         입력         |
|  2  | Runnable / Lambda |       입력 전처리       |
|  3  |     Retriever     |      관련 문서 검색      |
|  4  |     Document      |     검색된 원본 문서      |
|  5  |     Formatter     | Document → Context |
|  6  |      Prompt       |     질문 + 근거 구성     |
|  7  |       Model       |       답변 생성        |
|  8  | Parser / Pydantic |      결과 변환·검증      |
|  9  |       최종 결과       |    애플리케이션에서 사용     |

```text
[사용자 질문]
      ↓
[전처리]
      ↓
[Retriever]
      ↓
[Document]
      ↓
[Context]
      ↓
[Prompt]
      ↓
[LLM]
      ↓
[Parser / 검증]
      ↓
[최종 답변]
```

# 4. 개념 간 차이

|     개념      |      역할      |       언제 사용하는가       |
| :---------: | :----------: | :------------------: |
| `invoke()`  |    한 건 실행    |      사용자 요청 하나       |
|  `batch()`  |   여러 건 실행    |        대량 처리         |
| `stream()`  |   조각 단위 결과   |        실시간 채팅        |
|  Sequence   |    순차 처리     |   앞 결과가 다음 단계에 필요    |
|  Parallel   |    병렬 분기     |    같은 입력으로 여러 작업     |
|   Lambda    | Python 함수 연결 |       커스텀 전처리        |
| Passthrough |    원본 유지     |       기존 정보 보존       |
|   assign    |     값 추가     | context, answer 등 누적 |
# 5. 실제 LLM 프로젝트에서는 어떻게 사용되는가?

예를 들어 **사내 문서 Q&A 서비스**를 만든다면:

|단계|구성 요소|역할|
|---|---|---|
|1|사용자|질문 입력|
|2|RunnableLambda|질문 정리|
|3|Retriever|관련 문서 검색|
|4|Document|근거 문서|
|5|Formatter|Context 생성|
|6|Prompt|질문 + 근거 전달|
|7|Model|답변 생성|
|8|Parser|최종 문자열 변환|
|9|Pydantic|필요한 경우 구조 검증|

```text
"Retriever가 뭐야?"
        ↓
관련 문서 검색
        ↓
doc-003
        ↓
context 생성
        ↓
LLM
        ↓
"Retriever는 관련 문서를 찾는 검색 인터페이스입니다."
```

현재 배우는 구조는 이후 **RAG 시스템을 만드는 기본 뼈대**가 된다.

# 6. 같이 알아두면 좋은 관련 개념

- **Chunking** → 긴 문서를 검색 가능한 작은 단위로 나누기
    
- **Embedding** → 텍스트를 의미를 담은 벡터로 변환
    
- **Vector DB** → Embedding 저장 및 유사도 검색
    
- **Semantic Search** → 단어가 아니라 의미 기반 검색
    
- **Reranking** → 검색된 후보를 다시 평가해 순위 조정
    
- **Retrieval Evaluation** → 검색 결과 품질 평가
    

현재 과정에서는 이 기능보다 먼저 **Document → Retriever → Prompt → LLM**의 데이터 흐름을 이해하는 데 집중한다.

# 7. 복습용 핵심 정리

**LCEL / Runnable**  
→ LangChain 부품을 연결하는 구조  
→ LLM 파이프라인 구성

**invoke / batch / stream**  
→ Chain 실행 방식  
→ 한 건 / 여러 건 / 실시간 결과

**Sequence / Parallel**  
→ 작업 순서와 분기 구성  
→ 복잡한 LLM Workflow 설계

**Lambda / Passthrough / assign**  
→ Python 함수 연결, 원본 유지, 데이터 추가  
→ Chain 안에서 데이터 가공

**Structured Output / Pydantic**  
→ LLM 결과의 구조와 타입 검증  
→ 분류·저장·자동화

**Document / Retriever**  
→ 문서 저장 + 관련 문서 검색  
→ RAG의 검색 부분

**Retrieval Chain**  
→ 검색한 문서를 LLM에게 전달해 답변 생성  
→ 문서 기반 Q&A

# 8. 내가 설명할 수 있어야 하는 질문

1. LCEL에서 `|`는 어떤 역할을 하는가?
    answer : 앞 단계의 결과를 다음 단계로 넘겨 연결하는 역할을 한다. 
	 A | B = A의 결과를 B에게 넘긴다.
    
2. `invoke()`, `batch()`, `stream()`은 언제 각각 사용하는가?
    answer : 
    **invoke( )는 질문 하나를 처리할 때 쓴다. (사용자 질문 하나 )**
    그래서 챗봇에 질문 하나 보내기, 문서 하나 요약하기, API 요청 하나 처리하기 같은 상황에 가장 기본적으로 사용한다.
    
    **batch( )는 여러 입력을 한 번에 처리할 때 사용한다. (뉴스 1000개 분류)**
    뉴스 제목 100개 분류, 여러 문서 요약, 여러 테스트 데이터 평가처럼 **같은 작업을 여러 데이터에 반복해야 할 때** 유용하다.
    
    **stream( )은 결과가 전부 만들어질 때까지 기다리지 않고 생성되는 대로 조금씩 받아올 때 쓴다. (ChatGPT 같은 실시간 챗봇)**
    ChatGPT에서 답변이 한꺼번에 나타나지 않고 **글자가 계속 생성되는 것처럼 보이는 방식**과 비슷하다. 
    
3. Sequence와 Parallel은 어떤 기준으로 구분하는가?
    answer : 작업이 서로 의존하냐로 구분한다
    Sequence는 앞 단계 결과가 다음 단계에 필요할 때 사용한다.
```
    chain = prompt | model | parser
```

즉, 순서가 중요하다, 앞 작업이 끝나야 다음 작업을 할 수 있다 -> Sequence
반대로 Parallel은 여러 작업이 서로의 결과를 기다릴 필요 없이 동시에 실행될 수 있을 때 사용함.

4. Structured Output이 일반 자연어 출력보다 프로그램에서 사용하기 좋은 이유는 무엇인가?
    answer : Structured Output은 출력 형식이 정해져 있어서 프로그램이 값을 안정적으로 읽고 바로 사용할 수 있기 때문이다. 
    
5. Document, Retriever, Context는 Retrieval Chain에서 각각 어떤 역할을 하는가?
    answer :
    1. Document : 정보가 들어 있는 문서 데이터, 즉 LLM이 참고할 수 있는 원본 지식 조각
    2. Retriever : 사용자의 질문을 보고 관련 있는 Document를 찾아오는 검색기
    3. Context : Retriever가 찾아온 Document 중에서 LLM에게 실제로 전달되는 참고 내용
	   LLM은 이 Context와 사용자의 질문을 함께 보고 답변을 생성한다.  


# 9. 오늘의 한줄

LangChain은 LLM 호출뿐 아니라 입력처리, 데이터 흐름, 출력 검증, 문서 검색을 하나의 Chain으로 연결하여 실제 LLM 애플리케이션을 구성할 수 있게 해준다.
